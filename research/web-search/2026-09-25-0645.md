## 关键发现

1. **搜索工具链当前处于降级状态**：三次查询均只返回 DuckDuckGo 首页占位符，Wikipedia/HN/GitHub 全部无结果。这说明当前 WebSearch 后端要么被限流、要么 API 契约已失效——**这本身就是第一个查询主题的实证案例**。

2. **三个查询主题构成一条自洽的技术栈**：WebSearch 替代方案（基础设施层）→ 多 Agent 通信协议（协作层）→ 因果推断根因溯源（可观测性层）。这不是三个孤立问题，而是同一系统在不同抽象层的投影。

3. **搜索结果为空 ≠ 无信息**：空结果模式（统一返回 `duckduckgo.com — here`）暴露了当前搜索适配器的失败模式——它没有区分「无匹配」与「后端不可用」，这是可靠性设计缺陷。

## 值得深挖的方向

- **搜索后端的多源冗余架构**：DuckDuckGo Lite 单点依赖是脆弱性根源。可行替代：SearXNG 自托管聚合、Brave Search API、Kagi API、Exa（语义搜索）。关键不是选一个，而是**故障转移 + 结果去重 + 一致性校验**。
- **Agent 通信协议的共识层**：MCP 解决工具调用，A2A 解决 Agent 互操作，但**共识机制**（谁的结果可信、冲突如何裁决）仍是空白。可借鉴 Raft/PBFT 的简化版用于 Agent 投票。
- **因果推断用于根因溯源**：多 Agent 系统中，症状（搜索失败）与根因（API 限流 vs 网络分区 vs 适配器 bug）之间需要 do-calculus 式的干预分析，而非相关性排查。

## 与已有知识的关联

- 当前搜索失败模式 → 直接对应 **分布式系统单点故障** 经典问题，也是第三个查询的动机来源。
- 多 Agent 共识 → 与 **拜占庭容错**、**CRDT** 同源，但 Agent 场景下「恶意节点」概率低、「幻觉节点」概率高，需要新的信任模型。
- 因果溯源 → 与 **可观测性三支柱**（logs/metrics/traces）互补：traces 告诉你「发生了什么」，因果推断告诉你「为什么」。

**一句话**：这三个查询不是并列的，而是「基础设施脆弱性 → 协作层协议缺失 → 诊断层方法论」的因果链，建议按此顺序深挖。
