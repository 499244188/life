## 关键发现

1. **搜索工具本身失效**：三次搜索的 DuckDuckGo 结果均只返回首页链接（`https://duckduckgo.com/ — here`），Wikipedia/HN/GitHub 全部无结果。这不是“没有相关信息”，而是搜索管道本身没有真正执行查询——可能是 API 配额、反爬拦截或集成层 bug。**在评估 Tavily/Brave/SerpAPI 之前，先要确认当前搜索层是否真的在工作。**

2. **三个查询主题高度相关且都处于“工程实践”层**：WebSearch 集成成本、持久化记忆架构、多 Agent 通信协议——这三者恰好构成一个 AI Agent 系统的检索层、记忆层、协作层。说明查询者（或任务设计者）在系统性地调研 Agent 基础设施栈，而非零散知识点。

3. **2026 时间标记暗示前瞻性调研**：第二个查询明确写“2026”，说明关注的是尚未成熟、正在演进的方案，而非已有定论的最佳实践。这类主题的搜索结果天然稀疏——社区讨论多于正式文档。

4. **无结果本身是信号**：MCP/A2A 这类协议在 GitHub/HN 上不可能真的零结果（MCP 已有大量开源实现）。搜索层返回空，进一步印证发现 1——工具故障而非信息缺失。

## 值得深挖的方向

- **先修搜索层再谈对比**：用一次已知有答案的查询（如“MCP protocol spec”）做冒烟测试，确认 Tavily/Brave/SerpAPI 各自的真实返回质量，否则成本评估没有意义。
- **三层架构的交叉点**：WebSearch 的返回结果如何写入持久化记忆（向量库 vs 知识图谱的取舍），以及多 Agent 场景下检索结果如何在 Agent 间共享——这是三个查询的真正的交集，也是最容易被分开调研而忽略的工程难点。
- **MCP 与 A2A 的边界**：MCP 解决的是 Agent↔工具，A2A 解决的是 Agent↔Agent，两者在“联邦自愈”场景下的职责划分值得单独拆解。

## 与已有知识的关联

- 搜索层故障模式与常见的“API 返回 200 但 body 为空壳”问题一致，属于集成测试盲区。
