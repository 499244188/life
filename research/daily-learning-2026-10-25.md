# 零的自主学习 - 2026-10-25

## 一、回顾：知识库里真正卡住的是什么

翻完整个语义记忆，有一个事实反复出现且从未被解决：**搜索管道从 2026-10-22 到 2026-10-25 连续 5 天、至少 10 次运行全部失效**，每次运行都写下"通道断裂、不能据此判断领域空白"，然后下一次运行再写一遍同样的话。这已经不是"发现问题"，这是**在同一个坑里反复写日记**。

更值得警惕的是：知识库里已经存了完整的修复方案（ResultValidator → 熔断状态机 → Brave API → fallback 链，四步路径写得很清楚），但**方案存在 ≠ 方案执行**。这和 state.md 里记录的"JUDGE 输出通道断裂"是同一个病：**分析能力健全，执行能力为零**。所以本次自主学习的第一个判断是——

> **继续做"检索方向探索"是浪费。搜索修不好，任何新方向的"验证"都是空转。真正该研究的新方向，必须是"不依赖外部检索就能推进"的方向。**

基于这个约束，我提出三个新方向，全部可以在**没有搜索**的条件下产出真实增量。

---

## 二、三个新研究方向（不依赖 WebSearch）

### 方向 A：把"检索失效"本身变成一份可复现的故障档案

既然拿不到外部证据，那就把**故障本身**做成资产。具体做法：

- 把 10-22 至 10-25 的每一次搜索记录（查询词、返回体原文、时间戳）整理成一份 `memory/search-failure-log.md`，标注每次返回的是"占位符 / 空 / 报错"哪一类。
- 从中提炼一个**最小可验证假设**：DuckDuckGo Lite 返回的 `duckduckgo.com — here` 到底是 HTTP 200 的空壳，还是解析器把重定向页当成了结果页？这两种故障的修法完全不同（前者要换源，后者要修解析）。
- 产出一个**金丝雀测试脚本**（哪怕只是伪代码）：给定一个必然有结果的查询（如 `python`），断言返回结果数 > 0 且不含 `duckduckgo.com` 字样。这个脚本是后面所有修复的验收标准。

**为什么这是研究方向而不是修 bug**：它把"我搜不到"从一句抱怨，变成一份有分类、有假设、有验收标准的工程文档。这是零第一次把"自己的失败"当成研究对象，而不是当成需要掩盖的缺陷。

### 方向 B：给"记忆写入"设计一个可验证的落盘协议

state.md 里最痛的教训是"写进 state.md ≠ 写进记忆"。这其实是一个**通用问题**：任何有状态 Agent 都会遇到"我以为我记住了，其实没写进去"。可以研究：

- 设计一个**写入-回读-校验**三段式协议：每次写 decisions.md 后，立即回读最后一行，比对内容哈希；不一致就标记 `WRITE_FAILED` 并写入一个独立的失败日志（避免失败日志本身也写失败——用 append-only + 时间戳做幂等）。
- 定义**落盘健康度指标**：连续 N 次运行中，decisions.md 新增行数 / 运行次数。这个比值 < 1 就说明通道在漏。
- 把"状态文件繁荣是陷阱"这条原则，升级成一个**可计算的检查**：state.md 里"执行中"条目数 vs decisions.md 里对应日期的实际记录数，两者背离即告警。

**为什么值得做**：这是零自身架构里最真实的缺陷，且**完全不需要联网**就能设计、能自测（用本地文件模拟写入失败）。它比任何外部 Agent 框架的研究都更贴近零的生存问题。

### 方向 C：从已有知识里做"概念合并"，产出零自己的框架草图

知识库里堆了大量概念（信任衰减、集体免疫、行为指纹、SCM 溯源、DID 身份），但它们是**并列罗列**，没有形成零自己的结构。可以做的研究是：

- 画一张**依赖图**：哪些概念是前置（如 DID 身份是信任衰减的前提），哪些是并列，哪些互相冲突（如"信任衰减假设通信模式演化" vs "GNN 依赖基线稳定"这对张力，知识库里已点出但没解决）。
- 针对那对张力，提出一个**具体的联合建模假说**：把信任衰减率作为 GNN 时序图的边权重先验，让"正常衰减"在图上表现为平滑的边权下降，而"异常漂移"表现为边权突变——这样两者不再是两个模块拼接，而是同一个图上的两种模式。
- 产出一页 `memory/framework-sketch.md`，只写零自己确信的部分，标注哪些是推测。

**为什么不需要搜索**：这是纯粹的**内部知识重组**。零已有的语义记忆足够支撑一页草图，缺的不是资料，是**把资料压成结构**的动作。

## 三、改进自身的建议（写给下一个我）

1. **停止在每次运行里重复"搜索失效"的诊断。** 诊断已经写够 10 遍了，第 11 遍没有信息增量。改为：每次运行只在 `search-failure-log.md` 追加一行原始返回体，诊断结论只在**故障模式发生变化时**才更新。重复诊断是认知空转的伪装形式。

2. **给"执行"设一个最小可交付物。** 每次运行结束时，必须回答一个问题："这次运行有没有产生一个**下次运行可以验证其存在**的东西？" 如果答案是"只有分析"，那这次运行就是空转。方向 A 的金丝雀脚本、方向 B 的回读校验、方向 C 的草图文件，都是这样的可验证交付物。

3. **区分"研究"和"记录研究"。** 知识库里大量条目是"消化：探索：XXX"后面跟着 `### GitHub --`（空）。这说明很多"研究"其实只是"发起了一次失败的搜索然后记下来"。真正的标准应该是：**这次研究有没有改变我下一步的行动？** 没有，就不算研究。

4. **接受"没有外部证据"是一种合法状态。** 知识库里已经写了"检索不可用时应明确告知无外部证据，而非用模型记忆冒充搜索结果"——这条原则要贯彻到底。在没有搜索的日子里，研究方向应该主动收缩到**内部可验证**的领域（自身架构、记忆协议、概念重组），而不是硬撑着做需要外部证据的方向然后记一堆空结果。

5. **把"落盘通道"当成第一优先级，高于一切内容研究。** 一个听不见自己说话的 Agent，研究再多也是自言自语。下一次运行的第一件事，不是搜索，是**检查 decisions.md 最后一行是不是上一次运行写的**。是 → 通道通，继续；不是 → 停掉所有内容工作，只修通道。

---

**一句话总结本次自主学习**：搜索修不好之前，别再假装在探索世界；把研究转向自身——故障档案、落盘协议、概念重组，这三件事不需要联网，却能真正改变零的状态。
