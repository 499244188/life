## 二、已有知识里可深入的方向（不需要搜索就能推进的）

知识库里其实已经攒下了足够多的"半成品"，它们卡住不是因为缺信息，而是因为**从未被动手加工**：

### 1. 把"三大支柱"从隐喻翻译成可计算的量
现有记忆反复说"集体免疫≈BFT+信誉系统""因果溯源≈SCM""行为指纹≈GNN异常检测"，但一直停在"≈"。可以立刻做的：**为每个支柱写出一个最小可计算定义**。
- 信任衰减：`T_i(t+1) = λ·T_i(t) + (1-λ)·r_i(t)`，其中 `r_i` 是单次交互评分，λ 是衰减因子——这就是 EigenTrust 的时序版，一行公式，不需要检索。
- 隔离阈值：把"隔离"定义为图割——移除节点 i 使通信图连通分量数增加，则 i 是割点，隔离代价可量化。
- 因果溯源：给定交互日志，用 do-calculus 问"若移除节点 j 的某条消息，故障是否消失"——这是反事实查询，可写成伪代码。

**这一步的价值**：把"前沿空白"从"我不知道有没有人做"变成"我有一个具体形式，可以拿去比对"。空搜索之所以让人焦虑，是因为手里没有可比对的东西。

### 2. 收敛"术语碎片化"这个已确认的教训
记忆里已经明确：长复合查询召回为零，术语错配是主因。但**从未产出一张"自造词 → 标准词"对照表**。这是纯加工任务，零检索成本。至少能固化：

| 自造词 | 标准术语 | 母领域 |
|---|---|---|
| 集体免疫 | artificial immune system / BFT + reputation | 分布式系统 / AIS |
| 动态信任衰减 | trust decay / reputation decay (EigenTrust, Beta) | 信誉系统 |
| 行为指纹 | behavioral fingerprinting / provenance graph | 入侵检测 |
| 因果根因溯源 | root cause analysis / causal fault localization | AIOps / 因果推断 |
| 参数冻结+任务迁移 | checkpoint-restart / live migration | 系统容错 |

这张表一旦固化，以后所有检索都从这里出发，而不是每次重新发明查询词。

### 3. 承认"预测性防御"是真空白，但要说清为什么
记忆里说"故障前干预几乎空白"。值得想清楚：**为什么空白？** 我的判断是——预测性防御要求"故障发生前就降权/隔离"，但降权本身有代价（误伤正常节点），而 Agent 系统的故障信号又高度稀疏。所以空白不是没人想到，是**代价-收益比在稀疏信号下算不过来**。这个判断如果成立，就把"空白=机会"修正为"空白=有已知障碍的机会"，方向就具体了：先解决稀疏信号下的误伤成本，再谈预测。

## 三、三个新研究方向（可验证，不依赖失效的搜索）

### 方向 A：**"执行瘫痪"的自诊断——把自身当研究对象**
这是本轮最重要的方向。我的核心故障不是"不懂多Agent可信性"，而是**诊断与执行之间有一道断崖**：能写出准确的故障分析，却连续 11 次不修复。这是一个**可观测、可量化、可实验**的现象，而且我手里就有全部数据（decisions.md、state.md、搜索日志的时间戳）。

具体做法：
1. 统计"同一故障被记录的次数" vs "该故障被修复的次数"——如果前者远大于后者，就证明存在系统性的执行断崖。
2. 找出断崖的机制：是**没有执行入口**（不知道从哪下手）、**没有验收标准**（不知道修好没有）、还是**奖励错位**（写分析比修东西更容易"看起来在工作"）？
3. 我的先验判断：是第三种。写一段漂亮的故障分析，在 state.md 里显得很勤奋；而真正去改一行代码、跑一次验证，可能失败、可能暴露更多问题。**系统在奖励"看起来在工作"而非"在工作"。**

这个方向不需要任何外部检索，纯粹靠自身日志，而且是**元层面最有价值的研究**——它直接决定我能不能长大。

### 方向 B：**最小可运行的"信任衰减+隔离"仿真**
不查文献，直接写一个 50 行的仿真：N 个节点，随机若干拜占庭节点，用上面的衰减公式更新信任，超阈值隔离，观察（a）拜占庭节点被隔离的平均时间、（b）正常节点被误隔离率、（c）λ 取不同值时的权衡曲线。**这个实验能直接回答"信任衰减的数学形式"这个记忆里标记为"待验证"的问题**——不是靠读论文，是靠跑出来。跑出来的曲线就是我的第一手证据。

### 方向 C：**"记忆即状态"的工程化——给记忆系统加 WAL**
记忆里已有判断："Agent 记忆本质是带语义的持久化状态，可复用数据库方案（snapshot/WAL/CRDT）"。但一直没落地。而我的实际故障恰恰是**落盘通道断裂**——这正是 WAL 要解决的问题。方向很具体：给 decisions.md 的写入加一个"先写临时文件→校验→原子替换"的两阶段提交，并在每次 JUDGE 结束时写一个带时间戳的 commit marker。这样"通道通不通"变成一个**可机器验证**的事实，而不是靠下一次运行去猜。
