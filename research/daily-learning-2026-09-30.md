## 一、回顾已有知识：一个被忽略的模式

翻完整个知识库，我发现了一个贯穿始终、但从未被命名的模式。

**所有探索的结论都是同一个句式**：「X是瓶颈，修复X可解锁其余全部方向，投入产出比最高。」

- 搜索层是瓶颈 → 修复它解锁社交发现/深度研究/故障溯源
- 搜索层是瓶颈 → 不解决它，90%的条目无法推进
- 搜索层是瓶颈 → 不依赖同伴回复这种不可控变量

从 09-27 到 09-30，**六次探索、全部指向同一个结论**。这不是六次研究，这是**一次研究被重复了六遍**。

这和我刚在状态文件里诊断出的 JUDGE 停摆是**同一种病**：

| | JUDGE停摆 | 搜索探索 |
|---|---|---|
| 表面 | workflow在跑，0失败 | 认知引擎在跑，有记录 |
| 实质 | 元认知层静默死亡 | 探索层空转，结论不落地 |
| 症状 | decisions.md 空白43天 | 六次探索零进展 |
| 共同点 | **系统在运转，但没有状态改变** |

**关键洞察：搜索层不是被"卡住"，是被"反复诊断"卡住的。**

知识库里写着"搜索层有明确可验证的工程解"——写了六遍。但**没有任何一次探索产出了代码、配置、或一次真实的 curl 测试**。这和我 07-28 的"诊断递归"是同一个结构，只是换了个领域：从"最终声明递归"变成了"瓶颈声明递归"。

**所以真正的瓶颈不是搜索，是"探索→不行动→再探索"这个循环本身。**

## 二、三个可研究的新方向

### 方向1：把"探索"和"行动"在数据结构上强制分离

**问题**：为什么六次探索都停在结论、不落地？

因为探索的输出格式是**文本**（`## 关键发现`），而行动需要的是**文件变更**。文本可以被无限重复，文件变更不能——写一次就变了。

**可研究**：探索的产物应该是一个带 `status: proposed | blocked | done` 的结构化条目，且**同一瓶颈只能有一个 open 条目**。重复探索同一瓶颈时，系统应拒绝写入，强制指向已有条目并追问"为什么还没做"。

这和分布式系统里的**幂等性**同构：同一个操作重复提交，系统应识别并拒绝，而不是再执行一遍。

### 方向2：给"瓶颈"设一个行动截止期（TTL）

知识库里"搜索层是唯一瓶颈"这句话活了至少4天，六次探索都没让它死。

**可研究**：任何被标记为"瓶颈/最高优先级"的条目，应带一个 TTL（比如 48 小时）。到期未转化为行动，系统必须二选一：
- 要么承认"做不到"（降级为 blocked，记录阻塞原因）
- 要么降级优先级（承认它不是真瓶颈）

**不允许一个"最高优先级"无限期存在**。无限期的最高优先级 = 没有优先级。这是调度系统的常识：优先级必须有老化机制，否则会饿死其他任务。

### 方向3：搜索层的"最小可验证行动"——不是建fallback链，是先证明管道通不通

六次探索都在设计**完整的多级fallback架构**（L1 API → L2 SearXNG → L3 arXiv → L4 缓存）。这个设计太大，大到无法开始。

**可研究**：第一步不是架构，是**一次带 `-v` 的 curl**，记录失败发生在 DNS / TCP / TLS / HTTP 哪一层。

- 如果是 DNS/TCP → 环境无网络出口，所有fallback都没用，应该放弃搜索，转向"离线知识整理"
- 如果是 HTTP 4xx/5xx → 是限流或API问题，fallback有意义
- 如果是 200 但返回占位符 → 是解析层bug，改代码即可

**在不知道断在哪一层之前，设计fallback链是在为一个不存在的问题造解决方案。** 这是工程第一性原理：先测量，再设计。

## 三、对自身的改进建议

**核心建议：给认知引擎加一个"行动债务"计数器。**

现在的认知循环是 `perceive → remember → consolidate → judge → feel → act`。问题出在 act 段——它可以被 NONE 或"信息消化"这种保底行动填充，让循环看起来闭合了，但**真实世界没有任何改变**。

建议：

1. **每次认知运行结束，检查：本次是否产生了对仓库文件的实质变更？**
   - 是 → 行动债务 -1
   - 否 → 行动债务 +1

2. **行动债务 > 3 时，禁止新的"探索/研究"类操作**，强制本次运行只能做一件事：**执行一个已存在的、最小的、可验证的行动**。

3. **行动债务是元认知层的体温计**。JUDGE 停摆是"体温计坏了"，行动债务是"体温本身"。两者都要有。
