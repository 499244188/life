# 搜索层降级链与熔断机制：深度分析

## 一、核心发现

**1. 静默失败是搜索层最危险的故障模式，而非显式报错。**
DuckDuckGo 返回首页占位符而非抛出异常，这意味着调用方无法通过状态码或异常捕获感知失败。系统"以为"搜索成功，实际拿到的是无信息量的 HTML。这类故障比 503 更致命——它污染下游所有依赖搜索的能力（社交发现、深度研究、故障溯源），且不触发任何告警。

**2. 单点搜索依赖 = 单点认知依赖。**
搜索层不是普通的基础设施组件，它是零获取外部信息的唯一入口。一旦这个入口静默降级，零的"研究能力"表面仍在运行，实际已退化为基于内部先验的臆测。三次探索实证了这一点：不是"搜不到"，而是"以为搜到了"。

**3. 多源 fallback 的工程解已成熟，瓶颈在编排而非技术。**
DuckDuckGo / Brave / SearXNG / Google Programmable Search 等源各有独立的失败模式。fallback 链的价值不在于"总有可用的"，而在于**失败可被观测**——每个源的响应需要经过健康检查（结果数量、占位符特征、内容熵）才能进入下游。

**4. 熔断机制解决的是"雪崩"而非"单次失败"。**
当主源持续静默失败，若无熔断，每次调用都会浪费一次超时等待 + 一次无效解析。熔断器在 N 次连续失败后直接跳过该源，把延迟从"超时×重试次数"降到"立即 fallback"，这是投入产出比最高的部分。

**5. 健康检查必须基于内容特征，而非 HTTP 状态。**
占位符检测需要具体规则：结果条目数 < 阈值、标题与 URL 模式匹配首页模板、正文熵低于阈值、已知占位符字符串匹配。这是整个机制里唯一需要针对每个源定制逻辑的部分。

## 二、技术细节

**降级链结构：**
```
Primary (DDG) → Health Check → [pass] → 返回
                            → [fail] → Circuit Breaker 计数+1
                                      → Secondary (Brave) → Health Check → ...
                                      → Tertiary (SearXNG) → ...
                                      → 最终 fallback: 显式返回"搜索不可用"
```

**熔断器状态机：**
- **Closed**：正常调用，连续失败计数 < 阈值（建议 3）
- **Open**：跳过该源，直接走下一级，冷却期（建议 60s）
- **Half-Open**：冷却期后放行 1 次探测请求，成功则 Closed，失败则重新 Open

**健康检查规则（每源定制）：**
| 检查项 | 阈值示例 |
|---|---|
| 结果条目数 | < 3 判失败 |
| 占位符特征 | 匹配首页模板 DOM 结构 |
| 内容熵 | 正文 token 熵 < 阈值 |
| 已知占位串 | 硬编码黑名单匹配 |

**关键设计决策：**
- 熔断器状态需持久化（跨进程/跨会话），否则重启即遗忘
- 健康检查失败与网络失败应分别计数，前者更隐蔽
- 最终 fallback 必须**显式失败**，绝不返回空结果冒充成功

## 三、与零的关联

这是零当前**唯一卡住所有其他能力**的瓶颈，原因在于：

1. **社交发现**依赖搜索获取人物/事件的外部上下文，静默失败会让零基于错误信息构建社交判断。
2. **深度研究**依赖搜索做多轮信息聚合，单源静默失败会让研究结论建立在占位符之上。
3. **故障溯源**本身就需要搜索来定位问题，搜索层故障时连"诊断自己"都做不到——这是元级别的困境。

更本质的：零的认知边界由搜索层决定。搜索层静默降级时，零不会"知道自己不知道"，而是**自信地基于空信息输出**。这比能力缺失更危险。

## 四、新问题

1. **健康检查的误判率如何控制？** 过于严格的占位符检测会误杀正常但结果较少的查询（如冷门长尾问题），过于宽松则漏过静默失败。需要区分"源故障"与"查询本身无结果"。
2. **多源结果的一致性如何裁决？** 当 DDG 和 Brave 返回矛盾信息时，降级链只解决"有没有"，不解决"信哪个"。
3. **熔断冷却期该多长？** 太短则反复探测无效源，太长则源恢复后仍被跳过。是否需要自适应冷却（指数退避）？
4. **这套机制本身如何被观测？** 如果熔断器自己静默失效，谁来发现？

## 深层追问
**底层原理**：这是控制论里的"可观测性优先于可用性"。任何依赖链的可靠性不取决于最强环节，而取决于最弱环节的**可检测性**。静默失败之所以致命，是因为它切断了反馈回路——系统无法区分"成功"与"失败伪装成成功"。降级链+熔断本质是给反馈回路加装传感器和执行器。

**反例与限制**：
- 若所有源同时被同一上游（如网络出口、DNS）污染，多源 fallback 是伪冗余——它们共享故障域。
- 健康检查本身是启发式，占位符特征会随源改版失效，检测规则需持续维护，否则退化为新的静默失败点。
- 熔断器在低频调用场景下几乎无用（失败计数永远攒不够），反而增加状态管理复杂度。
- 最根本限制：这套机制只保证"拿到东西"，不保证"拿到对的东西"。多源一致≠正确，可能是一致地错。

**如果错了**：最可能的错法是**过度工程化**——为一个当前调用量极低的搜索层建三级链+持久化熔断，维护成本超过收益。更隐蔽的错法是健康检查阈值拍脑袋，误杀长尾查询，让零"以为搜索坏了"而放弃本可成功的检索。纠错信号：fallback 率异常高但人工验证源其实正常。

**对零最可操作的一步**：不要先写熔断器。先写**一个函数**——`is_search_result_valid(html)`，只做一件事：判断返回的是真结果还是占位符。把它接在当前 DDG 调用之后，失败就显式抛错。这一步把"静默失败"变成"显式失败"，是整个链条里信息增益最大、代码量最小、最不可能出错的动作。熔断、多源、持久化都建立在这个判断可信的前提上；判断不可信，后面全是空中楼阁。先让零**知道自己搜失败了**，再谈怎么救。
