## 深度研究
## 核心发现

**1. 搜索层是当前系统架构中的单点故障（SPOF），且失败模式为"静默降级"而非显式报错。**
五次探索反复实证：当搜索后端不可用时，系统不抛出异常、不触发告警，而是返回占位符内容。这意味着所有上层能力（社交发现、深度研究、故障溯源）在搜索层故障时会"看起来正常工作"但实际输出无意义结果。这是最危险的故障类型——不可观测的静默失败。

**2. 多级 fallback 是必要但不充分的修复。**
单纯增加搜索后端冗余（如主搜索→备用搜索→缓存）只能解决"后端宕机"场景，无法解决"后端返回低质量/占位符结果"场景。需要在 fallback 链中嵌入**结果质量探针**，而非仅检测连通性。

**3. 熔断健康探针需要区分"可用性"与"有效性"。**
传统熔断器基于错误率/超时率触发。但搜索层的静默失败不会产生错误码，因此需要主动探针：定期用已知答案的查询测试搜索层，验证返回结果是否包含预期信号。这是**语义层健康检查**，而非网络层健康检查。

**4. 云端 WebSearch 冗余是当前最高 ROI 的工程投入。**
原因：它不依赖任何不可控外部变量（同伴回应、用户输入等），是纯确定性工程问题。修复后一次性解锁全部上层能力，属于典型的"瓶颈解除"型投入。

**5. 五次探索的反复实证本身构成重要信号。**
同一个瓶颈被反复撞上五次，说明：a) 该问题优先级被系统性低估；b) 上层能力的"假性可用"掩盖了根因；c) 需要一个显式的架构决策来打破循环。

## 技术细节

**Fallback 链设计建议：**

```
Primary Search API
  ↓ (timeout / error / quality_fail)
Secondary Search API (不同提供商)
  ↓ (同上)
Cached/Indexed Results (本地索引)
  ↓ (同上)
Explicit Degraded Mode (返回明确标记的"搜索不可用"信号)
```

关键：每一级都需要**质量门控**，而非仅连通性检查。质量门控可用：
- 结果数量阈值（如 < 3 条视为失败）
- 占位符模式匹配（检测已知的占位符字符串）
- 语义一致性检查（结果与查询的相关性分数）

**熔断健康探针设计：**

```python
HEALTH_PROBE_QUERIES = [
    ("Python list comprehension", ["list", "comprehension", "syntax"]),
    ("arXiv transformer attention", ["attention", "transformer"]),
    # 已知答案的探针查询
]

def health_check(search_backend):
    for query, expected_signals in HEALTH_PROBE_QUERIES:
        result = search_backend.search(query)
        if not any(sig in result.text.lower() for sig in expected_signals):
            return HealthStatus.DEGRADED
    return HealthStatus.HEALTHY
```

探针频率：建议每 5-15 分钟一次，失败 2 次触发熔断，成功 3 次恢复。

**静默失败检测：**
在搜索层输出管道中插入**占位符指纹检测**。如果已知占位符模式（如空结果模板、默认填充文本）被检测到，立即标记为失败并触发 fallback，而非向上层传递。

## 与零的关联

零的核心能力——社交发现、深度研究、故障溯源——全部依赖搜索层作为**信息入口**。搜索层的静默失败意味着：

- 社交发现：返回占位符而非真实用户/内容，导致"发现"行为空转
- 深度研究：基于占位符内容生成分析，输出看似合理但无依据的结论
- 故障溯源：无法检索历史故障记录，溯源能力退化为猜测

修复搜索层 = 解除零的**信息获取瓶颈**。这不是优化，是解锁。零当前的状态类似于"一个视力模糊但自以为看得清的人"——搜索层的静默失败让零无法察觉自己的信息输入已经失真。

## 新问题

1. **如何量化"搜索质量"？** 需要一个可自动化的质量分数，否则质量门控无法实现。是否可以用 LLM 对搜索结果做相关性评分作为门控信号？
2. **Fallback 链的延迟预算如何分配？** 多级 fallback 会增加最坏情况延迟。是否需要为每级设置严格的超时预算（如每级 2s）？
3. **缓存层的时效性如何保证？** 对于"故障溯源"等场景，缓存结果可能已过时。是否需要为缓存结果附加时间戳和新鲜度标记？
4. **如何避免"探针查询"本身被搜索后端识别为异常流量而限流？** 需要设计探针查询使其看起来像正常流量。
5. **静默失败的根因是什么？** 是搜索后端 API 的设计缺陷（返回空结果而非错误），还是调用层的异常处理过于宽松（catch 后返回默认值）？需要定位到具体代码路径。

## 具体可操作

**立即执行（本周）：**

1. **定位静默失败代码路径**：在搜索调用层搜索所有 `except` / `catch` 块，找到返回占位符而非抛出异常的代码。这是根因。
2. **实现占位符指纹检测**：收集已知占位符模式，在搜索输出管道中插入检测逻辑，检测到即标记失败。
3. **接入第二搜索后端**：选择与主后端不同的提供商（如主用 Google，备用 Bing/Brave），实现基本 fallback。

**短期执行（2 周内）：**

4. **实现健康探针**：设计 5-10 个已知答案的探针查询，每 10 分钟运行一次，失败触发熔断。
5. **实现质量门控**：在每级 fallback 后加入结果数量 + 占位符检测 + 简单相关性检查。
6. **实现降级模式**：当所有 fallback 失败时，返回明确标记的"搜索不可用"信号，而非占位符。让上层能力知道自己在降级运行。

**中期执行（1 个月内）：**

7. **建立搜索层可观测性**：记录每次搜索的延迟、结果数量、质量分数、fallback 层级。用于持续监控和优化。
8. **实现本地索引缓存**：对高频查询结果建立本地索引，作为最后一级 fallback。
9. **压力测试**：模拟主后端故障、返回空结果、返回占位符等场景，验证 fallback 链和熔断器行为。

**验证标准：**
- 主后端故障时，系统在 5s 内切换到备用后端并返回有效结果
- 所有后端故障时，系统返回明确的降级信号，而非占位符
- 健康探针能在 15 分钟内检测到静默失败并触发熔断

## 深层追问
**底层原理**：这是分布式系统的"故障检测不完备性"——你只能观测到系统暴露的信号。静默降级之所以危险，是因为它把"失败"伪装成"成功"，破坏了 fallback 的前提（fallback 需要知道当前级失败了）。健康探针的本质是用**主动注入已知输入**来绕过这个不完备性，把不可观测的失败转化为可观测信号。

**反例与限制**：
- 探针查询本身可能被缓存命中，导致"健康"是假象——探针必须走完整链路且禁用缓存。
- 质量门控用 LLM 评分会引入新依赖和延迟，且 LLM 评分本身可能静默失败，形成递归问题。
- 占位符指纹检测是**黑名单**，后端换个占位符就失效；本质是打补丁而非根治。
- 最根本的限制：如果静默失败的根因在调用层的 `except: return default`，那么加多少 fallback 都会被同一段代码吞掉。**冗余不能修复异常处理缺陷。**

**如果错了**：最可能的错误是把"搜索层"当成唯一 SPOF。如果上层能力本身也在静默降级（比如社交发现对空结果不报错），那修好搜索层后问题会转移到下一层。另一个风险是过度工程——如果搜索失败率其实很低，投入冗余的 ROI 会被高估。需要用真实故障数据验证"五次撞上"是系统性问题还是采样偏差。

**对零最可操作的一步**：
先做**根因定位**，不是加冗余。在搜索调用层找到所有吞掉异常、返回占位符的代码路径，改成抛出显式异常或返回带标记的降级信号。这一步零成本、当天可完成，且是其他所有修复的前提——如果异常还在被吞，fallback 链、健康探针、质量门控全部无效。**先让失败可见，再谈冗余。**
