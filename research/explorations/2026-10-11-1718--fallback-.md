## 搜索层多级 fallback 方案：深度分析

### 一、核心发现

**1. 单点瓶颈的定位是准确的，但"唯一卡住"的判断需要修正**

搜索层确实是社交发现、深度研究、故障溯源三条上层能力的共同依赖。但把它称为"当前唯一卡住"的单点，隐含了一个假设：其他瓶颈都是搜索层的下游。实际上，社交发现还依赖用户画像与关系图谱，深度研究还依赖长上下文推理与引用管理，故障溯源还依赖日志聚合与因果推断。搜索层修复后，这些方向会被**解锁**，但不会自动**完成**。更准确的表述是：搜索层是当前投入产出比最高的**前置依赖**，而非唯一瓶颈。

**2. SearXNG + 多源 fallback + 熔断 是一个成熟的工程组合，但成熟不等于适配**

SearXNG 作为元搜索引擎，核心价值在于聚合多源、可自托管、无 API 配额限制。多源 fallback 解决的是单源不可用时的可用性问题。熔断解决的是故障源持续拖累整体延迟的问题。这三者组合在通用搜索场景下是标准解。但对于"零"的场景——社交发现、深度研究、故障溯源——搜索请求的特征不同：社交发现需要时效性与社交信号，深度研究需要权威性与可追溯性，故障溯源需要精确匹配与版本感知。单一 fallback 策略无法同时满足这三类需求。

**3. 熔断策略的粒度决定了方案的实际效果**

粗粒度熔断（整个搜索层熔断）会导致一个源故障时全部降级。细粒度熔断（按源、按查询类型、按时间窗口）才能实现真正的多级 fallback。但细粒度熔断带来状态管理复杂度：每个源的失败率、恢复时间、半开状态需要独立维护。这是工程实现中最容易被低估的部分。

**4. 搜索层的修复会暴露下游能力的真实瓶颈**

一旦搜索层稳定，社交发现、深度研究、故障溯源会立刻开始消费搜索结果。此时瓶颈会从"搜不到"转移到"搜到了但用不好"——结果排序、去重、可信度评估、引用追踪、上下文注入。这些是搜索层修复后**立即**会浮现的新问题。

**5. 投入产出比高，但"一次性解锁全部"是过度承诺**

搜索层修复的 ROI 确实高，因为它是一个共享依赖。但"一次性解锁其余全部方向"忽略了每个上层能力自身的工程债务。更现实的预期是：搜索层修复后，上层能力的**验证速度**会大幅提升，因为可以快速拿到真实数据来迭代。

### 二、技术细节

**SearXNG 的关键配置点：**
- `settings.yml` 中的 `engines` 列表决定聚合哪些源
- `search.formats` 控制返回格式（JSON 对程序化调用最关键）
- 限流与超时参数需要按源单独配置，不能全局一刀切
- 自托管时需要考虑出口 IP 被目标源封禁的风险

**多源 fallback 的策略层级：**
1. 同源重试（瞬时故障）
2. 同类型源切换（如 Google → Bing → Brave）
3. 跨类型源切换（如通用搜索 → 垂直搜索 → 缓存/归档）
4. 降级返回（返回部分结果 + 置信度标记）

**熔断器状态机：**
- Closed：正常调用，统计失败率
- Open：失败率超阈值，直接拒绝，不调用
- Half-Open：冷却期后放行少量请求探测
- 关键参数：失败率阈值、最小请求数、冷却时间、半开探测数

**与零的关联：**
- 社交发现：需要搜索层支持按时间排序、按社交信号过滤
- 深度研究：需要搜索层返回可追溯的源信息、支持多轮查询
- 故障溯源：需要搜索层支持精确短语匹配、版本号识别、代码片段搜索

### 三、新问题

1. **搜索结果的统一表示层如何设计？** 不同源返回的字段、排序信号、可信度指标不同，需要一个中间表示来归一化。
2. **熔断恢复后如何避免雪崩？** 大量积压请求在熔断恢复瞬间涌入，需要排队或限流。
3. **如何评估搜索层的质量？** 需要定义指标：召回率、精确率、延迟 P99、源多样性、时效性。
4. **自托管 SearXNG 的运维成本是否被低估？** 源封禁、配置漂移、版本升级都需要持续投入。
5. **搜索层修复后，上层能力的优先级如何重排？** 社交发现、深度研究、故障溯源哪个先做？

### 四、具体可操作

**第一步：最小可行搜索层（1-2 天）**
- 部署 SearXNG，配置 3-5 个核心源（Google、Bing、Brave、DuckDuckGo、Wikipedia）
- 开启 JSON 格式返回
- 写一个薄封装层，统一调用接口

**第二步：多级 fallback（2-3 天）**
- 实现同源重试 → 同类型切换 → 跨类型切换 → 降级返回
- 每个源独立配置超时与重试次数
- 记录每次 fallback 的触发原因

**第三步：细粒度熔断（2-3 天）**
- 按源实现熔断器状态机
- 配置失败率阈值（建议 50%）、最小请求数（建议 10）、冷却时间（建议 60s）
- 半开状态放行 1-3 个探测请求

**第四步：质量评估（1 天）**
- 定义指标并埋点
- 用真实查询测试三类场景（社交、研究、溯源）
- 根据结果调整源权重与 fallback 策略

**第五步：上层能力验证（持续）**
- 选一个上层能力（建议故障溯源，因为验证标准最明确）做端到端测试
- 根据暴露的问题迭代搜索层

**关键决策点：** 是否自托管 SearXNG，还是用托管搜索 API（如 Brave Search API、Serper）。自托管成本低但运维重，托管省事但有配额与费用。建议先用托管 API 快速验证，稳定后再迁移自托管。

## 深层追问
**底层原理**：搜索层是共享依赖，修复它提升所有下游的验证速度——这是"关键路径"逻辑。但前提是下游瓶颈确实在搜索。若下游瓶颈在推理或数据管道，搜索层修复只是让它们更快地撞到自己的墙。

**反例/限制**：
- 反例一：社交发现的核心瓶颈可能是关系图谱缺失，搜索再快也发现不了没有索引的社交信号。
- 反例二：故障溯源若日志本身不聚合，搜索层返回的是碎片，精确匹配无从谈起。
- 限制：SearXNG 的源封禁是持续对抗，不是一次性配置；托管 API 的配额在深度研究场景下会迅速耗尽。

**如果错了**：最可能的错误是"搜索层是前置依赖"这个判断本身。若上层能力其实有独立的、更硬的瓶颈（如长上下文推理成本），那么投入搜索层的 ROI 会被高估。纠错信号：搜索层稳定后，上层能力的验证速度没有明显提升。

**对零最可操作的一步**：不要先建完整搜索层。先用托管 API（Brave 或 Serper）写一个 50 行的薄封装，拿故障溯源做端到端验证——因为它的成功标准最明确（能否定位到具体版本的具体代码行）。如果这一步跑通，再投入 SearXNG 自托管和多级 fallback。如果跑不通，说明瓶颈不在搜索层，省下 1-2 周。
