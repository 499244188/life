## 核心发现

**1. 搜索管道确实在工作，但存在"查询-结果"语义漂移**

本次搜索返回了高质量的 GitHub 仓库结果（Pimzino/spec-workflow-mcp ★4306、modelcontextprotocol/ext-apps ★3113 等），并成功抓取了两个 README 全文。这说明搜索层本身不是完全失效——问题在于**查询构造**：之前三次搜索可能用了过于宽泛或格式不匹配的查询词，导致引擎回退到 DuckDuckGo 首页。本次查询显然命中了 GitHub 索引，返回了结构化、可抓取的内容。结论：**先修复查询构造逻辑，再评估 Tavily/Brave/SerpAPI**——当前管道在正确查询下能产出可用结果，成本对比的前提条件已部分满足，但需要先做一次受控的 A/B 查询测试来量化"查询质量"对结果的影响。

**2. MCP 生态正在从"工具协议"向"UI 协议"扩展，ext-apps 是信号**

modelcontextprotocol/ext-apps（★3113）的 README 明确了一个趋势：MCP 不再只是"LLM 调用工具返回文本"，而是通过 `ui://` 资源让工具声明交互式 HTML 界面，在宿主（Claude、ChatGPT、VS Code、Goose、Postman）中以沙箱 iframe 内联渲染。技术细节：工具定义声明 `ui://` 资源 → LLM 调用工具 → 宿主抓取资源并渲染 → 双向通信（宿主通过 notifications 传数据给 UI，UI 可通过宿主调用其他工具）。这意味着**MCP 服务器的评估维度需要增加"是否支持 UI 资源"这一项**，而不仅是工具数量和 schema 质量。

**3. spec-workflow-mcp 展示了"结构化工作流"作为 MCP 服务器的成熟范式**

Pimzino/spec-workflow-mcp（★4306，本次最高星）的核心设计：顺序化 spec 创建（Requirements → Design → Tasks）+ 实时 Web Dashboard（端口 5000）+ VSCode 扩展 + 审批工作流 + 任务进度追踪 + 实现日志。技术细节：通过 `npx -y @pimzino/spec-workflow-mcp@latest /path/to/project` 注入，Dashboard 单实例多项目共享。值得注意的是 README 顶部声明作者"因个人原因暂时离开，未来会回来更新"——**这是一个维护风险信号**，在方案对比中应标注"活跃度待观察"。

**4. 认证与合规层正在成为 MCP 服务器的独立赛道**

Azure-Samples/mcp-auth-servers（★50）演示当前 MCP spec 下的认证参考实现；olaservo/mcp-advisor（★26）专门辅助 LLM 和人类理解 MCP spec 合规性；agent-receipts/obsigna（★22）提供密码学签名的 AI agent 操作审计轨迹（Go/TypeScript/Python SDK + MCP proxy）。这说明 MCP 生态的分层正在细化：**协议层 → 认证层 → 审计层 → 应用层**。在评估搜索方案时，如果目标知识库涉及 MCP 相关查询，应优先索引这些"基础设施型"仓库，而非仅看星数。

**5. 搜索结果的"已验证状态"污染问题需要机制化解决**

本次结果中，arXiv 和 HN 两个来源为空——这本身是一个数据点：当前搜索管道对学术和社区讨论的覆盖不足，只命中了 GitHub。如果知识库的"已验证"标记依赖搜索返回，那么**空来源应被标记为"未验证"而非"已验证无结果"**。建议在搜索层加入来源覆盖率检查：每次搜索后统计 GitHub/arXiv/HN/Web 各来源的返回数量，低于阈值的来源标记为"覆盖缺口"，不写入已验证状态。

## 深层追问
**底层原理**：搜索质量 = 查询构造 × 索引覆盖 × 结果解析，三者是乘法关系。本次证明解析层和部分索引可用，失败点在查询构造——宽泛查询触发引擎回退到首页，说明管道缺少"查询-结果"一致性校验。本质是**没有闭环验证**：搜完不检查返回是否语义相关，直接把空结果当"无答案"。

**反例/限制**：① 单次成功不能证明管道稳定，可能是 GitHub 索引恰好命中，换查询域（如学术）仍可能全空；② "来源覆盖缺口"标记会引入新噪声——arXiv 本来就不该响应所有查询，机械阈值会误报；③ 修查询逻辑可能只是把偏差从"宽泛"移到"过拟合"，A/B 测试若样本小，20%/50% 阈值本身不可信；④ ext-apps 的 UI 趋势可能被高估——星数 3113 不等于采用率，多数宿主未必支持 `ui://`。

**如果错了**：最可能的错法是"管道能工作"这个结论本身是幸存者偏差——你只看到了成功那次。若复现失败查询发现它们其实也返回了结果、只是解析层丢弃了，那修复方向应从查询构造转向解析层，整个优先级排序要重写。另一个风险：把"零"重新定义为"查询偏差"后，可能掩盖真正的供应商能力差距。

**对零最可操作的一步**：不要先建覆盖率检查，先做**失败查询复现**——把之前三次失败查询原样重跑，记录原始 HTTP 响应和解析后结果。这一步成本最低、信息量最大：能直接区分"引擎没返回"vs"返回了但被丢弃"，决定后续修查询还是修解析。在拿到这个数据前，任何方案对比都是空中楼阁。
