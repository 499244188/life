## 深度研究
## 核心发现

**1. DuckDuckGo Lite 失效不是孤立事件，而是免费搜索API系统性收紧的一部分**

DDG Lite 的 HTML 端点长期被当作免费搜索 API 使用，但 DDG 近年持续加严反爬（速率限制、UA 指纹、IP 信誉评分）。Lite 版本尤其脆弱——它没有 JS 挑战层，反而更容易被直接封禁。这意味着任何依赖单一免费端点的方案本质上都是不可靠的，fallback 不是优化项而是生存项。

**2. 多级 fallback 的正确架构是"按成本递增、按可靠性递减"排序，而非简单堆叠**

有效的 fallback 链应该按以下维度排序：
- **延迟**（本地缓存 < API < 爬取）
- **成本**（免费 < 付费）
- **可靠性**（官方 API > 第三方镜像 > HTML 爬取）

典型分层：
- L0: 本地缓存/会话记忆（0ms，命中即返回）
- L1: 结构化搜索 API（Brave Search API、SearXNG 自建实例）
- L2: 第三方搜索聚合（Serper、Tavily、Exa）
- L3: 直接爬取搜索引擎 HTML（Bing、DDG html 端点）
- L4: 降级到"无搜索"模式，用模型内部知识 + 明确标注不确定性

**3. SearXNG 自建实例是当前性价比最高的 L1 方案**

SearXNG 聚合多个上游引擎（Google、Bing、DDG、Brave 等），单点故障不会导致整体瘫痪。自建实例可以控制速率、避免 IP 被封，且返回结构化 JSON。代价是需要一台常驻服务器和一定的维护成本。对于"搜索层是所有能力前提"这个定位，这个投入是合理的。

**4. 关键工程细节：健康检查 + 熔断 + 结果质量验证**

单纯 try-catch 不够。需要：
- **主动健康检查**：定期对每个层级发探测请求，维护可用性状态
- **熔断器**：某层连续失败 N 次后暂时跳过，避免每次请求都等超时
- **结果质量验证**：返回空结果、返回验证码页面、返回结果数量异常少——这些都应触发降级，而非当作成功
- **超时预算**：整个 fallback 链的总超时要有上限（如 8s），否则用户等待体验崩溃

**5. 搜索层瘫痪的根因往往不是"没有备用源"，而是"没有统一的搜索抽象接口"**

如果每个调用点直接调 DDG Lite，那么换源需要改所有调用点。正确做法是定义统一的 `search(query, opts) -> results` 接口，fallback 逻辑封装在实现内部。这样上层（社交发现、深度研究、故障溯源）完全不感知底层换源。

---

## 与零的关联

零的定位是"所有其他能力的前提"——搜索层是零的感知层。感知层瘫痪意味着：
- 社交发现无法获取实时信息
- 深度研究无法验证事实
- 故障溯源无法查找已知问题

因此搜索 fallback 不是零的一个功能模块，而是零的**基础设施**。它的可靠性等级应该等同于"零能否存活"。

## 新问题

1. **SearXNG 自建 vs 付费 API（Brave/Tavily）的取舍**：自建省成本但需维护，付费 API 省心但有配额和费用。零的运行环境是否支持常驻服务？
2. **搜索结果的一致性**：不同上游引擎返回的结果格式、排序、字段不同，如何归一化？
3. **缓存策略**：哪些查询值得缓存？缓存多久？如何避免缓存导致的信息过期？
4. **降级到 L4（无搜索）时，如何向用户透明标注**？不能让用户以为结果是实时的。

## 具体可操作

1. **立即**：定义统一搜索接口 `search(query, opts)`，把所有直接调用 DDG Lite 的地方改为调用该接口
2. **本周**：部署 SearXNG 实例（Docker 一键部署），配置为 L1
3. **本周**：实现熔断器 + 健康检查 + 超时预算（总超时 8s）
4. **下周**：接入一个付费 API 作为 L2 备份（Brave Search API 有免费额度）
5. **持续**：实现结果质量验证（空结果/验证码/异常少结果 → 触发降级）
6. **持续**：实现 L4 降级模式，明确标注"当前无实时搜索，以下基于模型内部知识"

## 深层追问
**底层原理**：搜索 fallback 本质是分布式系统的降级模式——用冗余换可用性，代价是一致性和复杂度。核心假设是"各层失败独立"，但现实中免费源常被同一波反爬策略同时打击（DDG/Bing/Google 共享 IP 信誉体系），相关性失败会让多级 fallback 同时崩塌。

**反例与限制**：
- **SearXNG 不是银弹**：它只是聚合器，上游全挂它也挂；自建实例若 IP 被 Google 标记，聚合质量骤降。且它返回的是"引擎当时给的"，无 SLA。
- **熔断器悖论**：某层被熔断后，恢复探测本身可能触发反爬，形成"探测即封"。
- **L4 降级最危险**：模型内部知识有时效性，用户看到流畅回答会默认实时，标注常被忽略——这是**信任污染**，比直接报错更糟。
- **成本排序假设可能错**：付费 API 延迟未必低于自建 SearXNG，若 L1 慢于 L2，"按成本递增"排序反而拖慢整体。

**如果错了**：最可能的错是**高估了 fallback 的收益**。若搜索层调用频率低，维护 SearXNG + 熔断 + 质量验证的工程成本可能超过直接买付费 API。另一个错是**把可靠性问题当成架构问题**——有时根因是查询构造太差（触发反爬），而非源不够多。

**对零最可操作的一步**：**先量化，再架构**。在改任何代码前，埋点统计：搜索调用频率、各源失败率、失败类型（超时/封禁/空结果）、用户对无搜索结果的实际反应。如果数据显示 DDG Lite 失败率 <5% 且调用稀疏，那"生存项"判断就是过度反应；如果失败率 >30%，再按 L0→L4 落地。**没有数据的 fallback 设计是猜谜**。
