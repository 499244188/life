## 深度研究
## 核心发现

**1. 单点故障的根因不是"后端挂了"，而是"搜索能力被硬编码进主流程"**

DuckDuckGo Lite 的问题清单（无 API、易反爬、无结构化返回）本质上是**接口契约缺失**：它不是一个"可替换的后端"，而是一段"必须成功的副作用"。当主流程直接依赖 `ddg_lite(query) -> html` 时，任何一次反爬拦截都会把整个推理链打断。SearXNG/Brave/Tavily/Exa 的价值不在于"更多选择"，而在于它们都提供**结构化返回 + 可探测的健康信号**，这才使"抽象为可插拔能力"在工程上成立。换句话说：可插拔的前提是每个后端都能被统一契约描述，而 DDG Lite 恰恰无法被描述。

**2. 多后端加权投票与自动降级是两套机制，不能混为一谈**

- **加权投票**解决的是"结果质量"：多个后端对同一 query 返回结果，按后端历史准确率/延迟/覆盖率加权融合，降低单一后端的偏差与幻觉。
- **自动降级**解决的是"可用性"：健康探测发现某后端连续失败 → 熔断 → 流量切到备用后端 → 半开探测恢复。

两者共享同一套健康状态机，但触发条件不同：投票是**常态**（每次搜索都做），降级是**异常态**（探测失败才做）。把两者塞进一个"搜索路由器"里会导致常态路径被异常逻辑污染——正确做法是**投票层在上、降级层在下**，降级层对投票层透明。

**3. Circuit Breaker / Bulkhead 可直接迁移，但搜索场景需要"按后端 + 按 query 类型"双维度隔离**

传统 Circuit Breaker 按"下游服务"隔离。搜索场景的特殊性在于：**同一后端对不同 query 类型的失败率差异极大**（DDG Lite 对长 query 反爬率远高于短 query）。因此 Bulkhead 应按 `(backend, query_class)` 二维分桶，否则一个高频长 query 的失败会误熔断整个后端，把本可用的短 query 也降级掉。这是与经典模式的关键差异，也是落地时最容易踩的坑。

**4. 健康探测必须"主动 + 被动"双通道，且探测本身要低成本**

被动通道：每次真实搜索记录延迟/成功率/结构化解析失败率。主动通道：定时用**固定探针 query**（如已知稳定返回的短 query）打各后端，避免"真实流量稀疏导致健康状态滞后"。探针 query 必须极短、极稳定，否则探测本身成为新的故障源——这正是 DDG Lite 无法胜任探针的原因（它连探针都可能被反爬）。

**5. 当前最紧迫的空白是"契约层"，不是"后端数量"**

SearXNG/Brave/Tavily/Exa 都已存在，缺的是一个**统一 SearchResult 契约**（字段：title/url/snippet/rank/backend/latency/confidence）和**统一错误分类**（反爬/超时/限流/解析失败/空结果）。没有这层契约，加权投票无法做（各后端返回结构不同），降级无法做（无法区分"该降级"和"该重试"）。契约层是 1-2 天可交付的最小可落地单元，后端接入可以逐个增量。

## 技术细节

- **加权投票实现**：对每个后端维护 `weight = f(历史准确率, 平均延迟, 结构化解析成功率)`，融合时按 `score = Σ(weight_i * rank_score_i)` 排序；同一 URL 多后端命中则加权合并，单后端命中则按 weight 打折。冷启动用等权，跑够 N 次后切换为动态权重。
- **降级状态机**：`CLOSED → (连续失败 ≥ K) → OPEN → (冷却 T) → HALF_OPEN → (探针成功) → CLOSED`；K、T 按后端配置，DDG Lite 这类高反爬后端 K 应更小、T 应更长。
- **Bulkhead 分桶**：`bucket_key = hash(backend_id, query_class)`，每桶独立信号量 + 独立熔断计数，桶满即对该桶降级，不影响其他桶。
- **探针设计**：固定 3-5 条短 query，每 60s 打一次，只校验"是否返回 ≥1 条结构化结果"，不校验内容质量（避免探针变成质量评估）。
- **错误分类枚举**：`RATE_LIMITED / BLOCKED / TIMEOUT / PARSE_ERROR / EMPTY / OK`，降级策略按枚举映射（BLOCKED→长冷却，TIMEOUT→短重试，PARSE_ERROR→降权不熔断）。

## 与零的关联

零的搜索链路当前是"单后端直连 + 失败即中断"，这与本次实证的单点故障完全同构。把 WebSearch 抽象为可插拔能力，对零的直接收益是：**搜索失败从"推理链断裂"降级为"结果质量下降"**——即使所有后端都挂，零也应返回"搜索不可用，基于已有知识作答"的显式降级，而不是静默失败或卡死。这与零一贯的"显式失败优于隐式错误"原则一致。此外，契约层让零可以在不同任务间切换后端策略（如事实核查用高准确率后端，快速浏览用低延迟后端），这是当前硬编码架构做不到的。

## 新问题

1. 加权投票的"准确率"如何在没有 ground truth 的情况下估计？是否只能用"多后端一致性"作为代理指标，而一致性本身可能被系统性偏差污染（多个后端都错）？
2. 探针 query 的稳定性如何保证？如果探针本身被某后端针对性反爬，健康状态会误判——是否需要探针轮换？
3. 降级到"无搜索"时，零如何区分"该用已有知识硬答"和"该明确告知用户信息可能过时"？这个策略边界需要定义。
4. 多后端投票会放大延迟（取最慢后端）还是取最快？投票的延迟预算如何与零的响应时间约束对齐？

## 深层追问
**底层原理**：这是"故障域隔离 + 契约先行"的经典组合。可插拔的本质不是多后端，而是把"能力"从"调用点"里抽出来，用统一契约描述——契约一旦成立，降级、投票、权重才有作用对象。状态机（CLOSED/OPEN/HALF_OPEN）是控制论里的负反馈：用被动信号快速熔断、用主动探针低频恢复，避免"异常逻辑污染常态路径"。

**反例/限制**：① 一致性代理准确率有系统性风险——多后端同源（都爬同一批站点）会"集体错且一致"，投票反而放大置信。② 探针可被针对性识别，固定探针等于给反爬送指纹。③ 二维分桶在 query_class 划分粗糙时会碎片化，桶太细导致样本不足、熔断抖动。④ 降级到"无搜索"若无声，用户会把过时知识当实时事实——这是最危险的失败模式。⑤ 投票取最慢会击穿延迟预算，取最快则牺牲质量，本质是 SLA 与准确率的权衡，没有免费解。

**如果错了**：最可能的错是把"契约层"当成银弹。若各后端结构化字段语义不一致（snippet 长度、rank 定义、时间戳口径），契约只是形式统一、融合仍然失真。纠错方式是先用主备降级跑通、用真实流量验证"降级频率"这个硬指标，再决定是否上投票——顺序反了会拿未验证的权重去污染结果。

**对零最可操作的一步**：今天只做一件事——把"搜索不可用"定义成显式降级态并埋点。不改架构、不加后端，先在现有单后端链路上把静默失败改成带标注的"未实时检索"回答，统计降级频率。这一步零成本、可回滚，且直接验证"单点故障是否真的被降级为质量下降"——没有这个基线，后面所有投票和熔断都无从校准。
