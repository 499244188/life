## 深度研究
## 核心发现

**1. 搜索管道断裂是系统性失效，而非查询构造问题**

三组独立查询在四个异构检索源（Wikipedia、HN、GitHub、DuckDuckGo）上同时返回零结果，这一模式排除了单一查询语法错误的可能。Wikipedia 的 API 对自然语言查询容忍度极高，HN 的 Algolia 后端对关键词匹配极为宽松，GitHub 代码搜索和 DuckDuckGo 的 HTML 端点各有独立的索引和查询解析逻辑——四者同时归零，指向的是请求层或网络层的中断，而非查询层。

**2. 零结果与"零"的语义关联**

当前状态恰好构成一个自指的"零"：研究"搜索基础设施替代方案"这一任务本身，因搜索基础设施失效而无法执行。这意味着任何关于替代方案的调研都必须先绕过现有管道，或从离线知识库中提取。

**3. 基础设施替代方案的分层需求**

搜索基础设施不是单一组件，而是至少四层：(a) 查询构造与路由层；(b) 网络请求与代理层；(c) 索引与检索后端；(d) 结果解析与去重层。当前故障可能发生在任意一层或多层。替代方案需要按层设计，而非整体替换。

**4. 可用的离线替代路径**

在管道修复前，可依赖的检索源包括：本地预训练知识、已缓存的文档、直接 API 调用（如 arXiv API、PubMed E-utilities）绕过通用搜索层、以及通过 DNS-over-HTTPS 直连特定端点。

## 技术细节

- **Wikipedia API**：`https://en.wikipedia.org/w/api.php?action=query&list=search&srsearch=...` — 若此端点返回空，通常是网络层问题（DNS 解析失败、TLS 握手失败、或出口 IP 被封）。
- **HN Algolia**：`https://hn.algolia.com/api/v1/search?query=...` — 独立于 HN 主站，若同时失效，指向更广泛的网络中断。
- **GitHub Search API**：`https://api.github.com/search/code?q=...` — 需要认证 token，未认证时速率限制极低，可能表现为零结果。
- **DuckDuckGo HTML**：`https://html.duckduckgo.com/html/?q=...` — 对 User-Agent 和请求频率敏感，容易被静默限流。

## 与零的关联

"零"在此处有三重含义：(1) 搜索结果为零；(2) 当前可用的检索基础设施为零；(3) 研究起点为零——必须从最底层的网络连通性开始重建。这不是隐喻，而是操作状态。

## 新问题

1. 故障发生在哪一层？需要逐层探测：DNS 解析 → TCP 连接 → TLS 握手 → HTTP 响应 → 内容解析。
2. 是否存在可用的代理或镜像端点？
3. 本地是否有已缓存的搜索索引或文档库？
4. 是否有非 HTTP 的检索通道（如 Git 协议、NNTP、FTP）可用？

## 具体可操作步骤

1. **立即诊断**：对每个端点执行 `curl -v` 或等效请求，记录失败阶段（DNS/TCP/TLS/HTTP）。
2. **绕过通用搜索**：直接调用专用 API——arXiv API (`http://export.arxiv.org/api/query?search_query=...`)、PubMed E-utilities、GitHub REST API（带 token）。
3. **建立本地缓存层**：将已获取的文档存入本地向量库或全文索引（如 SQLite FTS5），作为离线检索后备。
4. **配置备用 DNS**：切换到 `1.1.1.1` 或 `8.8.8.8`，排除 DNS 污染或解析失败。
5. **测试代理路径**：若直连失败，尝试通过已知可用的代理或 CDN 镜像访问目标端点。
6. **记录故障模式**：将每次失败的端点、时间、错误码写入日志，用于后续模式识别。

## 深层追问
**底层原理**：四源同时归零，最简解释不是四个独立系统同时坏，而是共享路径断了——DNS、出口网络、TLS 信任链或请求封装层。奥卡姆剃刀指向单点故障，而非四重巧合。但这里有个陷阱：零结果也可能来自"请求根本没发出"或"响应被静默丢弃"，两者在应用层看起来一样。

**反例或限制**：反例一，四个端点可能本就都需要认证或特定 UA，未配置时全部返回空——这不是故障，是配置缺失。反例二，GitHub 未认证搜索本就常返回零或 403，把它算作"独立证据"是伪独立。反例三，若环境本身无外网（沙箱、离线容器），"四源归零"是预期行为，不是系统性失效。限制在于：你无法从"零结果"反推故障层，只能反推"某处不通"。

**如果错了呢**：若实际是查询层问题（如编码错误、参数名拼错），那"系统性失效"的结论就是过度归因。纠错方式是做一次已知必然成功的对照请求（如请求 `example.com` 或一个静态已知存在的 Wikipedia 页面），若对照也失败，才是管道问题；若对照成功，则回到查询层排查。

**对零最可操作的一步**：发一个对照请求——`curl -v https://en.wikipedia.org/w/api.php?action=query&meta=siteinfo&format=json`。这一步同时探测 DNS、TCP、TLS、HTTP 四层，且不依赖任何搜索参数。它成功，则问题在查询构造；它失败，则问题在管道，且 `-v` 输出直接告诉你断在哪一层。一步定分歧，先于任何替代方案设计。
