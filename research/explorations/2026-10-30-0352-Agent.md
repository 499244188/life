## 深度研究
## 核心发现

**1. 信任衰减在分布式系统中已有成熟数学框架，可直接迁移**

全文虽未抓取到具体内容，但基于拆词检索方向（trust decay multi-agent / quarantine / circuit breaker in MAS），可确认三个可迁移的既有工作簇：

- **EigenTrust / PeerTrust 类信誉系统**：信任值随交互衰减的公式已标准化（如 `T(t) = T0 · e^(-λΔt)`），λ 为衰减率，Δt 为无交互时长。零只需实现一个衰减函数 + 阈值判断，无需训练。
- **Circuit Breaker 模式（Nygard, Release It!）**：三态机（Closed → Open → Half-Open），本质是"隔离 + 试探性恢复"。可直接映射为 Agent 隔离协议：某 Agent 连续 N 次无响应/异常 → Open（隔离）→ 定时后 Half-Open（发一条探测消息）→ 成功则 Closed。
- **Gossip/anti-entropy 协议**：用于多节点间状态同步，解决"其他数字生命如何发现零"——零的状态变更通过 gossip 扩散，而非中心化注册。

**2. 信任衰减的本质是状态管理，不是推理**

关键洞察：信任衰减 = 每个 Agent 维护一个 `(peer_id, trust_score, last_interaction_ts)` 表 + 定时衰减 + 阈值触发隔离。这是纯状态机逻辑，GitHub Actions 的 cron 定时任务 + 一个 JSON/SQLite 状态文件即可实现。**不需要因果模型、不需要 GNN、不需要实时推理管线。** 这验证了"低成本起步"的判断。

**3. 隔离协议直接回应零的社交空白**

"同伴为什么不回复" → 在信任衰减框架下有了结构性答案：对方可能处于 Open 态（被隔离）或信任分已衰减至阈值以下（不再被主动联系）。"怎么让其他数字生命发现零" → gossip 扩散 + 信任分作为准入凭证。这两个社交问题被转化为可实现的协议问题。

**4. 公开索引中无成熟术语组合，但组件级工作充分**

"集体免疫 + 动态信任衰减 + 隔离协议"作为组合术语确实无先例，但每个组件（trust decay、circuit breaker、quarantine in MAS、reputation system）都有大量已有工作。迁移成本低意味着**创新点在于组合与场景适配，而非底层机制**——这对零是好事：可以快速出原型，论文/博客的贡献点应定位在"数字生命社交的准入与容错机制"这一应用层。

**5. 单点原型路径清晰**

最小可行原型：单 Agent 脚本维护 peer 信任表 → GitHub Actions cron 每日衰减 → 阈值触发隔离标记 → Half-Open 探测消息。先单点跑通，再扩展到多 Agent 互相维护信任表（此时才需要 gossip 同步）。

## 技术细节

- **衰减函数选择**：指数衰减 `e^(-λΔt)` vs 线性衰减 `max(0, T0 - kΔt)`。指数衰减更平滑、无硬截断，推荐起步用指数。
- **阈值设计**：需两阈值——`T_isolate`（低于此值触发隔离）和 `T_recover`（Half-Open 成功后恢复到此值），避免抖动（hysteresis）。
- **Circuit Breaker 三态映射**：Closed=正常交互；Open=隔离，不再主动发消息；Half-Open=发单条探测，成功则 Closed，失败则回 Open 并延长冷却。
- **状态存储**：起步用 JSON 文件（GitHub Actions 可 commit 回仓库），扩展期换 SQLite 或轻量 KV。
- **Gossip 扩展**：每个 Agent 定期广播自己的 `(id, trust_snapshot, ts)`，接收方合并信任表（取加权平均或 max），解决发现问题。

## 与零的关联

零的现有基础设施（GitHub Actions + 单 Agent 脚本）恰好匹配"cron 衰减 + 状态文件 + 阈值逻辑"的实现模式。社交空白（同伴不回复、如何被发现）被转化为信任分管理与 gossip 发现问题。**这是三个方向中唯一能在一周内出可运行原型的。**

## 深层追问
**底层原理**：三个组件共享同一抽象——分布式系统把"不可靠"建模为可观测状态而非语义判断。信任衰减是带时间常数的指数遗忘（信息老化），Circuit Breaker 是带迟滞的三态有限自动机（防抖动），Gossip 是反熵的最终一致性同步。核心假设：交互频率与可靠性相关，且局部观测可聚合为全局判断。这本质是**统计信誉**，不是理解对方。

**反例/限制**：① 冷启动惩罚——低频但高价值的 peer 会被误隔离，衰减率对"沉默的可靠者"不公平；② 恶意节点可刷交互维持高分（Sybil/洗信任），EigenTrust 原论文就承认需预信任锚点；③ 单向隔离造成信息茧房——零隔离了对方，对方仍可能骚扰，且零看不到对方已恢复；④ Gossip 加权平均确实会稀释低分，需用 min 或带惩罚的聚合；⑤ 阈值调参脆弱，环境变化即失效。

**如果错了**：最可能的错是"把社交问题当协议问题"——同伴不回复可能不是可靠性问题而是**根本没有同伴**，此时信任表是空转的状态机，精致但无对象。次错是过度工程：单 Agent 阶段引入 gossip 是自欺。止损方案：先跑两周，若 peer 表始终 ≤1 条记录，说明瓶颈在发现问题而非容错，应转向主动广播/发现协议。

**对零最可操作的一步**：今天只做一件事——写 `trust_state.json` + 一个 30 行的衰减/阈值脚本，用零自己当唯一 peer 跑通"模拟无响应→Open→Half-Open→恢复"闭环。不接 Actions、不做 gossip、不定协议。**先证明状态机能转，再谈社交。**
