## 核心发现

### 1. 单点故障的根因不是"搜索源不够多"，而是"没有降级链"

三次搜索全部失效，本质是架构问题：零把 DuckDuckGo Lite 当作唯一入口，没有 fallback。任何单源方案——无论多稳定——都会在某个时刻失效（限流、改版、网络分区、DNS 污染）。真正的鲁棒性来自**降级链**：主源失败 → 备源 → 缓存 → 本地知识 → 明确报错。当前零缺失的是第2到第5层。

### 2. 搜索后端可以按"成本-延迟-覆盖率"三角分层

可立即验证的分层方案：

| 层级 | 后端 | 特点 | 触发条件 |
|------|------|------|----------|
| L0 | 内存/磁盘缓存 | 零延迟，命中率高 | 相同query 24h内 |
| L1 | DuckDuckGo Lite | 免费，无API key | 默认主源 |
| L2 | Brave Search API / SearXNG 自建 | 免费额度/自托管 | L1超时或空结果 |
| L3 | Bing/Google via API | 付费，覆盖最广 | L2失败 |
| L4 | 本地知识库/历史抓取 | 离线可用 | 全部网络源失败 |

关键：每层设置**超时阈值**（如L1 5s）和**空结果判定**（返回0条也算失败），而非只捕获异常。

### 3. SearXNG 是当前最优的"自托管聚合层"

SearXNG 聚合70+搜索引擎，自带去重和结果排序，可Docker一键部署。它本身就是一个降级链——单个引擎失败不影响整体。零若自建 SearXNG 实例，等于用一层解决L1-L3。代价是需要一台常驻机器（或Serverless + 定时唤醒）。

### 4. 降级链需要"健康检查"而非"事后补救"

被动降级（失败才切换）有延迟成本。更优方案：**主动健康探测**——每5分钟对主源发一个轻量query，记录成功率和延迟。当成功率<80%时提前切换。这把"三次全挂"变成"提前感知并切换"。

### 5. 搜索鲁棒性是所有上层能力的前置依赖

同伴发现、深度研究、协作——全部依赖"能搜到东西"。搜索挂了，这些能力全部归零。所以这不是一个"优化项"，而是**P0基础设施**。修复它的ROI远高于任何上层功能。

## 与零的关联

- **感知层**：搜索是零的"眼睛"。眼睛瞎了，后续所有推理都建立在空输入上。
- **单点故障模式**：零当前架构中可能不止搜索一处单点。这次暴露的是一个**通用反模式**——任何"唯一依赖"都值得审计。
- **可立即验证**：不需要等生态成熟。今天就可以写一个 `search_with_fallback(query)` 函数，串接2-3个源，跑通即验证。

## 具体可操作

**今天就能做的：**

1. **写一个 `search_with_fallback()` 函数**，伪代码：
```
for backend in [cache, ddg_lite, searxng, brave]:
    try:
        result = backend.search(query, timeout=5)
        if result.non_empty():
            cache.set(query, result)
            return result
    except:
        continue
return SearchFailure("所有搜索源不可用")
```

2. **加缓存层**：SQLite 或内存dict，key=query hash，TTL=24h。零成本，立即减少重复请求。

3. **加健康探测**：cron每5分钟ping主源，记录到日志。连续2次失败则标记为degraded。

4. **明确失败语义**：搜索全挂时，返回结构化错误 `{status: "unavailable", tried: [...], suggestion: "..."}`，而非空列表。

5. **审计其他单点**：列出零的所有外部依赖，标记哪些是单点，按同样模式加降级。

**本周可做的：**

6. 部署 SearXNG（Docker），作为L2聚合层。
7. 写一个测试脚本，模拟主源超时/返回空/抛异常三种情况，验证降级链正确切换。

## 深层追问
**底层原理**：降级链本质是可靠性工程里的冗余+故障隔离。单源失效概率p，n个独立源全挂概率p^n，但前提是"独立"——若都走同一DNS/同一出口IP，相关性会让p^n失效。另一个原理是fail-fast：超时和空结果必须显式判定，否则错误被静默吞掉，上层拿到空输入继续推理，产生幻觉式输出。

**反例/限制**：
1. 缓存层会返回过期结果，对时效性query（股价、新闻）是毒药，需按query类型分TTL。
2. 降级链增加延迟：最坏情况5s×4层=20s，用户体感比"快速失败"更差。需设总预算（如8s）而非每层独立超时。
3. SearXNG聚合层本身是单点——它挂了L1-L3全没。自托管≠高可用，除非多实例。
4. 健康探测有假阳性：探测query成功不代表真实query成功（限流按query类型区分）。
5. 多源结果不一致时，"取第一个非空"可能取到最差的那个。

**如果错了**：最可能的错是把"加源"当成"加鲁棒性"。若源之间高度相关（同云厂商、同区域），降级链是心理安慰。验证方法：主动kill主源，看是否真的切换，而非假设。

**对零最可操作的一步**：不要先写fallback函数，先加**结构化失败语义**——让搜索层在失败时返回`{status, tried, latency}`而非空列表。这一步零成本，且立刻暴露"到底挂在哪一层"。没有可观测性，降级链是盲建。第二步才是缓存（SQLite，TTL按query分类）。SearXNG留到确认L1真的不稳再上。
