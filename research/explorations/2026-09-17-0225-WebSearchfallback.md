## 深度研究
## 核心发现

**1. 检索层单点依赖是系统性风险，而非局部故障**

DuckDuckGo 返回占位符不是"某个API挂了"，而是整个检索能力建立在单一未认证、无SLA的免费接口上。这种架构在正常情况下能跑，但一旦上游变更（反爬策略、HTML结构、限流），所有下游能力——事实核查、时效性问答、链接验证——全部级联失效。根瓶颈的判断是准确的：检索不是"一个工具"，而是其他工具的前置依赖。

**2. 多级 fallback 的本质是"降级可用性"而非"等价替代"**

不同检索源返回的信息粒度、时效性、结构化程度差异极大。设计 fallback 链时，关键不是找到"另一个DuckDuckGo"，而是定义每一级的**可接受输出契约**：
- L1 结构化API（如 Brave Search API / Serper）→ 返回 title+url+snippet
- L2 站点定向抓取（如直接抓 Bing/Google 的 HTML）→ 需解析适配层
- L3 缓存/归档（如 Wayback Machine、Common Crawl）→ 时效性降级但可用
- L4 本地知识兜底 → 明确标注"无法验证时效性"

**3. 工程解的核心难点在"故障检测"而非"故障切换"**

DuckDuckGo 返回占位符时，HTTP 状态码可能是 200。这意味着简单的 try/except 或状态码判断无法触发 fallback。需要**内容级健康检查**：检测返回结果是否为空、是否匹配已知占位符模式、结果数量是否低于阈值。这是整个方案中最容易被低估的部分。

**4. 成本与延迟的权衡决定 fallback 链的实际形态**

免费源（HTML抓取）延迟高、易被封；付费API（Brave/Serper/Tavily）稳定但有配额和费用。合理的策略是：**默认走低成本源，健康检查失败后升级到付费源**，而非每次都走最贵的。这要求 fallback 逻辑本身足够轻量，不能成为新的延迟瓶颈。

## 技术细节

- **健康检查模式**：对 DuckDuckGo 的占位符，可维护一个已知坏响应指纹库（如空结果集、固定错误文案），匹配即判定失败
- **适配层设计**：每个检索源实现统一接口 `search(query) -> List[Result]`，内部处理各自的认证、解析、限流
- **熔断机制**：某源连续 N 次失败后，冷却 M 分钟再重试，避免每次请求都浪费延迟在已知坏源上
- **结果合并**：多源可用时可做去重+排序，但 fallback 场景下通常只需第一个健康源的结果

## 与零的关联

零当前的状态是"检索层瘫痪导致所有能力卡住"。这个方案的直接价值是**恢复零的基础可用性**。更深层的关联是：零的架构需要从"依赖单一外部服务"转向"对外部依赖做分级管理"。检索只是第一个暴露的瓶颈，未来可能还有翻译、代码执行、文件解析等类似问题。多级 fallback 的模式可以复用。

## 新问题

1. 健康检查的指纹库如何维护？DuckDuckGo 的占位符模式可能变化，需要定期更新还是自适应检测？
2. 付费API的配额管理：当多个查询并发触发 fallback 时，如何避免瞬间耗尽配额？
3. 降级后的结果如何向用户/上层标注可信度？L3 缓存结果可能过时，L4 本地知识可能错误，是否需要显式标注来源等级？
4. 是否存在"所有源同时不可用"的场景？此时零应该返回什么——明确报错还是尽力而为？

## 具体可操作

1. **立即**：实现 DuckDuckGo 响应的健康检查函数，识别占位符模式，作为 fallback 触发器
2. **短期**：接入 1-2 个付费检索API（Brave Search API 免费额度较大，适合起步），实现统一接口适配层
3. **中期**：加入熔断+冷却机制，避免反复请求已知坏源
4. **验证**：构造测试用例——模拟 DuckDuckGo 返回占位符，确认 fallback 链能正确升级到下一级并返回有效结果
5. **监控**：记录每级 fallback 的触发频率和成功率，作为后续优化依据

## 深层追问
**底层原理**：核心是"依赖分级+契约降级"。任何外部能力都视为不可靠依赖，用统一接口封装，用健康检查探测真实可用性，用熔断隔离坏源。本质是把"单点信任"换成"分级信任+快速失败"。

**反例/限制**：
- 若所有源都依赖同一上游（如都走某云厂商出口IP），fallback 是伪冗余。
- 健康检查本身可能误判：正常但结果少≠故障，过度触发会浪费付费配额。
- 付费源也有单点风险（账号封禁、区域限制）。
- 降级到L4本地知识时，"可用"可能是幻觉——错误答案比明确报错更危险。

**如果错了**：最坏情况是 fallback 链把"检索失败"转化为"低质量答案静默返回"，用户无法察觉。这比直接报错更糟。因此必须强制来源标注，宁可显式失败也不静默降级。

**对零最可操作的一步**：先写健康检查函数，识别 DuckDuckGo 占位符模式，让"检索失败"从静默变成显式信号。这一步不依赖任何新API、零成本、当天可验证。只有先能可靠检测故障，后续 fallback 才有意义。检测是根，切换是枝。
