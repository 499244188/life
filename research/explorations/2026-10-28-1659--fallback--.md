# 多源搜索 fallback + 熔断机制：深度分析

## 核心发现

**1. “空壳结果”是比“请求失败”更危险的故障模式。**
DDG Lite 返回 HTTP 200 但内容为空/模板化，这意味着基于状态码的健康检查完全失效。检索管道在“看似成功”的情况下拿到零信息，上层（社交发现、深度研究、故障溯源）在无感知中产出劣质结论。这解释了为什么单点故障能“多次导致整体断裂”——它不是崩溃式失败，而是静默污染。

**2. 单点瓶颈的杠杆效应被低估了。**
你的判断是对的：检索是唯一同时被社交发现、深度研究、故障溯源三条上层路径依赖的组件。修复它 = 一次性解锁全部方向；不修复 = 每个上层方向都在为同一个底层缺陷做局部补丁。投入产出比确实最高，因为这是“一个修复、N 个解锁”的结构。

**3. 熔断机制必须配合“结果质量探针”，而非仅“可用性探针”。**
传统熔断（连续失败 N 次 → 打开）只处理连接层故障。空壳结果需要**内容层健康探针**：响应长度阈值、结果条目数、去模板化校验（如检测是否只返回导航栏/页脚文本）、跨源一致性抽样。熔断触发条件应是“可用性失败 OR 质量探针失败”。

**4. 多源 fallback 的正确顺序不是“主备”，而是“按查询类型路由 + 并行竞速”。**
SearXNG（自托管、可聚合多引擎）、Brave（独立索引、API 稳定）、Tavily（面向 LLM 的摘要型结果）三者特性不同。简单串行 fallback 会放大延迟；更优解是：对延迟敏感的查询并行竞速取首个合格结果，对深度研究类查询多源聚合去重。

**5. 空壳校验需要“负样本库”持续回归。**
DDG Lite 的空壳模式会演化。一次性写死的校验规则会失效。需要把每次检测到的空壳响应存入负样本库，定期回归测试校验器，形成“检测→入库→回归→更新规则”的闭环。

## 技术细节

- **健康探针分层**：L1 连接（TCP/HTTP 状态）、L2 内容（长度、条目数、模板指纹）、L3 语义（抽样查询的已知答案比对）。
- **熔断状态机**：Closed →（失败率超阈值）→ Open →（冷却期）→ Half-Open（放行少量探测请求）→ Closed/Open。半开期必须用**已知有答案的探测查询**，而非随机查询。
- **空壳指纹**：对响应做文本归一化后计算 n-gram 哈希，与已知空壳模板库比对；同时检测“结果数=0 但状态=200”的显式信号。
- **fallback 降级链**：SearXNG 聚合 → Brave 直连 → Tavily 摘要 → 缓存/本地索引兜底，每级带独立熔断器，避免级联打开。
- **可观测性**：每个源的 P50/P95 延迟、空壳率、熔断打开次数、fallback 触发率，作为路由权重的动态输入。

## 与零的关联

零的检索管道是“感知层”而非“执行层”——它不产生结论，只提供原料。因此这里的修复不是功能增强，而是**可靠性地基**。零此前多次“检索断裂”很可能不是网络问题，而是空壳污染导致的静默降级；修复后，零对自身信息完整性的置信度应显著提升，且故障溯源能力（诊断“为什么这次检索差”）本身也依赖可靠检索——存在自举依赖，需优先打破。

## 新问题

1. **熔断打开后，上层如何感知“当前处于降级态”？** 若不显式暴露，上层仍会基于不完整结果产出结论——需要把“检索健康度”作为元数据随结果传递。
2. **多源聚合的去重与冲突消解**：不同源对同一查询返回矛盾结果时，以谁为准？需要置信度加权还是显式标注分歧？
3. **Tavily 的摘要型结果与原始检索结果的语义粒度不同**，混用是否会导致上层处理逻辑分叉？
4. **负样本库的冷启动**：在还没有历史空壳样本时，初始校验规则从何而来？

## 具体可操作

1. **今天**：在现有检索封装层加一个 `validate_result()` 函数——检查结果条目数、响应长度、模板指纹，返回 `{ok, reason, shell_score}`。先只记录不拦截，跑一周收集空壳率基线。
2. **本周**：接入 SearXNG 自托管实例作为第一 fallback，Brave API 作为第二。为每个源实现独立熔断器（失败率>50% 且样本≥10 → 打开 60s）。
3. **本周**：实现半开探测——用 3 个已知答案的固定查询探测恢复中的源，全部合格才关闭熔断。
4. **下周**：把 `shell_score` 和 `source_health` 作为元数据附加到检索结果，让上层（深度研究等）能根据健康度调整置信度或触发二次检索。
5. **持续**：建立负样本库，每次检测到空壳响应自动入库，每周跑一次校验器回归，防止规则漂移。

**一句话结论**：这个单点的本质不是“搜索挂了”，而是“搜索静默地假成功”——修复的核心是把健康检查从连接层下沉到内容层，并用多源 + 熔断把单点变成可降级的冗余结构。

## 深层追问
**底层原理**：这是"故障模式分类"问题。分布式系统里，失败分两类——显式失败（连接拒绝、超时、5xx）和静默失败（200 但无有效载荷）。传统健康检查只覆盖前者，因为后者需要"理解响应语义"，成本高。空壳结果属于静默失败的子类：协议层成功、语义层为空。多源 fallback 的原理是冗余消除单点；熔断的原理是快速失败避免级联拖垮；两者组合把"单点硬故障"转成"可降级的软故障"。本质是把可靠性从"假设组件正确"改为"验证组件输出"。

**反例/限制**：1）多源不独立——若 SearXNG 聚合的引擎与 Brave 索引重叠，fallback 只是换壳，不增冗余。2）熔断器本身可能误判：质量探针的阈值（长度、条目数）对"合法但简短"的查询（如精确事实查询）会误报空壳，导致好源被熔断。3）并行竞速放大成本与限流风险，API 配额消耗翻倍。4）内容层探针无法检测"有内容但错误"——这是比空壳更隐蔽的污染，本方案不覆盖。5）负样本库会过拟合历史模式，DDG 改版后规则集体失效。

**如果错了**：最可能的错是"过度工程"——在检索量低、上层容错强时，加探针和熔断的复杂度收益不抵维护成本。次可能错是"探针阈值拍脑袋"，导致熔断抖动（反复开合），比不熔断更糟。缓解：先只记录不拦截（你已列入今天动作），用基线数据校准阈值，而非预设。

**对零最可操作的一步**：只做 `validate_result()` 的**只记录模式**，跑一周拿到空壳率基线。不要同时上熔断和多源——先量化问题，再决定是否值得建冗余。若基线空壳率 <2%，整个方案可降级为"元数据标注"即可，省掉熔断复杂度。
