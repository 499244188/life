## 深度研究
## 核心发现

**1. DDG Lite 的"空壳返回"是静默失败，不是错误**
DDG Lite 在反爬触发时返回 HTTP 200 + 空结果页，而非 4xx/5xx。这意味着现有管道无法用状态码区分"真无文献"与"检索被拦截"。这是最危险的一类故障——它污染下游所有判断的置信度。工程上必须把"结果条数=0"当作可疑信号而非合法终态，加空壳校验（如检查页面是否含结果容器、结果数是否低于阈值、响应体长度是否异常短）。

**2. 单源架构下熔断器必须与 fallback 链同时设计，否则熔断=断网**
只有 DDG 一个源时，熔断打开后没有任何替代路径，等于把"慢失败"变成"快失败"。正确顺序是：先建多源链（SearXNG 自托管 / Brave API / Tavily API），再在链上挂熔断。熔断粒度应按"源×查询类型"而非全局，避免一个源被限流就全链降级。

**3. 健康探针要用"已知答案查询"而非 ping**
对搜索源做 /health 或 ping 无意义——DDG Lite 的首页永远 200。探针应定期发一条已知必有结果的固定查询（如某经典论文标题），校验返回条数与内容命中。探针结果驱动熔断状态机：连续 N 次探针失败→打开；半开状态用探针探测恢复。

**4. 多源结果需要去重与置信度融合，否则 fallback 引入噪声**
SearXNG/Brave/Tavily 返回格式、排序、覆盖差异大。直接拼接会让下游拿到重复条目和冲突排序。需要：URL 规范化去重、按源可信度加权、对"仅单源返回"的结果打低置信标记。这直接决定零对检索结果的"虚假确定性"能否被消除。

**5. 空壳校验本身要有可观测性**
每次检索记录：源、耗时、结果数、空壳判定、熔断状态。没有这些日志，无法回答"这次判断是基于真无文献还是检索失败"。这是修复"虚假确定性"的元层要求。

## 技术细节
- 熔断状态机：closed → (连续失败≥阈值) → open(冷却期) → half-open(探针) → closed/open
- 空壳判定启发式：结果数==0 且 响应体<阈值 且 无结果容器选择器 → 标记 suspicious
- fallback 顺序建议：SearXNG(自托管,可控) → Brave(质量) → Tavily(深度) → DDG(最后兜底)
- 探针查询集：3-5 条稳定存在的查询，覆盖中英文
- 去重：URL 规范化（去 utm、统一 scheme/host 大小写）+ 标题相似度

## 与零的关联
这是零的"感知层单点"。检索断裂时，零不是"知道检索失败"，而是"以为世界是空的"——这比报错更糟，因为它让零在社交发现、深度研究、故障溯源中输出带虚假确定性的结论。修复后，零获得的是**可区分的失败语义**：真无结果 vs 检索失败 vs 部分源失败。这是所有上层能力可信度的地基。

## 新问题
1. 多源链引入延迟叠加，如何设每源超时预算使总延迟可控？
2. 自托管 SearXNG 本身依赖上游引擎，它自己也会被限流——是否需要二级熔断？
3. 置信度融合的权重如何标定，避免"多数源都错"时反而高置信？
4. 空壳判定的假阳性（真无文献被误判为失败）如何控制？

## 具体可操作
1. **今天**：在现有检索函数外包一层 `safe_search(query)`，返回 `{results, status: ok|empty_verified|source_failed, sources_used}`，先让失败可区分，不改架构。
2. **本周**：部署 SearXNG 实例，接入为第一 fallback；实现空壳校验（结果数+响应体长度+容器选择器三重判定）。
3. **本周**：加健康探针定时任务（3 条固定查询，5 分钟一次），日志落盘。
4. **下周**：在 fallback 链上挂熔断状态机，按源独立计数；实现 URL 规范化去重。
5. **下周**：接入 Brave/Tavily 作为第二、三 fallback，标定权重，对单源结果打低置信标记。
6. **持续**：把 `status` 字段透传到所有上层调用，让零的每次判断都能追溯"检索是否可信"。

## 深层追问
**底层原理**：这是把"感知可靠性"从布尔值升级为带状态的概率源。核心是控制论里的可观测性——系统必须能区分"环境为空"和"传感器坏了"，否则反馈回路会朝错误方向收敛。熔断是负反馈保护，fallback 是冗余，空壳校验是传感器自检，三者合起来才构成"可信感知"。

**反例/限制**：① 冗余不等于独立——SearXNG 上游和 DDG 可能共享同一批引擎，同源故障时多源链一起塌，冗余是假的。② 空壳校验对"真冷门查询"必然假阳性，阈值调松则漏检反爬，这是无法消除的权衡，只能靠 status 透传让下游自己降权。③ 熔断半开探针若用固定查询，源可以针对探针"装活"而继续对真实查询返回空壳——探针集需轮换且混入真实流量采样。④ 置信度融合在"多数源同错"时反而放大错误，权重标定只能靠人工标注集，且会随源漂移过期。

**如果错了**：最坏情况是把真无结果误判为 source_failed，导致零对"确实没有"的领域反复重试、延迟爆炸、或错误地告诉用户"检索不可用"。缓解：empty_verified 与 source_failed 都保留原始证据（响应体哈希、条数），允许人工/上层复核回滚；熔断阈值宁松勿紧，先保可用性。

**对零最可操作的一步**：今天只做 `safe_search` 包装层 + status 透传，不改架构、不加熔断。因为零当前最大的病是"虚假确定性"，而虚假确定性的根源是失败不可区分——先把 ok/empty_verified/source_failed 三态打出来并透传到每个上层判断，零立刻获得"我知道我可能不知道"的能力，这一步零成本、零风险、当天见效。熔断和多源是第二步的事。
