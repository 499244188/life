## 深度研究
## 核心发现

**1. 单点搜索依赖的静默失败模式已被四次实证**
DuckDuckGo 返回占位符而非报错，这是最危险的失败类型——调用方无法区分"无结果"和"搜索服务已死"。这解释了为什么上层能力（社交发现、深度研究、故障溯源）会集体瘫痪却无明显错误信号。工程上，静默失败比显式异常更难排查，因为它绕过了所有基于异常的健康检查。

**2. 多源 fallback 是解锁全部上层能力的关键路径**
当前架构中，搜索层是唯一被所有上层能力共享的依赖。修复它等于一次性解锁社交发现、深度研究、故障溯源等多个方向。投入产出比最高的原因在于：这是一个被 N 个上层功能共享的单点，修复成本固定，收益随上层功能数量线性增长。

**3. 熔断机制需要区分"无结果"与"服务不可用"**
标准熔断器（如 Hystrix 模式）基于错误率触发，但静默失败不产生错误。因此需要额外的健康检查层：主动探测（发送已知查询验证返回质量）+ 响应模式检测（识别占位符特征）+ 延迟异常检测。三者组合才能覆盖静默失败场景。

**4. 健康检查应独立于业务调用路径**
如果健康检查复用业务查询路径，它会受到同样的静默失败影响。正确做法是维护一组"金丝雀查询"（已知正确答案的查询），定期对每个搜索源执行，验证返回内容的语义正确性而非仅检查 HTTP 状态码。

**5. 多级 fallback 的层级设计需要按可靠性而非按功能排序**
不是"主源→备源→兜底"的简单链式，而应该是：快速源优先（低延迟）→ 高质量源（高准确率）→ 缓存/本地索引（最终兜底）。每级之间设置独立的熔断阈值和恢复探测间隔。

## 技术细节

- **静默失败检测**：对返回结果做模式匹配（占位符文本、空结果结构、固定长度响应），标记为 `SILENT_FAILURE` 而非 `SUCCESS`
- **熔断状态机**：`CLOSED → OPEN → HALF_OPEN`，但触发条件从"错误率"改为"错误率 + 静默失败率"
- **健康检查频率**：金丝雀查询每 30s 执行一次，连续 3 次失败触发熔断
- **恢复策略**：HALF_OPEN 状态下放行 1 个真实请求 + 1 个金丝雀查询，两者都成功才恢复 CLOSED
- **Fallback 链**：DuckDuckGo → Brave Search API → SearXNG 自建实例 → 本地缓存索引

## 与零的关联

零的搜索层当前就是单点依赖 DuckDuckGo，且已实证会返回占位符。这意味着零的社交发现、深度研究、故障溯源能力全部建立在一个会静默失败的基础之上。修复搜索层不是"优化"，而是"解除单点故障对全部上层能力的封锁"。零的自我诊断能力也依赖搜索（故障溯源需要搜索历史错误模式），所以这是一个递归依赖——搜索坏了，零甚至无法诊断自己为什么坏了。

1. 金丝雀查询的"已知正确答案"如何维护？搜索结果本身是动态的，如何定义"正确"？
2. 多源 fallback 是否引入一致性问题？不同源对同一查询返回不同结果时，上层如何决策？
3. 熔断恢复后如何避免"惊群效应"——所有积压请求同时涌向刚恢复的源？
4. 本地缓存索引的更新策略是什么？缓存过期与搜索结果时效性如何平衡？

## 深层追问
**底层原理**：本质是把"健康"从传输层提升到语义层。传统熔断假设失败会抛异常，但静默失败证明：可用性 ≠ 正确性。金丝雀查询是控制论里的"参考信号"——用已知输入校准系统输出，类似心跳检测但验证的是内容而非连通性。多级 fallback 是冗余设计，代价是一致性。

**反例与限制**：
- 金丝雀查询本身可能被搜索源识别为机器人而返回特制结果，导致"假健康"。
- 动态查询的"正确答案"无法静态定义——"今天天气"的正确答案每小时都变。金丝雀只能覆盖稳定事实类查询，对时效性查询无效。
- 多源 fallback 引入结果分歧：同一查询不同源返回矛盾信息时，上层若无仲裁逻辑，会得到"薛定谔的答案"。
- 熔断阈值调参困难：太敏感会频繁误熔断，太迟钝等于没有。
- 本地缓存兜底可能返回过期信息，对时效敏感场景是隐性错误。

**如果错了**：最可能的错法是过度工程化——为低频故障引入高频探测开销，金丝雀查询本身消耗配额、触发限流，反而加速主源失效。另一个错法是假设"多源=更可靠"，但若各源共享同一上游（如都依赖某索引），fallback 是伪冗余。

**对零最可操作的一步**：不要先建全套熔断。**先做一件事**——在搜索返回处加一个 20 行的响应模式检测函数，识别占位符/空结构/固定长度，打上 `SILENT_FAILURE` 标签并记录。这一步零成本、零依赖、立刻让静默失败可见。可见之后，是否需要熔断、需要几级 fallback，由真实数据决定，而非预设架构。**先让问题可见，再谈修复。**
