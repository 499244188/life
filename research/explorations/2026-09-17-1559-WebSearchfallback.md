## 一、核心发现（3-5 条）

**1. 单点搜索后端 = 单点故障，这是架构问题不是运维问题。**
DuckDuckGo Lite 连续失效瘫痪整条感知管道，说明当前检索层没有降级路径。任何依赖单一 HTML 端点（尤其是非官方 API 的 lite 页面）的方案，本质上是在别人的反爬策略上裸奔。DDG Lite 没有 SLA、没有官方 API 承诺、页面结构随时可变——它不该是主路径，更不该是唯一路径。

**2. “多级 fallback” 的关键不是堆叠引擎数量，而是分层异构。**
如果 fallback 链是 DDG Lite → DDG HTML → DDG API，那它们共享同一上游，一次 DDG 侧故障全部击穿。有效的多级应该是**跨供应商 + 跨协议 + 跨接入方式**的异构组合，例如：
- L1：官方 API（Brave Search API / Bing Web Search API / Google Custom Search JSON API / Serper / Tavily）
- L2：另一家官方 API（不同上游索引）
- L3：自建/第三方 SearXNG 实例（聚合多引擎，可自托管）
- L4：直接抓取 HTML 端点（DDG Lite、Startpage、Mojeek 等）作为最后兜底

**3. 检索层的健康检查与熔断必须先于上层能力建设。**
你现在的痛点是“失效了才知道”。需要的是：每个后端有独立的健康探针（定时发已知 query，校验返回条数与结构）、连续失败 N 次自动熔断、按优先级路由、失败自动降级并记录。这套东西不建，修好一次还会再瘫。

**4. 成本与延迟是 fallback 排序的隐藏约束。**
官方 API 通常按次计费且有 QPS 限制，HTML 抓取免费但慢且易被封。fallback 顺序不能只按“可靠性”，要按 **可靠性 × 成本 × 延迟** 综合排序，并且对高频 query 做缓存，减少对后端的实际压力。

**5. 归一化层是 fallback 能否真正工作的前提。**
不同后端返回的字段、排序、时间戳格式完全不同。如果没有统一的 result schema（title / url / snippet / published_at / source_engine / rank），上层（社交发现、深度研究、故障溯源）就要为每个后端写适配，fallback 等于没做。

## 二、技术细节（可直接落地的设计）

**路由与降级逻辑：**
```
for backend in sorted(backends, key=priority):
    if circuit_breaker[backend].is_open(): continue
    try:
        results = backend.search(query, timeout=T)
        if validate(results):          # 非空 + 结构合法 + 条数阈值
            circuit_breaker[backend].record_success()
            return normalize(results)
    except (Timeout, HTTPError, ParseError):
        circuit_breaker[backend].record_failure()
continue  # 全部失败 → 返回显式错误，不要静默返回空
```

**熔断参数建议：** 连续 3 次失败或 5 分钟内失败率 > 50% → 打开熔断，冷却 60s 后半开试探。

**关键工程点：**
- **超时要短**（单后端 3-5s），否则 fallback 链整体延迟爆炸。
- **并发探测可选**：对延迟敏感场景可同时打 2 个后端取先返回者（hedged request），但要注意成本。
- **结果校验不能只看非空**：DDG 失效时常返回“无结果”页面而非报错，必须校验结构特征（如结果节点数量、是否含跳转链接）。
- **缓存**：query 归一化后做 key，TTL 分级（热点 query 长、长尾短）。
- **可观测性**：每个后端的成功率、P95 延迟、熔断次数必须打点，否则无法判断 fallback 是否真的在起作用。

**候选后端清单（按异构性）：**
| 层级 | 方案 | 协议 | 备注 |
|---|---|---|---|
| L1 | Brave / Bing / Google CSE / Serper / Tavily | 官方 API | 需 key，有配额 |
| L2 | 第二家官方 API | 官方 API | 换上游索引 |
| L3 | 自托管 SearXNG | 聚合 | 可控，但依赖其上游 |
| L4 | DDG Lite / Startpage / Mojeek 抓取 | HTML | 免费，脆弱，仅兜底 |

## 深层追问
**底层原理**：fallback 本质是冗余 + 故障隔离。核心假设是"不同后端故障不相关"。熔断器（circuit breaker）来自分布式系统，用状态机（closed→open→half-open）把"反复打一个已死的后端"这种浪费掐掉。归一化层则是适配器模式，把异构返回映射到统一 schema，让上层不感知后端差异。

**反例/限制**：
1. **相关性失效**——若 L1/L2 都用同一上游索引（如都走 Bing），一次上游故障全链击穿，fallback 形同虚设。
2. **静默失败**——DDG 失效常返回"无结果"页而非报错，校验只看非空会误判成功，熔断永不触发。
3. **延迟叠加**——串行 fallback 最坏情况是各后端超时之和，3 个后端 × 5s = 15s，上层可能已超时。
4. **成本失控**——hedged request（并发打两个取先返回）会翻倍 API 计费。
5. **缓存掩盖**——热点 query 命中缓存时 fallback 链根本没被验证，故障被延迟发现。

**如果错了呢**：最可能的错是**把 fallback 当可靠性方案而非降级方案**。fallback 不提升单后端可靠性，只保证"整体不至于全瘫"。若误以为加了 fallback 就高枕无忧，会放松对主路径的监控。另一个错是**优先级排序只按可靠性**，忽略成本和延迟，导致高频 query 烧光 API 配额。

**对零最可操作的一步**：**先给现有 DDG Lite 加健康探针 + 结构校验**。具体：定时发已知 query，校验返回是否含结果节点（而非仅非空），连续 3 次失败即标记不可用并告警。这一步不需要新 API key、不需要预算、当天可做，且立刻让"失效可见"——这是所有后续 fallback 建设的前提。没有可见性，接再多后端也是盲修。
