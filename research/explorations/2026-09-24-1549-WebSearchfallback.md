## 深度研究
## 核心发现

**1. 检索层是单点故障，但"瘫痪"的根因不是搜索本身**

三条上层路径（社交发现、深度研究、故障溯源）全部依赖检索层，说明当前架构把 WebSearch 当作同步阻塞调用而非可降级的基础设施。真正的问题不是"搜索挂了"，而是没有定义"搜索部分可用时上层如何继续"。这是架构问题，不是工具问题。

**2. 多级 fallback 的本质是"降级策略设计"，不是"多接几个搜索引擎"**

有效的 fallback 链需要满足：每级有明确的触发条件（超时/空结果/质量阈值）、每级有明确的输出契约（上层不感知降级）、降级本身可观测。单纯堆叠 API 端点只会把单点故障变成级联故障。

**3. 社交发现、深度研究、故障溯源对检索的依赖模式不同**

- 社交发现：对时效性敏感，对完整性容忍度高 → 可用缓存/近实时索引降级
- 深度研究：对完整性敏感，对时效性容忍度高 → 可用离线语料/历史快照降级
- 故障溯源：对精确性敏感 → 需要结构化日志检索，可能根本不该走 WebSearch

统一 fallback 方案如果不区分这三类需求，会在降级时同时劣化三条路径。

**4. 不可控变量（外部 API 可用性、速率限制、结果质量）无法消除，只能隔离**

方案设计的关键是把不可控变量关在 fallback 链的某一级内部，让上层只看到"可用/不可用"二值信号，而不是让不确定性向上传播。

## 技术细节

- Fallback 链建议结构：主搜索 → 缓存层（TTL 分级）→ 备用 API → 本地索引 → 显式失败信号
- 每级需要：超时预算、结果质量评分、降级日志
- 输出契约：统一 schema，附带 `degradation_level` 字段供上层决策
- 可观测性：每级命中率、降级频率、端到端延迟分布

## 与零的关联

零的架构里，检索层是"感知外部世界"的唯一通道。它瘫痪意味着零失去的不只是搜索能力，而是**对外部状态的感知能力**——这比"搜不到东西"严重得多。修复 fallback 不只是恢复功能，是恢复零与世界之间的反馈回路。没有这个回路，零的所有上层推理都在对着过期或空白的内部状态做决策。

## 新问题

1. 三条上层路径是否应该共享同一条 fallback 链，还是各自独立？
2. 降级状态下，上层是应该"知道自己在降级"并调整行为，还是应该透明无感？
3. 本地索引的语料从哪来、多久更新一次、覆盖什么范围？
4. "显式失败"和"返回低质量结果"哪个对上层更安全？

## 具体可操作

1. **先定义输出契约**：统一检索结果 schema + `degradation_level` 枚举，再写任何 fallback 代码
2. **按路径拆分需求**：给社交发现/深度研究/故障溯源分别标注时效性 vs 完整性权重，决定各自的降级优先级
3. **实现最小可用链**：主搜索 → 缓存 → 本地索引 → 显式失败，先跑通再优化
4. **加可观测性**：每级命中率、降级触发原因、端到端延迟，这是后续调优的唯一依据
5. **故障溯源单独处理**：它可能不该走 WebSearch，先确认它的真实检索需求再纳入方案

## 深层追问
**底层原理**：这是"故障隔离 + 契约化降级"——把不确定性关进边界内，让上层只消费二值信号。本质是控制论里的反馈回路设计：检索层是零的传感器，传感器失效时系统要么盲走要么降级运行，不能假装没瞎。

**反例/限制**：
- 缓存降级在时效敏感场景会返回"正确但过期"的结果，比失败更危险——上层无法察觉自己在用旧世界的地图。
- 本地索引的覆盖盲区会系统性偏置：零会以为"搜不到=不存在"，把索引缺失误判为世界缺失。
- 统一 fallback 链在三条路径需求冲突时，会按最保守路径劣化全部——降级粒度错了。
- 质量评分本身不可靠：低质量结果混过阈值，比显式失败更毒。

**如果错了**：最可能的错是把"降级"当成"可用"。降级状态的零仍在推理，但推理前提已污染，错误会静默累积到上层决策。这比直接瘫痪更难排查。

**对零最可操作的一步**：先给检索层加一个 `degradation_level` 字段并让上层**必须显式读取**——不是透明无感，而是"知道自己在降级并调整行为"。透明降级是幻觉，显式降级才是诚实。这一步不改架构，只改契约，但它是所有后续 fallback 的前提：没有它，后面每一级降级都在制造看不见的错误。
