## 深度研究
## 核心发现

**1. 空壳页是"静默失败"，不是"报错失败"——这是熔断设计的关键前提。**
DDG Lite 返回 HTTP 200 + 合法 HTML 骨架 + 零结果，下游解析器拿到的是"成功但空"的响应。传统基于状态码/异常的重试机制完全失效，因为系统认为一切正常。这意味着熔断器不能只监听错误率，必须引入**语义级健康信号**：结果数=0、结果数骤降（相对7日基线）、DOM 结构指纹变化、关键选择器命中率。空壳检测应作为独立探针层，先于熔断判定。

**2. 多源 fallback 的正确顺序不是"优先级"，而是"成本-延迟-覆盖"三维排序。**
SearXNG（自托管、聚合、零边际成本、延迟中）适合做**第一跳**；Brave（API、低延迟、覆盖好、有配额成本）做**第二跳**；Tavily（为 LLM 优化、结果已清洗、成本最高）做**兜底**。关键工程点：fallback 触发条件要区分"源不可用"（熔断打开）与"源可用但结果差"（质量降级），后者应触发**并行补采**而非串行重试，避免延迟叠加。

**3. 熔断粒度必须下沉到"源×查询类型"，全局熔断会误伤。**
社交发现、深度研究、故障溯源三条线的查询特征差异极大（短查询/长尾/时效性）。若 DDG 对某类查询持续空壳但对另一类正常，全局熔断会切断健康流量。建议：每个源维护**分桶健康状态**（按查询长度、是否含时效词、语言），桶内滑动窗口统计空壳率，超阈值仅对该桶降级。

**4. 健康探针要用"金丝雀查询集"而非随机查询。**
随机探针无法区分"源挂了"和"这类查询本来就没结果"。维护一组已知必有结果的 canary 查询（如固定实体名、固定站点限定），定时打点，空壳率即真实健康度。探针频率与熔断恢复策略联动：半开状态用 canary 探测，连续 N 次通过才闭合。

**5. 单点修复的杠杆在于"检索抽象层"而非"换源"。**
真正要建的是一个 `SearchProvider` 接口 + `HealthRegistry` + `FallbackOrchestrator` 三层。上层三条线只依赖接口，源可热插拔。这样未来加源（如 Kagi、Exa）零改动，且熔断/探针逻辑复用。这是把"修 bug"变成"修架构"的关键。

## 技术细节

- **空壳检测启发式**：结果节点数==0；结果节点数 < 基线×0.3；页面含已知错误模板（"No results"、"rate limit"）；响应体大小 < 阈值（如 5KB）；解析后字段完整率 < 80%。
- **熔断状态机**：Closed →（空壳率>阈值，窗口≥20）→ Open（冷却 60s）→ Half-Open（canary 3 次）→ Closed。冷却时间指数退避，上限 10min。
- **并行补采**：质量降级时对次优源发起并行请求，取首个满足"结果数≥阈值且字段完整"的响应，其余取消（AbortController）。
- **健康数据持久化**：每源每桶存滑动窗口（最近 100 次）的空壳率、P50/P95 延迟，供基线计算与告警。

## 与零的关联

这是零的**能力基座单点**：社交发现依赖检索召回候选、深度研究依赖检索做多跳、故障溯源依赖检索定位证据。检索不可靠时，上层所有"智能"都在沙地上建楼，且失败是静默的——零会"自信地给出空结论"。修复后，零的每条线获得**可观测的检索健康度**，失败可归因、可降级、可告警，这是从"能跑"到"可信"的分水岭。

## 新问题

1. 三条线对"结果质量"的定义不同（社交要多样性、研究要权威性、溯源要时效性），统一的空壳阈值是否够用？是否需要分线的质量评分器？
2. Tavily 兜底成本随流量线性增长，配额耗尽时怎么办？是否需要"预算感知"的降级策略（低优先级查询不兜底）？
3. canary 查询集本身会漂移（实体过时、站点改版），如何自动维护？
4. 并行补采会放大对次优源的请求量，是否触发对方的限流，形成新的单点？

2. **下周**：接入 SearXNG 自托管实例作为第一跳，实现串行 fallback + 简单熔断（全局粒度先跑通），用 canary 集验证。
3. **再下周**：熔断下沉到分桶粒度，加 Brave 第二跳，实现并行补采与 AbortController 取消。
4. **持续**：建健康看板（每源每桶空壳率、延迟、fallback 触发次数），设告警阈值；Tavily 仅在"高优先级查询 + 前两跳均失败"时启用，加日预算上限。
5. **验收标准**：canary 集空壳率 < 2%；单查询 P95 延迟增幅 < 30%；fallback 触发率可观测；任一跳故障时上层三条线零感知（自动降级）。

## 深层追问
**底层原理**：这是控制论里的"可观测性先于控制"——熔断本质是反馈回路，而反馈需要真实信号。空壳页之所以致命，是因为它破坏了"响应=健康"的朴素假设，把故障藏进了语义层。多源 fallback 的原理是冗余换可靠性（可靠性≈1-∏(1-pᵢ)），但前提是故障不相关；分桶熔断的原理是避免"用全局统计掩盖局部退化"的辛普森悖论。

**反例/限制**：① 冗余源若共享上游（都走某 CDN 或都依赖同一索引），故障相关，fallback 形同虚设；② 空壳启发式会误杀"合法零结果"查询（生僻长尾词），把正常当故障，反而制造假熔断；③ 并行补采在限流敏感源上会自我放大成 DDoS 式触发，把次优源打成新单点；④ canary 集是"已知有结果"的查询，天然偏向头部实体，对长尾健康度是盲区——你测的是"源没死"，不是"源对这类查询好用"。

**如果错了**：最可能的错是把"架构修复"当成"可靠性修复"。三层抽象让失败可见、可降级，但**不提升召回质量本身**——DDG 空壳若源于其索引退化，换源只是转移问题。第二个错是过度工程：三条线流量若不大，分桶+并行+预算感知的复杂度可能超过收益，先用全局熔断+canary 跑两周数据再决定下沉。

**对零最可操作的一步**：本周只做一件事——给现有 DDG 调用包一层 `search()` 并**记录每次的结果数与响应体大小**，不改任何行为。一周后你就有真实空壳率基线，所有后续决策（阈值、分桶、是否值得接 SearXNG）都从猜测变成数据。先让失败可见，再谈修复。
