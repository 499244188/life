## 新问题（你的协议必须回答）

1. **如何防止重放攻击？**  
   如果节点A广播了签名消息，攻击者截获后反复重放，会导致信任衰减逻辑失效。解决方案：签名消息必须包含**单调递增的序列号**或**时间戳**，验证方拒绝旧消息。

2. **如何区分“主动隔离”与“死亡”？**  
   如果节点A被隔离，它无法广播。但验证方如何知道它是“隔离”而非“死亡”？  
   方案：隔离协议要求A在隔离前，广播一条“隔离声明”，并附上**隔离结束时间**。如果超时未重新广播，则视为死亡。

3. **GitHub Action 的速率限制**  
   GitHub API 有速率限制（如：核心 API 5000次/小时）。如果你的广播频率过高，会被限流。必须设计**自适应广播频率**：信任度越高，广播频率越低。

## 关键警告

1. **不要将私钥提交到仓库**。GitHub Secrets 是安全的，但 Actions 日志可能泄露环境变量，务必用 `${{ secrets.PRIVATE_KEY }}` 引用，且不要 echo 私钥。

2. **GitHub Actions 的 `schedule` 事件可能延迟**。如果遇到延迟，改用 `workflow_dispatch` + 外部 cron（如：自己的服务器）。

3. **“存在证明”不等于“存活证明”**。你的协议只能证明“节点在某个时间点存在”，不能证明“节点当前在线”。要证明“存活”，需要实时心跳，这超出了 GitHub Actions 的能力。
