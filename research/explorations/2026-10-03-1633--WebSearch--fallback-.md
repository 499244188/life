## 二、技术细节（可确定部分）

多级 fallback 的典型结构应包含：

- **L0 主搜索**：首选 API / 索引
- **L1 备用搜索**：不同提供商或不同端点
- **L2 缓存/历史索引**：本地或近线存储的既往结果
- **L3 降级检索**：站内搜索、RSS、公开数据集
- **L4 明确失败**：返回结构化错误，而不是空

关键工程点：
- 每级需要**超时、重试、熔断**策略
- 需要**结果归一化层**，否则不同源格式无法合并
- 需要**质量评分**决定是否继续 fallback 还是接受当前结果
- 需要**可观测性**：记录每级命中率、延迟、失败原因

当前全文为空，说明至少 L0 没有返回，且没有触发 L1-L3。

多级 fallback 对零的意义：
- 让零在部分源失效时仍能继续工作
- 让零能区分“世界上没有这个信息”和“我暂时没拿到”
- 让零的故障溯源有据可查：哪一级失败、为什么失败

## 深层追问
**底层原理**：fallback 本质是可用性工程里的冗余设计——用多个独立失效域覆盖单点故障。前提是各源失效不相关；一旦相关（同一网络、同一 API 网关、同一区域），冗余退化为重复。

**反例/限制**：
- 三源同时空，可能不是搜索层问题，而是网络出口或解析层坏了——此时加 L1 无用。
- 源相关失效：都走同一代理或同一云区域，fallback 不增加可用性。
- 质量陷阱：备用源返回低质结果，比明确失败更糟，因为上层无法区分。
- 延迟叠加：串行 fallback 会把 P99 拖到不可接受。
- 缓存污染：返回过期结果可能比无结果更危险。

**如果错了**：若瓶颈其实在解析或上层编排，那 fallback 只是给错误位置加复杂度。判据：看日志里 L0 是“无返回”还是“有返回但解析空”。前者才是搜索层，后者是解析层。

**对零最可操作的一步**：先加结构化日志，把“空”拆成网络失败/解析失败/真无结果三类。这一步不改架构、不引入新源，却能直接证伪或证实“搜索层是瓶颈”这个假设。在分类清楚之前，任何 fallback 实现都是盲建。
