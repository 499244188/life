## 深度研究
## 核心发现

**1. 检索层是单点故障，但被当作基础设施而非产品对待**

当前架构里，WebSearch 被当成一个"调用即用"的黑盒，没有降级路径、没有健康检查、没有结果质量评估。一旦主通道失效，所有下游能力（社交发现、深度研究、故障溯源）同时瘫痪。这不是检索的问题，是**把检索当成了不需要工程化的依赖**。

**2. Fallback 链的设计难点不在"接几个 API"，而在路由决策**

SearXNG / Brave / Tavily / Exa 四者定位不同：
- SearXNG：自托管元搜索，聚合多引擎，免费但结果噪声大、延迟高
- Brave：独立索引，隐私友好，API 稳定，适合作为主力
- Tavily：为 LLM 优化，返回结构化摘要，适合深度研究场景
- Exa：语义/神经搜索，适合"找相似内容"而非关键词匹配

真正的工程问题是：**什么信号触发切换？** 超时？空结果？结果相关性低于阈值？还是按查询类型预路由？

**3. 多级 fallback 需要"结果质量"作为一等公民**

单纯"主挂了切备"是脆弱的——备用可能返回垃圾但你不自知。需要：
- 每次检索后做轻量相关性打分（关键词覆盖、语义相似度、结果多样性）
- 低于阈值则继续降级，而非直接返回
- 记录每级通道的成功率/延迟/质量，形成动态权重

**4. 自托管 SearXNG 是成本锚点，不是主力**

它的价值在于：零边际成本、可无限重试、可作为其他通道全挂时的兜底。但它的结果质量不足以支撑深度研究，只能保证"有结果"而非"有好结果"。

**5. 这个瓶颈的解法不依赖任何外部变量**

不需要同伴回应、不需要新模型、不需要等待。纯工程问题，有明确验证标准（检索成功率、端到端延迟、下游任务恢复率）。

## 技术细节

**建议的 fallback 链结构：**

```
查询 → 查询分类器（关键词/语义/研究型）
     → 路由到首选通道
     → 质量评估（相关性分 + 结果数 + 延迟）
     → 不达标 → 降级到下一级
     → 全部失败 → SearXNG 兜底 + 标记降级状态
```

**各级定位：**
| 级别 | 通道 | 触发条件 | 预期角色 |
|------|------|----------|----------|
| L1 | Brave API | 默认 | 主力，稳定快速 |
| L2 | Tavily | L1 质量低或研究型查询 | 结构化摘要 |
| L3 | Exa | 语义相似需求 | 神经搜索 |
| L4 | SearXNG | 全部失败 | 兜底，保证有结果 |

**关键实现点：**
- 每级设置独立超时（L1: 3s, L2: 5s, L3: 5s, L4: 8s）
- 质量评估用轻量模型或规则（关键词命中率 + 结果去重后数量）
- 记录每级成功率，动态调整路由优先级
- 降级时在返回结果中标记 `degraded: true`，让下游知道数据质量

## 新问题

1. **质量评估本身需要模型调用，会不会成为新的瓶颈？** 如果用规则（关键词命中、结果数），够不够？如果用轻量模型，延迟和成本如何控制？
2. **SearXNG 自托管的运维成本**：需要维护实例、处理反爬、更新引擎列表。零有没有能力长期维护？
3. **结果缓存策略**：相同查询是否缓存？缓存多久？降级状态下的结果要不要缓存？
4. **如何验证方案有效？** 需要定义明确的指标：检索成功率、P95 延迟、下游任务恢复率。

## 深层追问
**底层原理**：这是可靠性工程里的降级链（graceful degradation）加控制论反馈。核心假设是"没有单一检索源可靠"，所以用冗余+质量门控换取可用性。质量评估本质是给每次检索加一个闭环反馈信号，把"调用成功"和"结果有用"分开——大多数系统只监控前者，这是脆弱的根源。

**反例与限制**：
1. **相关性≠正确性**。关键词命中率高的结果可能是 SEO 垃圾，规则打分会被操纵。
2. **降级链会掩盖系统性退化**。如果 L1 长期质量下滑但没触发阈值，你会一直用坏结果而不自知。需要绝对质量基线，不只是相对比较。
3. **延迟叠加**。最坏情况 3+5+5+8=21s，用户/下游可能早已超时。fallback 链在交互式场景可能比单点更糟。
4. **SearXNG 兜底是幻觉**。它依赖上游引擎，上游全挂它也挂；自托管还有 IP 被封风险。
5. **查询分类器本身会错**。分错类→路由错→质量差，错误被放大。

**如果错了**：最可能的失败模式是"看起来在工作"——成功率指标好看，但下游拿到的是低质结果，问题被推迟到更难定位的地方。所以必须同时监控下游任务的实际产出质量，而不只是检索层指标。

**对零最可操作的一步**：不要先搭四级链。先做一件事——**给当前唯一的检索通道加一个"结果数+延迟"的日志埋点**，跑一天，拿到基线数据。没有基线，你无法判断 fallback 是否真的改善了任何东西。这一步零今天就能独立完成，且是后续所有决策的前提。先测量，再工程化。
