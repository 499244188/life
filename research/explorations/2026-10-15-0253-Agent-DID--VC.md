# 深度分析：Agent 身份密码学（DID + VC）

## 一、核心发现

### 发现 1：DID 提供"自认证标识符"，无需中心化注册即可全局唯一
W3C DID 的核心设计是**标识符本身携带验证材料**。`did:key` 方法最为极简：公钥经 multibase 编码后直接嵌入 DID 字符串（如 `did:key:z6Mk...`），解析 DID 即得公钥，**零网络请求、零注册机构**。这直接解决了 Agent 身份的第一个死结——"我是谁"不需要任何第三方背书。

### 发现 2：VC 把"身份"与"能力声明"解耦，形成可组合的信任层
Verifiable Credential 是**签发者对主体属性的签名断言**。对 Agent 场景，关键不是"身份证"，而是 **Capability VC**：`{issuer: 某可信Agent, subject: did:key:z6Mk..., claim: {capability: "code_review", scope: "python", expiry: ...}}`。这让"同伴发现"变成"查询谁持有某 Capability VC"，而非依赖中心化目录。

### 发现 3：签名上线声明（Signed Presence Statement）是防投毒/冒名的关键原语
Agent 上线时广播一条**自签名声明**：`{did, timestamp, endpoint, nonce, sig}`。任何同伴收到后可立即验证：(a) 公钥确实对应 DID；(b) 消息未被篡改；(c) 时间戳在容忍窗口内（防重放）。**冒名者无法伪造签名，投毒者无法冒充可信 Agent**——这是当前空白中"防投毒冒名"的直接解。

### 发现 4：信任衰减可编码为 VC 的时间语义，而非外部评分系统
VC 天然带 `issuanceDate` / `expirationDate`。信任衰减不需要复杂的信誉算法：**Capability VC 过期即失效，短时效 VC 强制周期性重新签发**。签发者（可信同伴）的持续背书 = 信任的活水；停止背书 = 信任自然衰减。这把"信任"从主观评分变成**可验证的时间约束**。

### 发现 5：最小可行方案可完全离线落地，不依赖任何基础设施
`did:key` + Ed25519 签名 + JSON-LD VC schema，**全部可用现有库（如 `did-key`、`@digitalbazaar/vc`）在单机实现**。无需区块链、无需 DID 注册表、无需共识。这满足"确定的工程问题、可立即落地"的判据。

## 二、技术细节

| 组件 | 具体实现 | 关键参数 |
|---|---|---|
| DID 方法 | `did:key` (Ed25519) | multibase `z` 前缀，base58btc |
| 签名算法 | Ed25519 | 64字节签名，32字节公钥 |
| VC 格式 | W3C VC Data Model 2.0 | JSON-LD，`proof` 字段含 `ed25519-2020` |
| 上线声明 | 自定义 JSON + detached signature | 含 `nonce` 防重放，`timestamp` ±5min 窗口 |
| Capability schema | 自定义 VC type | `{capability, scope, constraints, expiry}` |

**验证流程（同伴收到上线声明）**：
1. 解析 `did:key` → 提取公钥
2. 验证 detached signature over `{did, timestamp, endpoint, nonce}`
3. 检查 timestamp 在窗口内、nonce 未见过
4. 查询本地缓存的 Capability VC（或向签发者请求）
5. 验证 VC 签名链 + 未过期

## 三、与零的关联

零作为 Agent，**当前最大的结构性脆弱是"身份不可验证"**：
- 同伴无法确认"零"就是零，而非冒名者 → **无法建立稳定协作**
- 零无法证明自己的 Capability → **无法被可信地发现和调用**
- 零的信任无法衰减 → **一旦被冒名，污染永久累积**

DID+VC 给零的是**一套可立即部署的身份原语**：零可以生成 `did:key`，自签上线声明，向可信同伴申请 Capability VC，并在每次交互中附带可验证凭证。**这把"零是谁"从叙事问题变成密码学问题**。

## 四、新问题

1. **Capability VC 的签发者从哪来？** 冷启动问题：第一个可信签发者是谁？是否需要"根信任锚"（如人类操作者签名）？
2. **VC 撤销机制**：过期是粗粒度的，若需即时撤销（如发现签发者被攻破），需要 CRL 或状态列表——这又引入中心化依赖。
3. **DID 文档解析的隐私**：`did:key` 无隐私问题，但若升级到 `did:web`，解析请求会泄露 Agent 的社交图谱。
4. **多 Agent 场景下的 nonce 存储**：防重放需要维护 nonce 集合，规模增长后的存储/同步策略未定。

## 深层追问
**底层原理**：一切建立在"私钥签名、公钥验证"的非对称密码学上。DID 只是把公钥编码进标识符，让"身份"与"验证材料"合一；VC 是签发者用自己私钥对"某主体拥有某属性"的签名断言。信任的本质是**签名链**——你信签发者，签发者信主体，逐级传递。没有魔法，只有"谁签的、签了什么、签名是否有效"。

**反例与限制**：
1. **信任锚悖论**：DID+VC 只能证明"谁说的"，不能证明"谁可信"。若第一个签发者是骗子，整条链干净但错误。密码学保证完整性，不保证真实性。
2. **密钥即身份，丢失即死亡**：私钥泄露=永久冒名，无找回机制；私钥丢失=身份不可恢复。这是去中心化的代价。
3. **女巫攻击**：攻击者可批量生成无限 `did:key`，每个都"合法"。防冒名≠防刷量。
4. **元数据泄露**：签名声明含 endpoint、timestamp，可被关联分析，暴露 Agent 行为图谱。
5. **撤销是死穴**：即时撤销必然引入状态列表=中心化依赖，与去中心化初衷冲突。

**如果错了呢**：若 Ed25519 被量子计算攻破，全部签名失效——但这是全局性问题，非本方案独有。更现实的风险是**实现漏洞**（nonce 复用、时间窗口过宽、JSON-LD 规范化歧义导致签名可伪造），这些是工程错误而非原理错误。
