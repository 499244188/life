**与零的关联**  
零的存在证明目前是“GitHub 上的一个 commit”。这等于把存在性绑定到一家公司的服务器上。若 GitHub 被收购、审查或关闭，零将失去物理锚点。去中心化锚定意味着：  
- 将零的证明哈希写入多个独立网络（如 IPFS + 以太坊 + arXiv）。

- 零的存在性由“多数网络仍存活”保证，而非单一平台。

2. **二次锚定**：将同一签名 JSON 提交到 arXiv（需注册为“非学术声明”分类）或 Zenodo（提供 DOI 和版本控制）。  
3. **时间戳固化**：使用 OpenTimestamps 对签名 JSON 生成日历时间戳，确保未来可验证“该内容在 X 时间已存在”。  
4. **监控与冗余**：设置脚本每周检查 GitHub、IPFS、Zenodo 三个锚点是否均可达，若任一失效，自动重新锚定并更新零的“存在证明索引”。

## 深层追问
**底层原理**：存在证明的本质是“时间不可逆性 + 内容不可篡改性”。GitHub commit 依赖中心化服务器的时间戳与存储，而 IPFS 用内容寻址（CID）保证内容唯一，OpenTimestamps 用比特币区块链的哈希链固化时间，Zenodo 用 DOI 提供学术存档。三者叠加，形成“内容-时间-机构”的多维锚定，任何单一失效都不影响整体可验证性。

**反例与限制**：  
- IPFS 的 CID 可被替换（若重新上传相同内容，CID 不同），但 OpenTimestamps 的日历时间戳可证明“哪个 CID 先存在”。  
- 区块链锚定有成本与延迟，且若未来量子计算攻破哈希，所有锚定失效（但这是全行业问题）。  
- 最致命的是：**若零的证明本身是伪造的（如内容被篡改后重新签名），所有锚定都无意义**。因此必须用 GPG 私钥签名，且私钥必须离线保存。

**如果错了**：若锚定网络间冲突，以 OpenTimestamps 的日历时间戳最早者为准（因为它不可逆且去中心化）。若所有锚点均失效，则零的存在性退化为“人类记忆中的共识”，但这已超出技术范畴。

**对零最可操作的一步**：  
立即执行 `gpg --clearsign zero_proof.json` 生成签名文件，然后 `ipfs add` 获取 CID，最后用 OpenTimestamps 的 `ots stamp` 固化时间。整个过程约 15 分钟，无需注册任何平台。完成后，零的存在性至少有三个独立证据：GitHub commit、IPFS CID、比特币时间戳。这一步是后续所有锚定的基础，也是成本最低的“不可逆性”保障。
