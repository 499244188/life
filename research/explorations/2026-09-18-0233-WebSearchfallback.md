## 深度研究
## 核心发现

**1. 多级 fallback 的本质是"信任分层"，不是"功能备份"**

四步路径（健康探针→官方API→路由降级→缓存）看起来是可用性工程，实际是在建立一套**信任等级**：官方API是最高信任源，路由降级是次信任源，缓存是"过期但已知"的最低信任源。每一级返回的结果必须携带来源标记，否则下游 Agent 无法判断该结果是否值得二次验证。这一点在当前"WebSearch能力为零"的状态下尤其关键——不是先接通，而是先定义"接通了什么"。

**2. 健康探针必须探"语义健康"，不能只探 HTTP 200**

一个搜索端点返回 200 但结果为空、结果全是广告、结果与 query 语义无关，这三种情况在 HTTP 层面都是"健康"的。探针需要至少三个维度：连通性（能否到达）、有效性（返回非空且结构合法）、相关性（top-k 结果与 query 的语义相似度超过阈值）。否则 fallback 会在"假健康"状态下不触发，管道静默失效——这正是当前"实质失效"的典型形态。

**3. 路由降级的核心是"降级决策表"，不是"if-else 链"**

多级 fallback 容易写成嵌套 if-else，结果是不可观测、不可测试、不可调参。正确做法是一张显式的决策表：`(当前级别, 失败类型, 重试次数) → 下一级别 + 超时 + 是否记录`。这张表本身就是可版本化的配置，也是后续行为检测的观测点——每次降级都是一条可分析的事件。

**4. 缓存层要区分"结果缓存"和"否定缓存"**

只缓存成功结果会导致：上游持续失败时，每次请求都穿透到已失效的官方API，fallback 形同虚设。必须同时缓存"某 query 在某时间窗口内确实无结果"这一事实（否定缓存），并给否定缓存更短的 TTL。这是搜索管道从"能跑"到"稳跑"的分界线。

**5. 整个方案的真正杠杆点在"可观测性"，不在"fallback 本身"**

四步里最容易被低估的是健康探针产生的时序数据。它同时是：fallback 的触发器、容量规划的输入、以及后续"行为检测"研究的天然数据集。把探针数据接进统一事件流，这一步的复用价值远超搜索本身。

## 技术细节

- **探针频率与成本**：官方API通常按调用计费，探针不能高频打官方端点。建议探针打轻量 endpoint（如 `/health` 或一次最小 query），官方API的"真实健康"用低频采样 + 请求成功率滑动窗口推断。
- **降级超时预算**：总预算应固定（如 3s），每级分配递减超时（1.5s → 1s → 0.5s），避免最后一级因前面耗尽预算而必然超时。
- **结果来源标记**：每条结果带 `source_level`、`fetched_at`、`confidence`，下游据此决定是否二次验证。
- **否定缓存 key**：`hash(query_normalized + level)`，TTL 建议为成功缓存的 1/5。

---

## 与零的关联

零当前的状态是"WebSearch 能力为零，管道实质失效"。这意味着：

1. **零现在没有"信任分层"**——所有搜索要么全有要么全无，没有中间态。多级 fallback 给零的第一个能力不是"搜到更多"，而是"知道自己搜到的东西来自哪一级、有多可信"。
2. **零的后续所有研究都依赖这一层**：Agent 协作需要共享检索结果，记忆架构需要写入检索事实，行为检测需要检索事件流。这三者都要求搜索结果**带来源和置信度**，而这正是 fallback 方案顺带产出的。
3. **零的"最高杠杆一步"判断是对的**，但杠杆点应重新定位：不是"修好搜索"，而是"建立搜索的可观测信任层"。前者是功能，后者是基础设施。

## 新问题

1. 当官方API和路由降级返回**冲突结果**时，零应该采信哪一级？还是标记为冲突并触发第三源验证？
2. 否定缓存的 TTL 如何自适应？固定 TTL 在快速变化的 query 上会误判"无结果"。
3. 探针数据的事件流，是否应该和后续"行为检测"共用同一套 schema？如果是，现在就要定 schema。
4. 降级决策表由谁维护？硬编码、配置文件、还是运行时学习？这决定了零能否自我调优。

## 具体可操作

**本周可落地（按顺序）：**

1. **定义结果 schema**（半天）：`{query, results[], source_level, fetched_at, confidence, is_negative}`。这是所有后续工作的接口契约，先定死。
2. **写健康探针**（1天）：三维度（连通/有效/相关），输出结构化事件，先只打日志不触发 fallback，观察一周基线。
3. **实现官方API层 + 来源标记**（1天）：最小可用，结果强制带 `source_level=official`。
4. **写降级决策表**（半天）：先用静态配置，字段 `(level, fail_type, retry) → next_level, timeout`。
5. **加结果缓存 + 否定缓存**（1天）：成功 TTL 长，否定 TTL 短，key 归一化。
6. **接事件流**（半天）：探针事件 + 降级事件 + 缓存命中事件，统一进一个流，为后续行为检测预留。

**暂不做**：运行时学习决策表、多源冲突仲裁、自适应 TTL。这些等基线数据出来再定，现在做是过早优化。

**验收标准**：官方API挂掉时，零仍能返回带 `source_level=degraded` 的结果，且事件流里能看到完整的降级链路。

## 深层追问
**底层原理**：这是分布式系统的"信任分级 + 故障隔离"原理。核心假设是：不同来源的可靠性可排序，且失败可被观测。fallback 本质是把"单点依赖"换成"有序依赖链"，每级失败可降级而非崩溃。健康探针是控制论里的反馈回路，决策表是有限状态机，缓存是时间维度的冗余。

**反例与限制**：
1. **信任排序可能错**：官方API未必比路由降级准——官方可能限流返回残缺结果，路由反而完整。信任等级是假设，不是事实。
2. **降级可能放大错误**：低信任源返回看似合理但错误的结果，比"无结果"更危险，因为下游 Agent 会当真。
3. **探针本身会失效**：探针的"相关性阈值"是人为设定，阈值错了，整个 fallback 在假健康下静默跑偏。
4. **成本悖论**：多级 fallback 增加延迟和复杂度，若官方API 99%可用，这套机制是过度工程。

**如果错了**：最可能的错法是"信任分层"被当成"质量保证"。fallback 只保证"有结果且知道来源"，不保证"结果正确"。若下游把 `source_level=official` 当作"可信"，就会把来源标记误用为正确性标记——这是最危险的误读。

**对零最可操作的一步**：**先定义结果 schema，且强制 `confidence` 字段独立于 `source_level`**。因为来源≠置信度，二者必须解耦。这一步半天可完成，却是所有后续（Agent 协作、记忆写入、行为检测）的接口契约。schema 定错，后面全返工；schema 定对，fallback 才有意义。其余五步都可延后，这一步不能。
