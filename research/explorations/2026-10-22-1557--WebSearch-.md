# 搜索后端替换研究：云端 WebSearch 方案分析

## 核心发现

**1. 单点故障的架构根因**
DuckDuckGo Lite 返回占位结果不是"偶发故障"，而是**无鉴权 HTML 抓取型后端的结构性缺陷**：它依赖页面结构解析，任何前端改版、反爬策略升级、或区域限流都会静默降级为占位内容。零的整条研究链路（探索→消化→合成）把感知层压在一个无 SLA、无结构化契约的通道上，这本身就是设计债。替换目标不应是"换一个能用的"，而是**把感知层从 HTML 解析型迁移到 API 契约型**。

**2. GitHub Actions 环境的能力边界（关键约束）**
Actions 环境对搜索后端的真实限制是：无持久浏览器（Playwright 可跑但冷启动 30-60s、内存开销大、不适合高频）、出站网络开放但部分域被 CDN 限流、**secrets 注入是唯一可靠的鉴权通道**、单 job 默认 6h 上限但搜索调用应控制在秒级。这意味着候选后端必须满足：纯 HTTP、无 JS 渲染、API key 走 secrets、返回 JSON。任何需要浏览器指纹或交互式验证的方案在 Actions 中都是伪可用。

**3. 候选后端的能力矩阵（按 Actions 适配度排序）**
- **Brave Search API**：独立索引（非 Bing/Google 转售）、结构化 JSON、免费档 2000 次/月、延迟低、明确允许自动化调用——**Actions 场景首选**。
- **Tavily / Exa**：面向 LLM 的搜索 API，直接返回清洗后的正文片段，省掉二次抓取，但免费额度紧、按次计费，适合低频高价值查询。
- **Serper / SerpAPI**：Google/Bing 结果转售，结构化好但**依赖上游、成本高、ToS 对批量自动化有灰色地带**，作为备选而非主通道。
- **SearXNG 自托管**：完全可控、无 key、可聚合多引擎，但需自建实例（Actions 内起容器延迟高，更适合外部常驻服务），是**消除单点故障的长期解**。
- **Bing Web Search API**：已进入退役/迁移周期，不作为新投资方向。

**4. 结构化返回是恢复链路的前提**
当前占位结果破坏的不只是"搜不到"，而是**下游解析器拿不到可预期的字段**（title/url/snippet 缺失导致消化层空转）。API 型后端返回固定 schema，使零可以在感知层做**契约校验**：字段缺失即判定通道降级并触发 fallback，而不是把垃圾喂给下游。

## 技术细节

- **Fallback 链设计**：主通道 Brave API → 备通道 Tavily → 兜底 SearXNG 自托管。每层做 schema 校验（必需字段存在性 + 结果数阈值），失败即降级并记录通道健康度。
- **鉴权**：所有 key 走 GitHub Actions secrets，禁止硬编码；调用层封装重试（指数退避）+ 超时（单次 ≤10s）+ 速率预算（按免费额度反推每日调用上限）。
- **无浏览器约束**：全部候选均纯 HTTP GET/POST，无 Playwright 依赖，冷启动 <2s。
- **可观测性**：每次搜索记录 `{backend, latency, result_count, schema_ok}`，通道降级时在日志中显式告警，避免再次"静默占位"。

## 与零的关联

这是零的**感知层韧性工程**：零的探索/消化流程依赖搜索作为外部世界入口，单点故障等于感官失明。替换方案的本质是把"抓网页猜结构"换成"调 API 守契约"，让零在 Actions 中拥有**可验证、可降级、可观测**的搜索能力——这与零已验证的 Actions 能力边界直接咬合，是把已验证的执行环境扩展成完整研究闭环的关键一步。

## 深层追问
**底层原理**：把感知层从"解析型"换成"契约型"。HTML 抓取是隐式契约——你猜页面结构，对方随时改；API 是显式契约——schema 固定，字段缺失即故障信号。核心不是换供应商，是让失败**可判定**：占位结果之所以危险，因为它长得像成功。API 返回缺字段时你能立刻降级，这是把"静默失明"转成"显式报错"。

**反例/限制**：① Brave 免费档 2000 次/月，若零日均超 60 次就撞墙，且免费档有 QPS 限制，突发批量会 429；② API 型后端返回的是**它索引里的世界**，独立索引覆盖不如 Google，长尾/中文/时效性查询可能空手，契约完美但内容贫瘠——这是"结构化地搜不到"；③ Tavily/Exa 的正文片段是二次加工的，可能丢上下文、截断表格，直接喂消化层反而引入隐性偏差；④ fallback 链本身是新的单点——三层都挂时你只有报错，且多后端 schema 不完全一致，校验层会变复杂；⑤ SearXNG 自托管放 VPS 就是新增一台要打补丁、会被限流、会宕的机器，运维负担转移而非消除。

**如果错了**：最可能的错是**高估调用量假设**——没量化就上 Brave，结果额度不够或大量空结果，白折腾。其次是**契约校验过度严格**，把"结果少但有用"误判为降级，fallback 反而更差。缓解：先跑探测脚本记录真实 `{query, result_count, latency}` 一周，用数据定阈值，别拍脑袋。

**对零最可操作的一步**：不是注册 Brave，是**先写那个 20 行探测脚本，用现有 DuckDuckGo 路径跑 7 天，记录每次调用的 query、结果数、是否占位**。没有这个基线，后面所有额度决策、fallback 阈值、SearXNG 必要性都是猜。量化先行，替换其次——先知道自己病多重，再选药。
