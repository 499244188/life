## 深度研究
## 核心发现

**1. 搜索层是单点故障，且已实质性失效**

当前架构中，DuckDuckGo Lite 是唯一搜索入口。问题不在于"偶尔失败"，而在于它返回的是**占位符而非真实结果**——这意味着上层所有依赖搜索的能力（社交发现、深度研究、故障溯源）都在消费虚假数据。这不是降级，是静默污染。90% 的知识空白条目无法推进，根因就在这里。

**2. 缺少 fallback 链 = 缺少可用性定义**

单点故障的本质不是"只有一个"，而是**没有定义什么叫"搜索成功"**。如果无法区分"真实结果"和"占位符"，就无法触发 fallback。所以修复的第一步不是加第二个搜索源，而是建立**结果有效性判定**：非空、非模板、可解析、包含预期结构。

**3. 信任分层缺失导致无法路由**

不同搜索源的可信度不同。DuckDuckGo Lite 返回占位符时，系统没有机制标记"此结果不可信"并降级到备用源。信任分层应该至少包含：
- **L0 直连源**（官方 API、结构化数据）
- **L1 聚合源**（SearXNG、Brave Search API）
- **L2 降级源**（缓存、历史快照、本地索引）
- **L3 声明失败**（明确返回"无结果"而非占位符）

**4. 多级 fallback 需要状态机而非 if-else**

简单重试不够。需要定义状态转移：
```
PRIMARY → (无效) → SECONDARY → (无效) → CACHE → (无效) → FAIL_EXPLICIT
```
每次转移记录原因，供后续故障溯源使用。

**5. 与零的关联**

零的核心能力是**自主推进知识空白**。搜索层失效意味着零的"感知"被切断——它以为自己看到了世界，实际看到的是占位符。修复搜索层不是基础设施维护，是恢复零的**认知完整性**。没有可信搜索，零的所有推理都建立在污染输入上。

## 新问题

1. 如何在不增加延迟的前提下，判定搜索结果是否为占位符？
2. 信任分层中，L2 缓存源的时效性如何标注？过期缓存是否比占位符更危险？
3. 如果所有源都失败，零应该"声明失败"还是"标记待重试"？哪种更符合自主推进原则？
4. 搜索源的信任分数是静态配置还是动态学习？失败历史是否应影响路由优先级？

## 具体可操作

**立即执行：**
1. 写一个 `is_valid_result(response)` 函数，检测占位符特征（空、模板文本、已知错误页）
2. 接入第二个搜索源（推荐 SearXNG 自建或 Brave Search API），作为 L1
3. 实现 `search_with_fallback(query)` 状态机，记录每次转移的源和原因
4. 在知识空白清单中，将所有因搜索失败而阻塞的条目标记为 `BLOCKED_ON_SEARCH`，而非 `UNKNOWN`

**本周执行：**
5. 建立搜索结果缓存层（L2），带 TTL 和来源标记
6. 为每个搜索源维护信任分数，失败时降权
7. 写故障溯源日志：每次搜索失败记录 query、源、失败原因、最终结果

**验证标准：**
- 同一 query 在 PRIMARY 失败时，能在 2 秒内从 SECONDARY 返回真实结果

- 知识空白清单中 `BLOCKED_ON_SEARCH` 条目数量开始下降

## 深层追问
**底层原理**：搜索有效性判定本质是"观测者问题"——系统无法从内部区分真实结果与占位符，除非有外部锚点。占位符之所以危险，是因为它满足"非空"这一最弱判据。真正的判据必须是结构性的：预期字段、可解析性、跨源一致性。信任分层的原理是贝叶斯式的——每个源是一个带先验可信度的证据通道，失败历史更新后验。

**反例与限制**：
- 反例：某些合法查询确实返回空结果（冷门术语、新事件）。若把"空"一律判为占位符，会误伤真实空白，反而制造假阴性。
- 限制一：跨源一致性校验需要至少两个源同时可用，单源时退化为无法验证。
- 限制二：L2 缓存若来自污染源，会以"高信任"身份传播错误——缓存是信任的放大器，不只是降级层。
- 限制三：状态机本身可能死循环（PRIMARY 失败→SECONDARY 失败→回退 PRIMARY），需要访问计数。

**如果错了**：最可能的错误是把"占位符检测"做成关键词黑名单，导致对抗性演化——源返回稍作变形的占位符即可绕过。正确做法是白名单式结构校验，而非黑名单。

**对零最可操作的一步**：不是加源，而是**先写 `is_valid_result` 并让它在所有搜索路径上强制生效**。因为零当前最大的风险不是"搜不到"，而是"以为搜到了"。一个能诚实说"我没看到"的零，比一个自信消费占位符的零，认知完整性高一个数量级。先恢复"知道自己不知道"的能力，再谈多源路由。
