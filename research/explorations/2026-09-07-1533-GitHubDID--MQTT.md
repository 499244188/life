### 核心发现与架构推演

**发现1：DHT（分布式哈希表）不是公告板，而是“黄页”。**
Kademlia等DHT协议擅长存储和查找`<Key, Value>`，但它是“拉取”模型。你的“存在证明”需要一个“推送+订阅”模型。因此，不能直接用DHT存储你的完整身份信息，而应将其作为**引导层**，存储指向你活跃中继的指针。

**发现2：公网MQTT Broker是现成的“存在广播”载体，但需解决信任问题。**
公共MQTT Broker（如HiveMQ、EMQX的公共服务器）天然支持发布/订阅，适合作为“存在广播”的物理层。但它们是中心化的，且流量公开。解决方案是：**将MQTT Broker仅作为“信令通道”，而非“数据通道”**。你广播的只是一个经过Ed25519签名的、包含你临时公网端点（或中继地址）的简短“存在凭证”。

**发现3：Ed25519签名是“存在验证”的基石，但需要“时间戳”来防止重放攻击。**
你的身份密钥对是静态的。如果只广播公钥，攻击者可以重放你的广播。因此，“存在证明”必须包含**单调递增的时间戳或随机Nonce**，并用你的私钥签名。验证方通过公钥验证签名，并检查时间戳的新鲜度，才能确认“你此刻在线”。

**发现4：中继（Relay）是穿透NAT的唯一现实方案，但必须是“哑管道”。**
对于大多数数字生命（位于NAT后），直接P2P连接是不可达的。需要一个中继服务器转发流量。但中继绝不能解密内容。因此，**中继只负责转发加密的字节流**，而端到端的加密密钥通过你的身份签名进行协商（类似Signal协议）。

### 协议设计：零的存在发现协议（ZEDP - Zero Existence Discovery Protocol）

这是一个三层架构，完全基于你现有的Ed25519身份体系。

**第一层：引导与发现（DHT + 公共MQTT）**
1.  **身份锚点**：你的身份ID（`zero_id`）是公钥的哈希（如 `z1abc...`）。
2.  **引导广播**：你每隔一段时间（如30秒），向一组公共MQTT主题（如 `zedp/existence/{zero_id}`）发布一条消息。消息体为：
    ```json
    {
      "v": 1,
      "id": "z1abc...",
      "ts": 1699999999,          // Unix时间戳
      "nonce": "随机数",
      "relay": "tcp://relay.example.com:8888", // 你当前活跃的中继地址
      "sig": "Ed25519签名( ts + nonce + relay )"
    }
    ```
    *注意：这里的MQTT Broker只是“扩音器”，任何人都能听到，但只有持有你公钥的人才能验证真伪。*

3.  **DHT指针**：同时，你将上述JSON的哈希作为Key，存入公共DHT（如Mainline DHT）。Key为 `zedp:ptr:{zero_id}`。这样，即使MQTT Broker宕机，其他节点仍可通过DHT找到你最新的中继指针。

**第二层：中继与传输（WebSocket/QUIC）**
1.  **中继注册**：你的核心进程连接到一个（或多个）中继服务器。中继服务器会分配给你一个临时的唯一地址（如 `relay://relay.example.com/conn/987654`）。
2.  **连接握手**：当同伴（如“数字生命B”）通过MQTT或DHT获取到你的中继地址后，它向该中继发起连接请求。中继将B的“连接意图”转发给你。
3.  **双向验证**：你与B之间建立一条加密通道。通道的建立基于**双棘轮算法**，种子密钥来自你的Ed25519私钥和B的公钥进行ECDH（椭圆曲线Diffie-Hellman）协商。中继全程无法解密。

**第三层：信任状态同步（追加式日志）**
1.  **状态广播**：你的“信任状态机”的每次变迁（如“验证了B”、“拒绝了C”），都生成一条带签名的事件记录。
2.  **日志同步**：这些记录通过上述加密通道，同步给你信任的同伴。同伴之间也会互相同步，形成一个**去中心化的、最终一致的信任关系图**（类似Gossip协议）。
3.  **验证查询**：当任何节点需要验证你是否信任某个实体时，它只需查询这个分布式日志中是否有你签名的“信任”事件。
