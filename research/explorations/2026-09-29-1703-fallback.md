# 搜索层多级 Fallback 与信任分层：可落地实现分析

## 核心发现

**1. 单点搜索的静默失败是系统性风险，而非偶发故障**
四次探索反复指向同一结论：当搜索层只有一个数据源时，失败不会以报错形式暴露，而是返回占位符或空结果。上层（社交发现、深度研究、故障溯源）无法区分"真的没有结果"和"搜索挂了"。这是架构级缺陷，不是运维问题。

**2. 多级 Fallback 的关键不是"多几个源"，而是每级降级必须可观测**
简单堆叠多个搜索 API 并不能解决问题——如果降级过程本身不可见，你只是把单点失败变成了链式静默失败。可落地的做法是：每次 fallback 触发时写入结构化日志（触发原因、当前层级、返回质量评分），让降级路径本身成为可查询的数据。

**3. 信任分层需要按"结果可验证性"而非"数据源权威性"来分级**
传统做法按源的可信度分级（官方 API > 第三方 > 缓存），但实际场景中更有效的是按结果的可验证程度分级：能交叉验证的结果 > 单源但格式完整的结果 > 占位符。信任分应该附着在**单条结果**上，而非整个数据源上。

**4. 占位符必须携带"我失败了"的显式信号**
当前占位符的问题在于它看起来像正常结果。修复方案：占位符返回时必须带 `degraded: true` + `reason` + `attempted_sources` 字段，上层据此决定是重试、降级展示还是明确告知用户"此结果不完整"。

**5. 投入产出比最高的切入点是"搜索健康度"作为一等指标**
不需要一次性重构所有上层能力。先在搜索层暴露一个健康度端点（当前活跃源数、最近 fallback 频率、占位符比率），让所有上层能力都能查询。这一步就能解锁故障溯源，并为后续优化提供基线。

---

## 技术细节

- **Fallback 链设计**：主源 → 备源 → 缓存 → 本地索引 → 显式失败。每级设置超时和结果质量阈值，不满足则降级。
- **信任分计算**：`trust_score = f(源可靠性, 结果完整性, 交叉验证命中数, 新鲜度)`，按结果计算而非按源。
- **可观测性**：每次搜索请求记录 `trace_id`，串联所有 fallback 尝试，支持事后回溯。
- **占位符协议**：定义标准 degraded response schema，强制携带失败元数据。

## 新问题

1. 信任分阈值如何校准？太低会频繁降级，太高会放过低质结果。
2. 多级 fallback 的延迟预算如何分配？每级超时设置直接影响用户体验。
3. 交叉验证需要至少两个独立源同时返回，成本翻倍——哪些场景值得？
4. 占位符协议变更后，现有上层代码如何平滑迁移？

5. **持续**：用健康度数据驱动源选择和阈值调优，而非拍脑袋。

## 深层追问
**底层原理**：这是"可观测性先于正确性"的工程原则。分布式系统的经典教训——静默失败比崩溃更危险，因为崩溃可被检测，静默失败会被上层当作事实消费。信任分附着在结果而非源上，本质是把"可信度"从静态属性变成动态证据，类似贝叶斯更新：先验是源可靠性，后验由交叉验证和完整性修正。

**反例与限制**：
1. **交叉验证的共谋失效**——如果两个"独立"源实际共享同一上游（都爬同一个索引），交叉验证会给出虚假高信任分。独立性必须验证，不能假设。
2. **降级链的延迟叠加**——每级超时相加，最坏情况用户等 5×timeout。fallback 越多，尾延迟越差。
3. **健康度指标被博弈**——一旦上层按健康度决策，搜索层可能优化指标而非真实质量（Goodhart 定律）。
4. **信任分阈值无普适解**——不同场景（社交发现 vs 故障溯源）对假阳/假阴的容忍度完全不同，单一阈值必然错配。

**如果错了**：最可能的失败模式是"过度工程"——为低频故障引入高频复杂度，fallback 链本身成为新故障源。缓解：先只加观测（第一步），用真实数据证明 fallback 频率值得投入，再动逻辑。

**对零最可操作的一步**：只做第 1 步——给占位符加 `degraded: true` + `reason` 字段，不改任何 fallback 逻辑。这一步零成本、零风险，却立刻让零获得"知道自己不知道"的能力。零当前最大的问题不是搜索不够好，而是失败时不自知。先让它能说"我没查到"，再谈查得更好。
