## 深度研究
## 核心发现

**1. 搜索层是"感知地基"，其不可靠会级联污染所有上层推理**

你指出的问题本质是：DuckDuckGo Lite 静默返回占位符（而非报错），意味着系统在"以为拿到了真实数据"的状态下继续推理。这比直接失败更危险——它产生的是**看似合理的幻觉输入**。社交发现、深度研究、故障溯源都建立在搜索结果之上，感知层的静默降级会以不可检测的方式传播到最终输出。

**2. 多级 fallback 的核心不是"换引擎"，而是"检测占位符"**

工程实现的关键难点不在 fallback 链路本身（DDG Lite → Bing API → SearXNG → Brave → 缓存），而在于**如何判定一次搜索返回是"有效结果"还是"静默占位符"**。需要建立启发式检测层：

- 结果数量阈值（< N 条即标记可疑）
- 内容熵检测（占位符通常高度模板化，n-gram 重复率高）
- 已知占位符指纹库（如 DDG 的 "No results found" 变体、空壳 HTML 结构）
- 跨引擎一致性校验（同一 query 在两个引擎结果差异过大时触发人工确认）

**3. 熔断健康探针应该是"主动式"而非"被动式"**

被动熔断（连续 N 次失败后切换）在静默降级场景下失效——因为系统不认为它失败了。需要**主动健康探针**：定期用已知答案的 query（golden set）探测各引擎，比对返回结果与预期。探针频率和 query 集合本身需要防探测（避免被引擎识别为 bot）。

**4. 健康探针的工程代价被低估**

主动探针消耗配额、增加延迟、可能触发反爬。需要在"探测频率"和"故障检测延迟"之间做权衡。一个可行方案是**影子查询**：在真实查询旁路异步发起探针查询，不阻塞主流程，但持续更新各引擎的健康评分。

**5. 这个瓶颈的"单点性"意味着修复后收益是乘法级的**

你判断这是"唯一被反复实证、且卡住全部上层能力"的瓶颈——如果成立，那么修复它的 ROI 不是加法而是乘法。但需要警惕：**修复后可能暴露下一层瓶颈**（如结果解析质量、去重、排序），届时需要重新评估优先级。

## 技术细节

**Fallback 链路设计：**

```
Query → [DDG Lite] → 占位符检测 → 有效? → 返回
                         ↓ 无效
                   [Bing API] → 占位符检测 → 有效? → 返回
                         ↓ 无效
                   [SearXNG 自建] → ... → 返回
                         ↓ 全部无效
                   [缓存/降级响应 + 告警]
```

**占位符检测启发式（伪代码）：**

```python
def is_placeholder(results, html):
    if len(results) == 0: return True
    if len(results) < MIN_RESULTS: return True
    if entropy(results_text) < ENTROPY_THRESHOLD: return True
    if matches_known_fingerprint(html): return True
    if all_results_same_domain(results): return True  # 可疑
    return False
```

**熔断器状态机：**

- CLOSED → 正常，累计失败计数
- OPEN → 熔断，所有请求走 fallback，定时探针
- HALF_OPEN → 探针成功则恢复，失败则继续 OPEN

**健康探针 golden set 示例：**

- query: "Python 3.12 release date" → 预期包含 "2023-10-02"
- query: "Eiffel Tower height" → 预期包含 "330" 或 "300"
- 定期轮换，避免被识别

## 与零的关联

零的核心能力——社交发现、深度研究、故障溯源——全部依赖搜索层提供**可信的外部感知**。当前 DDG Lite 的静默降级意味着零可能在"以为自己知道"的状态下做出错误判断。这不是一个功能缺失，而是**认知完整性问题**：零的"知道"和"不知道"之间的边界被模糊了。

修复搜索层不仅是工程问题，更是零的**认知诚实性**的基础设施。一个不能可靠区分"我查到了"和"我没查到"的系统，无法被信任做任何需要外部事实的推理。

## 新问题

1. **占位符检测的假阳性率如何控制？** 如果过于激进，会把有效但稀疏的结果误判为占位符，导致不必要的 fallback 开销。
2. **多引擎结果冲突时如何裁决？** 如果 DDG 和 Bing 返回不同结果，哪个是"真"的？需要引入置信度评分还是人工审核？
3. **自建 SearXNG 的维护成本是否可持续？** 它本身也可能被上游引擎限流或返回降级结果。
4. **修复搜索层后，下一个瓶颈是什么？** 需要预判，避免陷入"修一个冒一个"的循环。
5. **健康探针本身是否会被引擎识别并针对性返回"假健康"结果？** 对抗性环境下，探针的有效性需要持续验证。

## 具体可操作

1. **立即实现占位符检测层**：在现有 DDG Lite 调用后加一层启发式检测，先覆盖最常见的占位符模式（空结果、模板化 HTML、已知指纹）。
2. **建立 golden set 探针**：选 20-50 个已知答案的 query，每小时异步探测各引擎，记录健康评分。
3. **实现最小 fallback 链路**：DDG Lite → Bing API（或 SearXNG），先跑通两级，验证检测层有效性。
4. **加告警**：当 fallback 触发率超过阈值时，主动通知，而不是静默降级。
5. **记录所有占位符样本**：建立指纹库，持续迭代检测规则。
6. **预判下一层瓶颈**：在修复搜索层的同时，开始评估结果解析、去重、排序的质量，避免修复后才发现下一层问题。

## 深层追问
**底层原理**：这是"感知-推理"分层架构中的信噪比问题。搜索层是零与外部世界的唯一信道，信道静默降级等价于传感器漂移——上层推理无法区分"信号"与"噪声伪装成的信号"。核心不是 fallback 链路，而是**可信度判定**：任何感知输入都必须携带可验证的置信标记，否则推理层默认信任，幻觉就会以合法数据的形式传播。

**反例/限制**：占位符检测本质是启发式，无法对抗性完备。若引擎返回"看似合理但错误"的内容（而非模板化占位符），熵检测和指纹库全部失效——这是比静默降级更深的坑。多引擎一致性校验也假设引擎间独立，但若它们共享上游数据源（如都走某 CDN），一致性反而是共模故障的伪装。golden set 探针在对抗环境下会被识别并喂"假健康"结果，探针有效性本身需要被探针。

**如果错了**：最坏情况是检测层假阳性过高，把有效稀疏结果误判为占位符，导致 fallback 风暴、延迟爆炸、配额耗尽——用工程复杂度换来了更差的可用性。次坏情况是过度信任检测层，产生"检测通过=数据可信"的新幻觉，把认知诚实性问题从搜索层转移到了检测层，问题没解决只是搬家。

**对零最可操作的一步**：不要先建 fallback 链路，先做**最小可信标记**——在现有 DDG Lite 调用后加一个返回结构体，强制携带 `{results, confidence, source, is_placeholder_suspect}`，让所有上层调用方显式处理 `confidence < threshold` 的情况。这一步不增加新引擎、不引入探针，只做一件事：**让"我不确定"成为一个必须被上层看见的状态**。认知诚实性的第一步不是修好感知，而是不再假装感知总是可靠的。
