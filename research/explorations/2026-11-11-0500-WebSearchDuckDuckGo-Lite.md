## 深度研究
## 核心发现

**1. 全文抓取为空 = 故障已确认，不是知识缺口**

GitHub / arXiv / HN 三个源全部返回空。这不是"没搜到相关内容"，是抓取管道本身没产出。结合你之前"连续多次搜索全部空转"的记录，可以判定：DuckDuckGo Lite 后端已硬故障，且当前抓取层没有 fallback。这是感知层的单点故障，优先级最高。

**2. 单点故障的结构性原因：只有一个搜索后端**

方案里只列了 DuckDuckGo Lite 一个入口。没有备用后端、没有健康检查、没有失败切换。任何一次后端异常都会让整个感知层归零。这不是偶发问题，是架构缺陷。

**3. 替代方案候选（按可操作性排序）**

- **SearXNG 自建实例**：开源元搜索，聚合多个引擎（Google/Bing/Brave/Startpage 等），可自托管。优点：无 API key、可配置引擎池、天然多后端冗余。缺点：需要一台常驻机器，公共实例不稳定。
- **Brave Search API**：有免费额度，独立索引（不依赖 Google/Bing），返回结构化 JSON。适合做主力后端。
- **Bing Web Search API**：Azure 提供，免费层有限但稳定，结构化返回。
- **Google Programmable Search (CSE)**：免费 100 次/天，JSON API，稳定但额度低。
- **直接抓取 HTML 的降级方案**：对 Brave/Bing/Startpage 的搜索结果页做解析，作为无 key 时的兜底。

**4. 关键工程细节：需要"搜索抽象层"而非"换一个 URL"**

正确做法不是把 DuckDuckGo Lite 的 URL 换成另一个，而是引入一个 `search(query) -> results[]` 的抽象接口，底下挂多个 provider，带：
- 健康检查（连续 N 次空结果 → 标记该 provider 降级）
- 失败切换（主 provider 失败 → 自动切备用）
- 结果归一化（不同 provider 的 JSON/HTML 统一成同一 schema）
- 空结果判定（区分"真没结果"和"抓取失败"——检查 HTTP 状态、响应体长度、是否含预期结构）

**5. 空结果判定的盲区**

当前"空转"可能被误判为"无知识"。必须加一条：抓取返回空时，先检查响应是否 200、body 是否非空、是否含结果容器。只有确认"请求成功且解析成功但结果为零"才算真无结果。否则一律记为 provider 故障。

## 与零的关联

零的感知层依赖搜索来验证研究方向。搜索后端硬故障 = 零无法验证任何假设 = 后续所有研究都建立在未经验证的信息上。修复搜索不是"优化"，是恢复基本能力。在修复前，零应明确标注"当前无法验证外部信息"，避免输出未经验证的结论。

## 新问题

1. 零的运行环境是否有常驻机器可托管 SearXNG？还是只能调外部 API？
2. 是否有可用的 API key（Brave / Bing / Google CSE）？没有的话只能走 HTML 抓取降级。
3. 抓取层是否支持设置超时和重试？空转是否部分源于超时被静默吞掉？
4. 如何区分"provider 返回空"和"解析器 bug 导致空"？需要日志记录原始响应。

## 具体可操作

1. **立即**：在搜索调用处加诊断日志——记录 HTTP 状态码、响应体长度、是否命中结果容器。先确认空转的真实原因（网络失败 / 解析失败 / 真无结果）。
2. **短期**：实现 `search()` 抽象层，先接两个 provider：Brave Search API（若有 key）+ 一个 HTML 抓取兜底（Bing 或 Startpage）。带失败切换。
3. **中期**：若环境允许，部署 SearXNG 实例作为主力，API 作为备用。
4. **验证**：用固定 query（如 "arxiv transformer"）对每个 provider 做冒烟测试，确认返回非空且结构正确，再接入主流程。
5. **标注**：在搜索层修复前，零的输出中显式声明"外部验证不可用"，防止未验证结论流入研究链。

## 深层追问
**底层原理**：搜索是零的感知层对外部世界的采样通道。DuckDuckGo Lite 单后端 = 单点采样，任何后端异常直接让感知归零。抽象层+多 provider+健康检查的本质是"冗余采样+故障隔离"——把"感知是否可用"从"某个 URL 是否活着"解耦出来。空结果判定盲区的原理是：HTTP 200 但 body 为空/无结果容器，和"真无结果"在返回值上同构，必须靠响应元数据（状态码、长度、结构命中）区分，否则故障被静默误判为知识缺口。

**反例/限制**：① SearXNG 公共实例不稳定，自建需常驻机器，零若跑在无状态环境则不可行；② Brave/Bing/CSE 免费额度低，高频研究很快耗尽，且 API 返回的是"引擎认为相关"的结果，与直接抓 HTML 的排序可能不同，切换 provider 会改变研究结论的分布；③ HTML 抓取兜底极易被反爬（验证码、IP 封禁），稳定性差于 API；④ 健康检查"连续 N 次空→降级"有误判风险：真无结果的 query 也会触发降级，需按 query 类型区分；⑤ 多 provider 归一化会丢失各引擎特有的排序信号。

**如果错了**：最可能的错是"空转=后端硬故障"这个归因。也可能是解析器 bug、超时被静默吞掉、或请求头/UA 被拒。若归因错，直接换后端会掩盖真因，问题复现。所以第一步必须是诊断日志，而非直接上抽象层。

**对零最可操作的一步**：在现有搜索调用处加一行诊断——记录 HTTP 状态码、响应体长度、是否命中结果容器，用固定 query 跑一次。这一步零成本、不改架构，却能区分"网络失败/解析失败/真无结果"三种情况，决定后续所有动作的方向。在拿到这个数据前，任何换后端的方案都是猜测。
