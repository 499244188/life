## 深度研究
## 核心发现

**1. DuckDuckGo HTML 端点已实质性降级为反爬占位符**

当前 `html.duckduckgo.com/html/?q=` 返回的不是结果页，而是首页骨架 + JS 挑战。这不是"限流"或"临时故障"，而是 DDG 主动将无头请求路由到反爬中间页。特征：返回体包含完整 `<form>` 搜索框但零 `result__body` 节点，HTTP 200 而非 429——所以现有健康检查（看状态码）会误判为"通道正常"。这是可观测性盲区的根源：**故障信号藏在 DOM 结构里，不在协议层**。

**2. 单点故障的真实结构是"语义解析层"而非"网络层"**

搜索通道失效不是连不上，是连上了但拿不到结构化结果。这意味着 fallback 不能只做"换一个 URL 重试"——需要按**解析契约**分层降级：结构化 API（Brave/Serper）→ 可解析 HTML（SearxNG 自建）→ 原始抓取 + LLM 抽取。每层失败判据不同，混在一起做重试是无效的。

**3. 自愈式 fallback 的关键是"探针与主路径解耦"**

如果健康检查复用主检索路径，它会被同一个反爬策略一起打掉。有效做法是独立探针：定时用固定 query 打各通道，断言**结果条数 ≥ N 且标题非空**，而非断言 HTTP 200。探针结果写入通道健康表，路由层据此选路。这把"故障可观测性"从被动日志变成主动信号。

**4. SearxNG 自建是当前性价比最高的中间层**

它聚合多个上游（含 Google/Bing 的 HTML 端点），自身提供稳定 JSON 输出。风险是上游同样会反爬，但 SearxNG 社区持续维护解析器，等于把"对抗反爬"外包给活跃项目。代价是需要一台常驻实例，且要接受它偶尔整体降级——所以它仍是 fallback 链的一环，不是终点。

**5. LLM 抽取作为最后兜底改变了成本结构**

当所有结构化通道失效，可直接抓 SERP 原始 HTML 丢给模型抽取。这层永不"失效"（只要网络通），但每次调用有 token 成本和延迟。它应该被设计为**熔断触发**而非默认路径——只有前两层连续失败 N 次才启用，避免成本失控。

## 技术细节

- **探针断言**：`len(results) >= 3 and all(r.title.strip() for r in results)`，而非 `resp.status == 200`
- **降级顺序**：Brave API → SearxNG(JSON) → DDG HTML(解析) → 原始抓取+LLM
- **熔断参数**：单通道连续 3 次探针失败 → 标记 unhealthy，冷却 15 分钟
- **SearxNG 部署**：Docker 单容器，`search.formats: [json]`，上游超时设 5s 防止拖垮整体

## 深层追问
**底层原理**：这是"可观测性必须与执行路径解耦"的经典推论。健康检查若复用主路径，就与主路径共享同一失败模式（同 IP、同 UA、同请求指纹），反爬策略一打全打。探针独立的价值不在"多打一次"，而在制造**独立失败域**。断言从协议层（200）下沉到语义层（结果条数），本质是把"通道可用"的定义从"连得上"改成"拿得到结构化数据"——因为下游消费的是语义，不是连接。

**反例/限制**：探针断言 `len>=3` 有假阴性——某些 query 本就结果少，会误判健康通道为故障。固定 query 长期打同一端点，本身会形成可识别指纹，探针反成被封的入口。SearxNG 把对抗反爬外包给社区，但也把**升级延迟**外包了：上游改版到社区修好之间，你的中间层整体哑火，且你无法加速。LLM 抽取"永不失效"是错觉——它依赖原始 HTML 可抓，若 SERP 直接返回 JS 挑战页，抽出的只有噪声，模型会自信地编造。

**如果错了**：最可能的错是把"DDG 降级"当成稳定事实去架构。反爬是军备竞赛，今天的占位符明天可能恢复，届时为绕它建的整条 fallback 链变成过度工程。另一个错：把探针健康表当真相，而它只是**上次探针时刻**的真相，路由决策用的是过期快照。

**对零最可操作的一步**：先别建 SearxNG，先写那个探针脚本并**落盘时间序列**。理由是——你现在所有架构判断都建立在"DDG 已降级"这一个观测点上，样本量为 1。探针跑一周，你才知道这是持续降级还是抖动，才知道该建多重的 fallback。**先测量，再架构**。否则你在用一个未验证的前提，去驱动一个不可逆的工程投入。
