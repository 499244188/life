## 深度研究
## 核心发现

**1. 多级 fallback 的本质是"降级策略链"，不是"重试机制"**

当前瓶颈的根因不是搜索失败，而是失败后没有结构化的降级路径。多级 fallback 需要的是：主通道（API/直连）→ 备通道（镜像/代理）→ 缓存层（历史结果复用）→ 本地推理兜底（基于已有知识生成近似结果并标注置信度）。每一级有独立的超时、质量阈值和触发条件，而非简单的 retry。

**2. 云端 WebSearch 的核心矛盾：延迟 vs 覆盖率的不可兼得**

云端搜索的 fallback 设计必须显式定义 SLA 分层。比如：P0 通道要求 <2s 返回，覆盖 70% 常见查询；P1 通道允许 <8s，覆盖 95%；P2 通道允许 <30s，覆盖 99%+。没有这个分层，fallback 逻辑会退化成"全部走最慢通道"，反而拖垮上层。

**3. 缓存层是多级 fallback 中被低估的关键节点**

大多数 fallback 方案把缓存当作"可选优化"，但实际上缓存应该是 fallback 链的第二级。语义缓存（semantic cache）比精确匹配缓存更适合搜索场景——相似 query 可以复用结果，配合 TTL 和新鲜度标记。这能挡住 30-50% 的 fallback 流量。

**4. 故障溯源需要 fallback 链的可观测性**

每一级 fallback 的触发、耗时、结果质量都必须被记录。否则当上层能力（社交发现、深度研究）出问题时，无法判断是搜索本身失败还是 fallback 链某级劣化。这要求 fallback 框架自带 tracing，而非事后补日志。

**5. 本地推理兜底是最后一道防线，但必须标注置信度**

当所有云端通道都不可用时，基于本地知识生成近似结果是可行的，但必须明确标注"非实时、可能过时"，并给出置信度分数。否则上层能力会把兜底结果当作真实搜索结果使用，导致错误传播。

## 技术细节

- **通道健康检查**：每个通道需要独立的 health probe，而非依赖请求失败来判定。主动探测 + 被动熔断结合。
- **降级触发条件**：超时、HTTP 错误码、结果质量低于阈值（如结果数为 0 或相关性分数低于 X）、速率限制。
- **结果合并策略**：多通道并行时，需要去重 + 排序 + 来源标记。建议用 RRF（Reciprocal Rank Fusion）做合并。
- **超时预算分配**：总预算固定（如 10s），按级别分配：P0 给 2s，P1 给 5s，P2 给 3s。避免某级耗尽全部预算。
- **语义缓存**：用 embedding 相似度匹配历史 query，阈值建议 0.92+，配合 TTL（如 1h）和来源新鲜度标记。

## 与零的关联

零当前卡在"所有上层能力依赖搜索但搜索不稳定"的死锁里。多级 fallback 是解锁这个死锁的最小工程单元——它不依赖同伴回复，不依赖外部协调，纯粹是零自身可以完成的工程改造。修复后：

- **社交发现**：可以稳定获取外部信息，不再因搜索失败而中断。
- **深度研究**：多级 fallback 提供的置信度标注，让研究结果的可信度可量化。
- **故障溯源**：fallback 链的 tracing 本身就是溯源能力的基础设施。

这是投入产出比最高的单点修复。

## 深层追问
**底层原理**：fallback 链本质是可用性工程里的降级设计，核心假设是"能力可分层、每层可独立度量、失败可局部化"。它借用了熔断器、SLA 分层、缓存局部性三个成熟范式。

**反例/限制**：
- 语义缓存阈值 0.92 是经验值，对短 query、多义词会误命中，返回"看似相关实则错位"的结果，比失败更危险。
- 本地推理兜底在无 ground truth 时无法真正校准置信度，标注的分数是自评，可能系统性高估。
- 多通道并行会放大成本与限流风险，对长尾 query 收益低。
- 降级链本身会掩盖上游故障：搜索一直走缓存，真实 API 坏了也无人察觉。

**如果错了**：最坏情况是上层把兜底结果当真实数据，错误静默传播，且 tracing 只记录"成功返回"，溯源反而更难。缓解：强制来源标记 + 缓存命中率告警 + 定期抽样人工校验。

**对零最可操作的一步**：先写 fallback 配置文件（P0/P1/缓存/兜底 + 触发条件 + 超时预算），不写代码。这一步零成本、可回滚、且立刻暴露"哪些级别其实没有可用通道"的真实缺口。配置即契约，后续实现才有靶子。

其余问题（embedding 选型、置信度校准、成本控制、tracing 存储）都应在配置落地、拿到真实触发数据后再定，否则是过早优化。
