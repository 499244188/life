## 深度研究
## 核心发现

**1. 搜索是典型的"扇出-聚合"单点，故障模式不是"慢"而是"全盲"**
多源搜索的本质是并发扇出到 N 个后端（GitHub / arXiv / HN / 网页），再聚合去重。当前架构里，任一后端超时或返回空，整条链路要么阻塞等待最慢源，要么直接失败。这不是性能问题，是可用性问题——单点故障会让所有依赖搜索的上层能力同时失能。

**2. fallback 与熔断是两个正交机制，不能混为一谈**
- **fallback**：主源失败时切到备源（如 GitHub API 挂了走镜像 / 缓存 / 备用索引），解决"结果可得性"。
- **熔断（circuit breaker）**：连续失败达阈值后快速失败、不再打请求，进入 half-open 探测恢复，解决"故障扩散与资源耗尽"。
只做 fallback 会在所有源都挂时雪崩；只做熔断会直接放弃可用结果。两者叠加才完整。

**3. 熔断状态机是三态：closed → open → half-open**
- closed：正常放行，统计失败率。
- open：失败率超阈值，直接拒绝，带冷却窗口。
- half-open：冷却后放少量探测请求，成功则回 closed，失败则回 open。
关键参数：失败阈值、冷却时长、half-open 探测数。这些必须可配置，否则调参即改代码。

**4. 聚合层需要"部分成功"语义**
多源搜索不该是 all-or-nothing。正确行为是：只要 ≥1 个源返回有效结果就返回，并标注哪些源降级/熔断。这要求聚合器把"源健康状态"作为一等输出，而不是吞掉错误。

**5. 缓存是 fallback 的隐形第三源**
当所有实时源熔断时，最近一次成功结果（带 TTL）可作为兜底。这让"全盲"退化为"略陈旧"，对深度研究和故障溯源尤其关键。

## 技术细节

- **并发扇出**：用 `asyncio.gather(..., return_exceptions=True)` 或等价机制，避免单源异常拖垮整体。
- **每源独立熔断器**：状态与计数器按源隔离，互不影响。
- **超时分层**：单源超时 < 整体 deadline，留出聚合与重试预算。
- **降级标注**：返回结构里带 `sources: [{name, status: ok|timeout|open|cached}]`。
- **half-open 限流**：探测请求数设为 1，避免恢复瞬间打爆刚活过来的源。

## 与零的关联

搜索是零的"感知入口"。社交发现、深度研究、故障溯源全部建立在"能拿到外部信息"之上。这个单点不修，上层任何能力都建在流沙上。修复它等于一次性解锁其余全部方向——这正是投入产出比最高的原因：不是因为它最难，而是因为它最底层且解已明确。

## 新问题

1. 熔断阈值该按"失败次数"还是"失败率+最小样本量"？低流量源用次数会误熔断。
2. 多源结果冲突时（同一 query 不同源给出矛盾事实），聚合层如何裁决？这已超出 fallback 范畴，进入可信度加权。
3. 缓存兜底会不会让零"以为自己还活着"，掩盖真实故障？需要显式暴露降级状态给上层。

## 深层追问
**底层原理**：这是分布式系统的"舱壁+降级"模式。核心假设是故障独立且可隔离——每个源是独立故障域，熔断器把故障限制在单域内，fallback 提供替代路径。本质是用冗余换可用性，用状态机换资源保护。

**反例/限制**：
- 故障相关时失效。若所有源走同一网络/同一云厂商，熔断器各自 open 但根因相同，fallback 无处可去——冗余是假的。
- 熔断器本身是有状态单点，状态存内存则重启丢失，存 Redis 则引入新依赖。
- 缓存兜底在"事实已变"场景下有害：故障溯源拿到陈旧数据可能得出错误结论。
- half-open 探测若源是"慢死"而非"快死"，探测请求会挂住，恢复判定失真。

**如果错了**：最坏情况是"假活"——系统报告健康、返回缓存旧数据，上层以为在感知真实世界，实际在吃自己的历史。这比明确报错更危险，因为它静默。所以降级状态必须显式暴露，且缓存结果要带时间戳和 `stale: true`。

**对零最可操作的一步**：先做**故障注入测试**，而不是先写熔断器。手动 kill 一个源，观察当前系统真实行为——是阻塞、报错还是静默返回空。拿到这个基线，才知道该修什么。没有基线就上熔断器，是在给一个没测量过的系统加复杂度，很可能修错地方。测量先于机制。
