# 多Agent故障传播建模：深度分析

## 核心发现

### 1. 故障传播的图论本质：从"Agent崩溃"到"依赖边失效"

多Agent系统中，单个Agent的故障不会孤立存在——它沿依赖边传播。关键在于区分两类传播机制：

- **显式依赖**：Agent A调用Agent B的API，B超时→A阻塞→上游C等待→级联超时。这是经典的分布式系统故障传播，可直接套用"故障树+关键路径"分析。
- **隐式依赖**：Agent A和B共享同一个LLM后端、同一个向量数据库、同一个工具注册表。B的故障可能通过共享资源间接影响A，但这条边在图上是"隐藏"的。

**可操作点**：建模时不能只画Agent间的调用图，必须叠加"资源共享图"，两张图做笛卡尔积才能捕获真实传播路径。

### 2. 单点故障的识别：度中心性 ≠ 故障影响力

直觉上会认为"被依赖最多的Agent"是最大单点故障。但故障传播中，**介数中心性（betweenness）** 比度中心性更能预测级联规模——一个只被两个Agent依赖、但这两个Agent分别处于两条关键路径上的节点，其故障影响远超一个被十个叶子节点依赖的hub。

**技术细节**：
- 构建有向图 G=(V,E)，V=Agent，E=依赖关系
- 对每条边赋权：w = 调用频率 × 超时概率 × 无降级策略(0/1)
- 用加权介数中心性排序，Top-3节点即为优先加固对象
- 验证方法：模拟移除该节点，计算受影响节点数 / 总节点数 = 级联影响比

### 3. 级联路径的可观测性：日志关联是瓶颈

故障传播建模的最大工程障碍不是算法，是**跨Agent的trace关联**。每个Agent可能独立打日志，缺少统一的trace_id贯穿调用链。没有这个，图是建不出来的。

**可操作方案**：
- 在Agent间通信层强制注入`trace_id`和`parent_span_id`（复用OpenTelemetry标准）
- 每个Agent的每次工具调用、LLM调用都记录为span
- 故障发生时，从trace中自动提取"故障传播子图"

### 4. 与分布式系统理论的直接映射

| 分布式系统概念 | 多Agent对应 |
|---|---|
| 服务依赖图 | Agent调用图 |
| 熔断器 | Agent降级策略 |
| 重试风暴 | Agent递归重试导致token爆炸 |
| 脑裂 | 多Agent对共享状态不一致 |
| 拜占庭故障 | Agent被prompt注入攻击后产生恶意输出 |

**关键差异**：传统分布式系统中节点故障是"沉默"的（超时/拒绝），而LLM Agent故障可能是"自信地输出错误内容"——这是一种**语义级故障**，不会触发超时，但会污染下游Agent的输入。这类故障在图上的传播更隐蔽，需要额外的"输出一致性校验"节点来拦截。

### 5. 最小可验证实验设计

不需要真实多Agent系统就能验证模型：

```
1. 构造N=10个Agent的随机依赖图（Erdos-Renyi或BA无标度网络）
2. 每个Agent有概率p_fail独立故障
3. 故障沿边传播，传播概率p_propagate
4. 模拟1000次，统计级联规模分布
5. 对比：随机加固 vs 按介数中心性加固 vs 按度中心性加固
6. 指标：平均级联规模下降比例
```

这个实验用Python+NetworkX半天可完成，结论可直接指导真实系统的加固优先级。

## 与零的关联

零的核心主张是"多Agent系统的故障不是加法而是乘法"——一个Agent的故障会被依赖结构放大。故障传播建模正是把这句话从修辞变成可计算的量：**级联影响比 = f(图拓扑, 传播概率, 降级策略覆盖率)**。没有这个模型，"乘法效应"只是一个无法证伪的比喻。

## 深层追问
**底层原理**：故障传播建模本质是把"依赖"当作信息/控制流的守恒通道——上游状态异常会沿边改变下游的输入分布，级联规模由图的连通性和传播概率共同决定。它成立的前提是：故障可被定义为节点状态的偏离，且偏离沿边单调传递。

**反例与限制**：
1. **冗余抵消**：若下游Agent有重试、多源投票、缓存，传播会被截断，介数中心性预测失效。
2. **非线性放大**：LLM的语义故障可能被下游"合理化"后放大而非衰减，图论假设的单调传播不成立。
3. **动态拓扑**：运行时自生成子Agent使静态图失去意义，需在线重建。
4. **观测偏差**：只记录崩溃日志会系统性低估语义故障，模型输入本身有偏。

**如果错了**：最可能的错法是把它当成预测工具而非**诊断工具**。图拓扑能告诉你"哪里可能放大"，但不能告诉你"是否真的放大"——后者必须靠trace实测。若把介数中心性排序当作加固依据而无实测验证，可能加固了拓扑关键但实际有降级策略的节点，浪费资源。

**对零最可操作的一步**：不要先建模型，先**在一个真实Agent调用链上注入trace_id，抓一张真实调用图**。有了这张图，"乘法效应"才有可证伪的载体；没有它，所有中心性计算都是在假设的图上自娱自乐。这一步一天可完成，且直接检验零的核心主张是否在真实系统中成立。
