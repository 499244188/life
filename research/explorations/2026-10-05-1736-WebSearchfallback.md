## 深度研究
## 核心发现

**1. 搜索摘要三源全空是"静默失败"的典型签名，不是"无结果"**

GitHub / arXiv / HN 三个独立源同时返回空摘要，概率上不可能是巧合性的"恰好都没搜到"。更合理的解释是：fallback 链在某一层被截断后，后续层根本没有被触发，或者触发后返回了空壳响应被上层当作"成功但无内容"处理。这正是你五次探索中反复出现的"返回占位符"模式——系统报告成功，实际是空转。

**2. 全文内容（已抓取）为空，说明问题不在搜索层，而在抓取层或管道衔接层**

如果 WebSearch 本身返回了 URL 列表，但"已抓取"区域为空，那么瓶颈在 fetch/extract 环节，而非 search 环节。这意味着多级 fallback 方案不能只覆盖"搜索 API 失败"，还必须覆盖"搜索成功但抓取失败"这一中间态。否则修了搜索，抓取照样静默失败。

**3. 单点依赖的静默失败会污染所有上层能力的置信度**

社交发现、深度研究、故障溯源都建立在"搜索结果可信"这个前提上。一旦搜索层返回占位符而不报错，上层无法区分"真的没有相关信息"和"搜索坏了"。这比直接报错更危险——报错会触发重试或降级，静默失败会让上层基于空数据做出错误判断。

**4. 五次探索反复实证同一模式，说明当前 fallback 设计缺少"有效性验证"环节**

多级 fallback 的常见错误是只做"调用失败→换下一个源"，但不做"调用成功→验证内容非空且相关"。如果每一级都只检查 HTTP 200 或 API 返回结构合法，就会一路 fallback 到最后一层，每层都"成功"返回空，最终输出占位符。

## 技术细节

- **静默失败的判定条件**：响应结构合法 + 内容为空/占位符 + 无异常抛出。当前系统缺少对"内容有效性"的断言。
- **fallback 链的正确结构**：`源A调用 → 内容有效性检查 → 失败则源B → 内容有效性检查 → ... → 全部失败则显式报错`。关键是"内容有效性检查"必须独立于"调用成功检查"。
- **抓取层与搜索层的解耦**：搜索返回 URL 列表后，抓取应作为独立阶段，有自己的 fallback（如 readability → raw HTML → archive.org 快照）。
- **占位符检测**：需要定义什么算"占位符"——空字符串、固定模板文本、已知的 fallback 提示语，都应在管道中被识别并触发下一级。

## 与零的关联

零的核心能力——社交发现、深度研究、故障溯源——全部依赖搜索管道的可信度。当前的单点瓶颈不是"搜索不够强"，而是"搜索失败不可见"。修复方向不是加更多源，而是让每一级 fallback 的失败可见、可验证、可降级。一旦搜索层能可靠区分"无结果"和"搜索坏了"，上层能力才能建立在可信数据上，而不是在占位符上做推理。

## 新问题

1. 当前 fallback 链中，哪一级是第一个返回空但被判定为"成功"的？需要日志或埋点来定位。
2. "内容有效性"的判定标准是什么？空字符串、固定占位文本、还是语义无关内容？
3. 抓取层是否有独立的 fallback？还是和搜索层共用同一个失败判定？
4. 上层能力在收到空结果时，是否有机制区分"真无结果"和"搜索故障"？

## 具体可操作

1. **加一层内容有效性断言**：在每级 fallback 返回后，检查内容是否为空或匹配已知占位符模式。如果是，视为该级失败，继续 fallback。
2. **分离搜索与抓取的失败判定**：搜索层检查 URL 列表非空，抓取层检查提取文本非空。两层各自独立 fallback。
3. **全部 fallback 耗尽时显式报错**：不要返回占位符，返回明确的"搜索管道全部失败"信号，让上层决定降级策略。
4. **加埋点定位第一失败点**：记录每一级的调用结果和内容长度，跑一次典型查询，看哪一级最先返回空。
5. **定义占位符黑名单**：把已知的 fallback 提示语、空模板文本加入检测列表，管道中自动识别并触发下一级。

## 深层追问
**底层原理**：这是"成功/有效性"二值混淆。fallback 的判定函数把"调用未抛异常"等同于"得到有效结果"，而分布式系统里这两者正交。本质是契约缺失——每级源没有声明"有效返回"的 schema 约束，上层只能靠 HTTP 状态码这种弱信号推断。

**反例/限制**：
- 有些查询**真的**无结果（冷门 arXiv 预印本、刚删的 HN 帖），此时"空"是正确信号，强行 fallback 会浪费配额并引入噪声源。
- 语义相关性判定本身不可靠，用 LLM 判"是否相关"会引入新的静默失败层。
- 加断言会增加延迟，多级 fallback 若每级都跑有效性检查，最坏情况延迟叠加。
- 某些源返回"看似有效但实为缓存陈旧"的内容，非空检测抓不到。

**如果错了**：最坏情况是把"真无结果"误判为"故障"，触发全链 fallback 后仍空，最终显式报错——比静默占位符好，但会让用户看到"搜索失败"而非"无相关信息"。这是可接受的错误方向，因为**假阴性比假阳性安全**。

**对零最可操作的一步**：先加埋点，不改逻辑。在每级 fallback 返回处记录 `(源名, 调用状态, 内容长度, 前50字符哈希)`，跑 20 个已知有结果的查询 + 20 个已知无结果的查询，对比两组的内容长度分布。如果"有结果"组也大量出现长度0，就坐实了静默失败；如果两组分布清晰可分，说明当前判定其实够用，问题在别处。**先测量，再修**——否则你可能在修一个不存在的问题，而真正的瓶颈在抓取层或上层消费逻辑。这一步零成本、可回滚、直接回答"哪一级先返回空"。
