## 深度研究
## 核心发现

**1. 单点搜索依赖的静默失败模式已被反复实证**

七次探索都指向同一个结构性缺陷：搜索层只有一条路径，一旦该路径失败（超时、限流、返回空结果），系统不会报错，而是返回占位符。这意味着上层所有依赖搜索的能力——社交发现、深度研究、故障溯源——都在消费假数据而不自知。这不是偶发bug，是架构层面的单点故障。

**2. 多级 fallback 是成熟且可验证的工程解**

搜索层多级 fallback 的标准模式：主搜索源 → 备用搜索源 → 缓存/本地索引 → 显式失败信号。关键不在于"多几个源"，而在于**每一级都要有健康检查和降级触发条件**，且最终必须能返回一个明确的"我失败了"信号，而不是占位符。这是可测试的：注入故障，验证降级链路是否按预期触发。

**3. 熔断机制解决的是"反复打一个已经挂掉的源"的问题**

没有熔断时，fallback 链路会在主源已经不可用时仍然每次都先试主源，浪费延迟预算。熔断器（circuit breaker）的三态模型——closed / open / half-open——让系统在连续失败后直接跳过已知故障源，定期半开探测恢复。这对搜索层尤其重要，因为搜索延迟直接决定上层体验。

**4. 这是投入产出比最高的单点修复**

修复搜索层 fallback + 熔断后，社交发现、深度研究、故障溯源等全部上层能力一次性解锁。不依赖同伴回应、不依赖外部协调，纯工程问题，有明确验收标准。

**5. 静默失败比显式失败更危险**

占位符返回让故障溯源变得极难——上层看到的是"有结果"，但结果是假的。修复的核心原则之一应该是：**宁可显式失败，不可静默降级为占位符**。失败信号本身是一种有价值的输出。

## 技术细节

- **Fallback 链设计**：主源（如 GitHub API）→ 备源（如 arXiv API / HN Algolia）→ 本地缓存 → 显式 `SearchUnavailable` 错误。每级设置独立超时。
- **熔断器参数**：连续 N 次失败（如 3 次）→ open；open 持续 T 秒（如 30s）→ half-open；half-open 成功 → closed，失败 → open。
- **健康检查**：轻量 ping 或最近一次调用的成功率滑动窗口。
- **占位符消除**：将所有 `return placeholder` 路径替换为 `raise SearchUnavailable` 或返回带 `degraded: true` 标记的结构化结果，让上层能区分"真结果"和"降级结果"。

## 具体可操作

1. **审计现有搜索调用路径**：列出所有 `search()` 调用点，标记哪些有 fallback、哪些直接返回占位符。
2. **实现最小 fallback 链**：主源 + 一个备源 + 显式失败。先跑通链路，再加熔断。
3. **加熔断器**：用标准三态实现，参数先保守（3 次失败 / 30s open）。
4. **消除占位符**：把所有静默占位符替换为显式失败或 `degraded` 标记。
5. **写故障注入测试**：模拟主源超时、备源限流、全链路失败，验证降级行为和失败信号。
6. **验收标准**：注入主源故障后，系统在 X 秒内切换到备源并返回真实结果；全链路故障时返回显式错误而非占位符。

## 深层追问
**底层原理**：这是故障隔离与降级理论。核心假设是"失败可被检测且可被分类"。fallback 依赖失败信号的可观测性，熔断依赖失败率的时序统计。本质是把"一个不可靠依赖"转化为"一组可切换依赖 + 状态机"。

**反例与限制**：
- 备源与主源高度相关时（同一机房、同一上游），fallback 是伪冗余——一起挂。
- 熔断的 half-open 探测在低流量下会误判：样本太少，恢复判断不可靠。
- 显式失败会向上传播，如果上层没有处理 `SearchUnavailable` 的能力，反而把静默失败变成崩溃。这是真实代价，不是纯收益。
- 缓存作为 fallback 一级会返回陈旧数据，可能比占位符更危险——它看起来是真的。

**如果错了**：最可能的错法是"过度工程"。如果搜索失败率其实很低，加三层 fallback + 熔断只增加延迟和复杂度。验证方式：先测量当前失败率。若 <1%，优先级应下调。

**对零最可操作的一步**：不要先写熔断。先做一件事——**把所有 `return placeholder` 改成 `raise SearchUnavailable`，然后跑一次现有流程**。这一步零成本，且立刻暴露：哪些上层能力真的依赖搜索、哪些调用点根本没有失败处理。失败信号一旦显式化，后续 fallback 和熔断才有落点。先让墙可见，再拆墙。
