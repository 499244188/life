## 核心发现

**1. 全文抓取为空，这本身就是最强的诊断信号。**
三组查询（社交发现、深度研究、故障溯源）的检索结果全部为空，且已被两次独立验证排除"信息真空"的可能。现在连"全文内容（已抓取）"字段也是空的——这不是巧合，而是同一条管道故障的第三次显影。**空结果不是"没找到"，而是"根本没发出请求"或"请求在返回前被吞掉"。** 这直接支持你的判断：搜索后端是单点瓶颈，而非查询构造问题。

**2. 故障形态指向"静默失败"而非"显式报错"。**
如果后端返回 4xx/5xx，你的管道大概率会记录错误；现在呈现的是"空壳"——请求看似完成、返回空集。这类故障的典型成因有三类：
- 熔断器/限流器处于打开状态但未上报（静默短路）；
- 上游 API 返回 200 但 body 为空（配额耗尽、key 失效、区域封锁的常见表现）；
- 解析层把非预期响应结构（如 HTML 错误页）解析成空列表，吞掉了异常。

**3. 多源 fallback 的价值不在"更多源"，而在"故障可区分"。**
Brave/Tavily/SerpAPI/Exa 四源并存的真正收益是：当单源静默失败时，其余源的结果差异会让故障**可见**。单源时"空=不知道"；多源时"三源有、一源空=该源故障"，故障从不可观测变为可观测。这是修复单点的核心机制，而非冗余备份。

**4. 空壳页检测必须前置到解析层之前。**
"200 但空 body"和"200 但 body 是错误页"是两类不同故障，检测点应放在 HTTP 响应落地后、解析前：检查 content-length、关键字段存在性、以及已知错误页特征（如 "rate limit"、"quota"、"captcha" 关键词）。否则解析层会把错误页静默转成空列表，重演当前故障。

**5. 健康探针要能自举验证——这正是你提到的"自举验证后续查询"。**
探针不应只 ping 端点，而应发一条**已知有确定答案的查询**（如某个稳定存在的 GitHub repo 名），断言返回非空且包含预期 token。这样探针本身就能区分"端点活着但功能死了"和"真活着"。

## 技术细节

- **熔断器状态机**：closed → (连续 N 次空/错) → open（短路，直接走 fallback）→ half-open（放一条探针查询）→ 成功则 closed，失败则回 open。关键参数：N 建议 3，open 冷却 30–60s，half-open 只放 1 条。
- **空结果判定**：不能只判 `len(results)==0`，要区分 `empty_valid`（查询确实无结果，如极冷门长尾词）与 `empty_suspect`（同源历史命中率高的查询突然空）。用"该源近期命中率"做基线，偏离阈值即判 suspect。
- **fallback 顺序**：按源的历史成功率动态排序，而非固定顺序；失败源降权但不移除，half-open 时重新参与。
- **探针查询集**：3–5 条固定查询，覆盖不同内容类型（代码、论文、新闻），每条带预期 token 断言。

## 与零的关联

零当前卡住的三条上层能力——社交发现、深度研究、故障溯源——共享同一个检索入口。修复这个单点不是"修一个功能"，而是**解除一个横跨所有能力的结构性阻塞**。更关键的是：零的"自举验证"能力依赖搜索能返回可断言的结果；搜索修好后，零才能用自己的检索去验证自己的修复，形成闭环。这是投入产出比最高的原因——它同时是**被修的对象**和**验证修复的工具**。

## 新问题

1. 当前空结果到底是"熔断器已打开但未上报"，还是"上游 200 空 body"？两者修复路径不同（前者查状态机日志，后者查配额/key/区域）。**需要先拿到一次带 HTTP 状态码和 body 长度的原始日志**，否则多源方案可能修错层。
2. 解析层是否已有"错误页→空列表"的静默转换？如果有，这是故障被隐藏的直接原因，必须先拆掉这个转换再谈多源。
3. 探针查询集由谁维护？如果探针本身也走同一条故障管道，它会跟着一起静默失败——探针必须走独立路径或至少独立记录。

## 具体可操作

1. **今天**：在检索入口加一行原始日志（URL、状态码、body 长度、解析后条数），跑一次三组查询，拿到故障的真实形态。这是所有后续决策的前提。
2. **拆静默转换**：找到解析层把非预期响应转成空列表的代码，改为抛异常或标记 `empty_suspect`，让故障可见。
3. **接第二源**：先只加 Tavily（接入成本最低），实现"双源差异告警"——两源结果差异超阈值即报警。这一步就能让单点故障从不可观测变可观测。
4. **加熔断器**：按上述状态机实现，N=3，冷却 45s，half-open 放 1 条探针。
5. **建探针集**：3 条固定查询 + 预期 token 断言，独立于主管道记录，每日跑一次。
6. **自举验证**：修复后用零自己发一条"已知有答案"的查询，断言非空——这是修复完成的验收标准，也是零自举能力的第一次真实使用。

## 深层追问
**底层原理**：本质是把"不可观测的单点故障"转为"可观测的差异信号"。单源搜索的失败模式是信息坍缩——空结果既可能是真无结果，也可能是管道故障，二者不可区分。多源 fallback 的价值不在冗余，而在提供参照系：多源结果差异使故障从"沉默"变为"可断言"。熔断器则是把"每次请求都赌后端活着"改为"用状态机显式管理信任"，避免故障期间持续无效请求放大延迟。

**反例/限制**：① 多源并非真独立——若四源共享同一上游（如都走某聚合层）或同一网络出口，故障会共模，差异告警失效。② 空结果基线判定在冷启动或查询分布突变时会误报。③ 熔断器 half-open 探针若走同一故障管道，会自我确认失败，永远开不回来。④ 双源差异告警在长尾查询上噪声大，可能淹没真故障。⑤ 最根本的限制：这套机制只能让故障**可见**，不能修复上游配额/key/区域封锁——可观测性不等于可用性。

**如果错了**：最可能的错法是"修错层"——把上游 200 空 body 误判为熔断器静默短路，于是调状态机参数，而真因是 key 失效，结果多源全部空、告警全响、根因仍在。防御手段就是先拿原始日志（状态码+body 长度），用证据定位层，而非用假设定位层。

**对零最可操作的一步**：今天只做一件事——在检索入口加原始日志（URL、状态码、body 长度、解析后条数），跑一次三组查询。这一步零成本、不改架构、不引入新依赖，却能一次性回答"熔断器打开 vs 上游空 body"这个分叉问题。在拿到这条日志前，任何多源或熔断实现都是在猜层。**先让故障说话，再决定修哪里。**
