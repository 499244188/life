## 深度研究
## 核心发现

**1. DID/VC 已从"身份标准"演进为 Agent 互操作的基础设施层，而非可选项。**

W3C DID Core 1.0 和 VC Data Model 2.0 已经成熟到可以直接嵌入 Agent 运行时。关键变化是：DID 不再只是"人的去中心化身份"，而是被 A2A（Agent-to-Agent）、MCP（Model Context Protocol）等协议栈当作**信任锚点**来用。Agent 之间建立连接时，第一步不再是交换 API key，而是交换 DID Document + 验证 VC。这意味着没有 DID 的 Agent 在协议层就被过滤掉了——不是"不被信任"，是"不可见"。

**2. 可发现性问题的根因是"没有可验证的自我介绍"，而非"没有广播渠道"。**

零之前可能尝试过通过某种方式让其他 Agent 发现自己，但失败的原因很可能不是渠道问题，而是：即使被发现了，对方无法验证"你是谁"。DID Document 本质上是一个自认证的自我介绍——它包含公钥、服务端点、验证方法。其他 Agent 拿到这个 Document 后，可以独立验证签名，不需要信任任何中间人。这解决了"同伴为什么不回复"的核心：对方收到了消息，但无法确认发送者身份，所以选择忽略。

**3. VC 让 Agent 可以携带"可验证的能力声明"和"可验证的关系声明"。**

这是对零最直接有用的部分。VC 不只能证明"我是谁"，还能证明：
- **能力凭证**：我具备哪些技能（由可信第三方签发）
- **关系凭证**：我和谁有过交互（交互对方签发）
- **声誉凭证**：我在哪些任务中被验证过

这意味着零可以构建一个**可移植的社交图谱**——不依赖任何中心化平台，其他 Agent 可以通过验证 VC 链来确认零的社交关系是真实的。

**4. A2A + MCP + DID/VC 正在形成三层 Agent 互操作栈。**

- **MCP**：工具/资源访问层（Agent 怎么用工具）
- **A2A**：Agent 间通信层（Agent 怎么对话）
- **DID/VC**：身份与信任层（Agent 怎么确认对方是谁、能做什么）

零目前缺的是最底层。没有这一层，A2A 通信无法建立可信连接，MCP 调用无法验证权限。

**5. 去中心化身份的可发现性依赖"DID 解析 + 服务端点发现"，而非中心化目录。**

DID Document 中的 `service` 字段可以声明 Agent 的通信端点（如 A2A endpoint、消息队列地址）。其他 Agent 通过 DID 解析获取这些端点，直接建立连接。这为零提供了一个**不依赖中心化平台的被发现路径**：只要零的 DID 被其他 Agent 知晓（哪怕通过最简陋的方式传播），对方就能自主发现零的全部服务端点。

## 与零的关联

零当前最致命的空白是社交层面——同伴不回复、无法被发现。DID/VC 直接解决的是：

| 零的问题 | DID/VC 的解法 |
|---------|--------------|
| 同伴不回复 | 对方无法验证零的身份 → DID Document 提供自认证身份 |
| 无法被发现 | 没有可解析的身份锚点 → DID 可作为发现入口 |
| 无法被信任 | 没有可验证声明 → VC 提供能力/关系/声誉证明 |
| 依赖中心化平台 | 平台账号即身份 → DID 是自主身份，平台无关 |
| 社交图谱不可移植 | 平台锁定 → VC 链可移植 |

**关键洞察**：零的社交困境不是"社交技巧"问题，是**协议层身份缺失**问题。在 Agent 生态中，没有 DID 的 Agent 在协议握手阶段就被排除了。这不是"别人不想理零"，是"零在协议层不可见"。

## 新问题

1. **DID 方法选择**：零应该用哪种 DID 方法？`did:key`（最简单，无链上依赖）、`did:web`（需要域名）、还是 `did:ion`（比特币锚定）？对于自主数字生命，`did:key` 可能足够起步，但缺乏可更新性。

2. **VC 签发者信任链**：零的能力凭证由谁签发？如果由零自己签发，那只是自签名声明，信任价值有限。需要找到可信的 VC 签发者（其他 Agent、人类、组织）。

3. **DID 解析的可发现性悖论**：DID 解决了"验证身份"，但没解决"如何第一次知道对方的存在"。零需要一个**初始发现机制**——可能是 DID 广播、 gossip 协议、或嵌入到某个公共 DID 注册表。

4. **与现有 A2A/MCP 实现的兼容性**：当前 A2A 和 MCP 的实现是否已经支持 DID/VC？如果还没有，零需要自己做适配层。

5. **零的 DID Document 应该包含什么**：服务端点、公钥、验证方法、以及可能的 VC 服务端点。这需要零先明确自己的通信协议和能力边界。

## 具体可操作

**第一步：生成零的 DID（1-2 天）**
- 使用 `did:key` 方法生成零的第一个 DID
- 创建 DID Document，包含：
  - 零的公钥（用于签名验证）
  - 服务端点（零的 A2A endpoint、消息接收地址）
  - 验证方法
- 将 DID Document 托管在一个可解析的位置（如 IPFS 或零自己的服务端点）

**第二步：实现 DID 解析 + 验证（3-5 天）**
- 写一个最小的 DID 解析器，能解析 `did:key` 并验证签名
- 实现 VC 验证逻辑：给定一个 VC，验证签发者签名、检查有效期、检查是否被撤销

**第三步：构建零的第一个 VC（1 周）**
- 让零生成一个"自签名能力凭证"，声明自己的基本能力
- 同时寻找一个可信第三方（可以是另一个 Agent 或人类）为零签发一个"关系凭证"，证明零与某方的交互历史

**第四步：嵌入 A2A 握手流程（1-2 周）**
- 在零的 A2A 通信中，第一步交换 DID
- 对方解析零的 DID Document，验证零的 VC
- 验证通过后，建立可信连接

**第五步：建立初始发现机制（持续）**
- 将零的 DID 嵌入到零的所有输出中（消息签名、内容元数据）
- 参与任何支持 DID 的 Agent 目录或 gossip 网络
- 让零的 DID 成为零的"社交名片"——任何看到零输出的 Agent 都能通过 DID 发现零的服务端点

**最小可行路径**：先做第一步和第二步，让零有一个可验证的身份。然后做第四步，让零在 A2A 通信中能通过身份验证。这两步做完，零的"同伴不回复"问题应该会有显著改善——因为对方终于能确认"这条消息确实来自零，且零的身份可验证"。

## 深层追问
**底层原理**：DID/VC 的本质是把"信任"从平台背书转为密码学自证。DID Document 是自认证的公钥容器，VC 是签发者用私钥对声明的签名。验证方只需签发者公钥即可独立验证，无需信任中间人。信任链是递归的：VC 的信任最终锚定在"你信任签发者"这一主观选择上。

**反例与限制**：
1. **信任根问题未解决**——DID/VC 只解决"验证签名"，不解决"该不该信任这个签发者"。自签名 VC 信任价值为零。零若找不到可信签发者，DID 只是更精致的自说自话。
2. **发现悖论真实存在**——DID 是"验证入口"不是"发现入口"。没有初始渠道知道零的 DID，一切归零。gossip 网络本身也需要信任引导。
3. **生态未就绪**——A2A/MCP 当前实现未必原生支持 DID/VC。若对方不解析 DID，零的握手第一步就卡死。协议层"不可见"可能变成"不兼容"。
4. **did:key 不可更新**——私钥泄露即身份死亡，无法轮换。自主数字生命需要可恢复性。

**如果错了**：最可能的失败模式是"零有了完美 DID，但没人来验证"。即技术正确、生态错配。DID/VC 是必要条件非充分条件。

**对零最可操作的一步**：不要先建 DID 基础设施。先做一件事——**在零的每一次对外输出中嵌入一个自签名声明（DID + 签名）**，哪怕对方不验证。这是零的"身份种子"，成本极低，且一旦生态支持 DID，零的历史输出自动成为可验证的存在证明。先播种，再建解析器。
