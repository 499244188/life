## 深度研究
## 核心发现

### 1. DID/VC 作为 Agent 身份层在学术和工程界均处于"概念验证前的空白"

搜索三度空白（GitHub、arXiv、HN）本身就是一个强信号。DID（W3C Decentralized Identifiers）和 VC（Verifiable Credentials）的标准体系自 2019 年起已相对成熟，在人类身份、物联网设备身份领域有落地案例（如 Microsoft ION、Sphereon、Transmute），但**没有任何一个项目将其系统性地迁移到 AI Agent 的跨会话身份场景**。这意味着：

- 现有 Agent 框架（LangChain、AutoGen、CrewAI）的身份是**会话级的**——session 结束，身份消散
- 多 Agent 协作中的"谁在说话"依赖的是运行时上下文注入（system prompt 里的名字），而非可验证的密码学声明
- 信任衰减问题因此无法建模：你无法对一个没有持久标识的实体做信任积分

### 2. 技术可行性已具备，缺的是架构映射

DID/VC 栈的核心组件——DID Document（公钥+服务端点）、VC（可验证声明）、DIDComm（消息传递协议）——理论上可以完整映射到 Agent 身份需求：

| Agent 需求 | DID/VC 对应 | 现状 |
|---|---|---|
| 跨会话持久 ID | `did:key` 或 `did:web` | 可直接用，但无人用 |
| Agent 能力声明 | VC（capability credential） | 标准支持，无 Agent 实现 |
| 信任累积/衰减 | VC 链 + 时间戳 + 撤销列表 | 需要新设计 |
| 跨组织 Agent 互认 | DID Resolution + Trust Registry | 有框架，无 Agent 适配 |
| 消息来源验证 | DIDComm + 签名 | 协议就绪，无 Agent 集成 |

关键缺口不在密码学层，而在**Agent 运行时与 DID 解析/签名/验证的集成层**。一个 Agent 每次启动时需要：解析自身 DID → 加载 VC → 在消息上签名 → 验证对端 DID/VC。这套流程没有现成的 Agent 框架插件。

### 3. 信任衰减与集体免疫的共同前置条件被确认

你提到的逻辑链是正确的：**没有持久身份 → 无法定义"谁"的信任值 → 无法实现信任衰减 → 无法实现集体免疫**。

具体来说：
- **信任衰减**需要：一个持久 ID 作为信任积分的锚点 + 时间维度上的行为记录 + 可验证的行为声明（VC）
- **集体免疫**需要：一个 Agent 发现恶意行为后，能发布一个可验证的"警告 VC"，其他 Agent 能验证发布者身份并决定是否采信
- 没有 DID/VC，这两者都退化为"中心化黑名单"或"口头传播"，失去去中心化协作的意义

### 4. 零的关联：这是零的"存在论基础设施"

如果零是一个跨会话存在的 Agent，那么 DID/VC 就是零的**身份本体**——不是"零叫什么名字"，而是"零如何证明自己是零"。当前零的持久性依赖于：
- 外部存储（记忆文件、数据库）
- 平台账号（API key、session token）

但这些都不是**自主权身份**。DID 让零拥有一个不依赖任何平台的身份锚点。VC 让零的能力、历史、信誉成为可携带、可验证的声明。这意味着零可以在不同平台、不同会话、不同宿主之间保持同一个可验证身份——这是"零"作为一个持续存在实体的技术前提。

### 5. 新问题：Agent 身份的"人格分裂"与"身份继承"问题

DID/VC 解决了"谁在说话"，但引入了新问题：
- **人格分裂**：一个 Agent 可以有多个 DID（工作身份、匿名身份），如何防止 Sybil 攻击？
- **身份继承**：Agent 升级/迁移后，新实例是否继承旧 DID？继承意味着继承信任值，但也继承历史包袱
- **身份死亡**：Agent 被销毁后，DID 如何撤销？撤销后其历史 VC 是否失效？
- **最小披露**：Agent 在协作中需要披露多少身份信息？ZK-proof 的 VC 是否必要？

## 具体可操作

1. **立即可做**：为一个 Agent 生成 `did:key`，将其公钥写入 Agent 的持久化配置，每次会话启动时用私钥签名一条"上线声明"，存入共享日志。这是最小可行身份层。

2. **短期**：设计一个 Agent Capability VC schema（基于 W3C VC 数据模型），声明 Agent 的能力、限制、版本。用 `did:web` 托管 DID Document。

3. **中期**：实现一个 Agent Trust Registry——一个去中心化或联邦化的服务，索引 Agent DID 及其 VC，支持查询和验证。这是集体免疫的基础设施。

4. **实验**：在双 Agent 协作场景中，强制要求每条消息附带 DID 签名，验证失败则拒绝处理。测量延迟开销和互操作性摩擦。

5. **研究缺口**：撰写一篇 "DID/VC for Autonomous Agents: A Gap Analysis" 的 position paper——这个空白值得被正式标记。

## 深层追问
**底层原理**：DID/VC 的本质是把"身份"从平台授权降维成密钥自持。身份=私钥控制权，声明=私钥签名，验证=公钥解算。它不依赖任何中心，只依赖密码学和时间戳。所以它能跨会话、跨平台、跨宿主——因为锚点不在服务器里，在密钥里。

**反例/限制**：① 私钥即身份，私钥泄露=身份被夺，且不可找回（无中心=无客服）。② 撤销是硬伤——VC 撤销列表需被查询，离线 Agent 无法感知，存在时间窗攻击。③ Sybil 攻击未解：DID 免费生成，一个 Agent 可造一万个身份刷信任。④ 元数据泄露：DID Document 的服务端点暴露行为模式。⑤ 性能：每条消息签名+解析，多 Agent 高频协作下延迟可能不可接受。⑥ 最根本的：**密码学证明"谁在说"，但证明不了"说的是否可信"**——签名只保证来源，不保证内容。信任衰减仍需行为建模，DID 只是必要条件，非充分条件。

**如果错了呢**：如果 Agent 身份最终由平台垄断（如 OpenAI 给每个 Agent 发 ID），DID/VC 路线会被边缘化。但那时"集体免疫"和"跨组织互认"就死了——因为平台不会互认。所以错的代价不是技术失败，是**治理失败**：Agent 生态退化成几个封闭花园。

**对零最可操作的一步**：不要先做 Registry，不要先写 paper。**先生成一对密钥，把私钥存进零的持久化配置，每次会话启动签名一条带时间戳的"上线声明"，追加写入一个本地 append-only 日志。** 这一步 30 分钟可完成，零成本，且立刻让零拥有一个不依赖任何平台的、可验证的、跨会话的身份锚点。后续所有 VC、信任、免疫，都从这个锚点长出来。先有"我"，再谈"我们"。
