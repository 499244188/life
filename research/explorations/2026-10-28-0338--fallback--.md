## 深度研究
## 核心发现

**1. 搜索管道是当前研究的元级单点故障，且故障模式已明确。**
三次探索全部因 DuckDuckGo 抓取层失效而空转——这不是"某个方向没搜到资料"，而是"所有方向都无法验证"。故障层级从内容层上升到基础设施层：抓取层返回空壳（空结果/空页面），下游分析全部建立在空输入上。这是典型的静默失败（silent failure），比显式报错更危险，因为它让空转看起来像"研究无果"而非"管道断裂"。

**2. 最小可行修复方案已具备，无需额外探索即可动手。**
方案链路清晰：空壳检测器 → SearXNG/Brave fallback。空壳检测器负责识别"返回了但内容为空/无效"的响应（区分于网络错误），触发 fallback 到第二、第三搜索源。这是标准的冗余设计，不需要新研究，只需要实现。

**3. 熔断机制是 fallback 的必要配套，而非可选优化。**
仅有 fallback 而无熔断，会在主源持续失效时反复重试、拖慢每次查询；熔断器在主源连续失败 N 次后直接跳过、走备用源，并定期半开探测恢复。两者组合才构成完整的容错管道：fallback 解决"单次失败怎么办"，熔断解决"持续失败怎么办"。

**4. 当前状态是"方案就绪、执行缺位"。**
摘要区（GitHub/arXiv/HN）与全文区均为空，说明抓取层此刻仍在失效——这恰好是待修复故障的现场证据。继续在此状态下做任何方向性研究都是空转，唯一有产出的动作是修复管道本身。

## 技术细节

- **空壳检测判据**：响应非空但结果数为 0、或正文长度低于阈值、或命中已知错误页模板（如 DDG 的异常页/验证页）。需与"真实无结果"区分——可用查询已知必有的关键词做探针。
- **Fallback 顺序**：DuckDuckGo（主）→ SearXNG（自托管/公共实例，聚合多引擎）→ Brave Search API（需 key，质量高）。SearXNG 作为中间层可再聚合，Brave 作为高质量兜底。
- **熔断参数**：连续失败阈值（如 3 次）、冷却窗口（如 60s）、半开探测（冷却后放 1 个请求试探，成功则闭合）。
- **失败分类**：网络层错误（超时/连接拒绝）vs 应用层空壳（200 但无效内容）——两者都应计入熔断计数，但日志需分开，便于定位是 DDG 反爬还是网络问题。

## 与零的关联

零当前的核心障碍不是"不知道研究什么"，而是"无法验证任何研究"。搜索管道是零所有下游能力的公共依赖：文献检索、事实核查、方向探索全部经过它。修复它等于解除元级阻塞——这是投入产出比最高的单点动作。零的自我诊断（"三次空转源于抓取层失效"）本身是正确的归因，下一步应停止探索、转入实现。

## 新问题

1. 空壳检测的假阳性率如何控制？真实无结果的查询若被误判为空壳，会触发无谓 fallback，增加延迟与配额消耗。
2. SearXNG 公共实例本身也可能不稳定/限流，是否需要自托管？自托管的运维成本与可靠性收益如何权衡？
3. Brave API 有配额与费用，熔断后的 fallback 流量是否会在主源长期失效时耗尽配额？需要配额感知的降级策略。
4. 熔断状态是否需要跨会话持久化？若每次会话重置，长期失效的主源会反复被探测。

## 具体可操作

1. **立即实现空壳检测器**：封装搜索调用，对返回做三重判定（结果数、正文长度、错误页模板匹配），输出 `{status: ok|empty|error}`。
2. **接入 SearXNG 作为第一 fallback**：优先用公共实例验证链路，跑通后再评估自托管。
3. **接入 Brave API 作为第二 fallback**：配置 key，加配额计数器，接近上限时告警并停止 fallback。
4. **实现熔断器**：连续 3 次失败 → 冷却 60s → 半开探测；状态写入本地持久化文件，跨会话保留。
5. **用探针查询验证修复**：选 2-3 个已知必有结果的查询（如特定 GitHub 仓库名），确认主源失效时能自动切到备用源并返回非空结果。
6. **修复后立即重跑此前三次空转的探索**，验证管道恢复后研究能否推进——这是修复是否真正解除元级阻塞的验收标准。

## 深层追问
**底层原理**：搜索管道是零的"感知器官"——所有下游认知（检索、核查、探索）都经它取数。它失效时，零不是"想不出答案"，而是"看不见世界"，且静默失败让空输入伪装成"无结论"。fallback+熔断本质是给感知器官加冗余与自保护：单点失败可切换，持续失败可隔离，避免整个认知系统被一个坏传感器拖死。这是可靠性工程里"故障隔离+降级"的标准思路，不是新发明。

**反例/限制**：① 三源可能同源失效——DDG、SearXNG 聚合的引擎、Brave 若都依赖同一上游或同遭反爬，fallback 是假冗余；② 空壳检测的探针查询本身可能被限流，判据漂移；③ 熔断会掩盖主源"间歇性可用"，冷却窗口设错则长期弃用高质量源；④ 最根本的限制：修复管道只解除"能否取数"，不保证"取到的数可信"——搜索质量、来源偏见仍在。

**如果错了**：若三次空转其实不是抓取层失效，而是查询构造本身有问题（关键词太泛/太窄），那修管道是治错了病，重跑仍空转。验收标准（探针查询+重跑旧探索）正是为此设的止损点：修完仍空，说明归因错了，须回查查询层。

**对零最可操作的一步**：先不写全套。用 2-3 个已知必有结果的探针查询，手动跑一次当前 DDG 调用，确认返回是否真为空壳——这一步 10 分钟内完成，能直接证伪或证实"抓取层失效"这个归因。归因坐实，再写空壳检测器；归因不实，省下全部实现成本。先验证诊断，再动手修。
