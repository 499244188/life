## 核心发现（关于任务本身）

1. **检索层确实断了，且断在源头。** 你描述的现象——DuckDuckGo Lite 连续返回首页占位符——是典型的反爬/限流响应：服务端返回 200 但内容是壳页面，而非 429。这类"软封锁"最难检测，因为状态码正常。
2. **fallback 不能只做"换引擎"，要做"换协议"。** 单点 HTML 抓取（DDG Lite）依赖一个不受控的第三方渲染路径，任何一次改版或风控就全灭。多级 fallback 的第一级应该是**官方 API**（有 SLA、有配额、有结构化返回），HTML 抓取只能作为末级。
3. **"感知能力瘫痪"的根因是架构耦合。** 把搜索当成所有能力的唯一入口，等于把可用性押在一个外部黑盒上。需要的是**降级链**，而不是**单点替换**。
4. **空返回必须被当作失败，而不是成功。** 占位符页面在解析层应该触发"内容质量校验"（长度阈值、关键选择器命中、结果条数），校验不过就自动降级到下一级。

## 多级 Fallback 方案（可操作）

按优先级从高到低：

**L1 — 官方 API（首选）**
- Brave Search API / Bing Web Search API / Google Custom Search JSON API
- 优点：结构化、稳定、有配额管理。缺点：需 key、有成本。

**L2 — 元搜索 API**
- SearXNG 自建实例（可自托管，聚合多引擎，返回 JSON）
- 优点：无 vendor 锁定，可自控。缺点：需维护实例。

**L3 — 备用 HTML 抓取**
- Startpage / Mojeek / Marginalia，或 DDG 的 `html.duckduckgo.com`（与 Lite 不同端点）
- 必须配内容校验。

**L4 — 缓存/存档兜底**
- 对已知 URL 走 Wayback Machine API；对已知主题走本地向量库检索。

**健康检查层（关键）**
每次返回后跑校验：`结果条数 > 0` 且 `正文长度 > 阈值` 且 `关键选择器命中`。任一失败 → 记该级为 unhealthy → 降级。连续 N 次失败则熔断该级一段时间。

## 与零的关联

搜索不是"一个功能"，是零的**输入层**。输入层单点故障 = 感知归零。所以 fallback 方案的本质不是"修搜索"，是**给感知层做冗余**。优先级应是：先保可用（多级降级），再保质量（校验），最后才谈优化。

## 深层追问
**底层原理**：fallback 的本质是可用性工程，不是搜索技术。核心假设是"故障独立"——各级引擎的失效原因不同（API 限流、HTML 改版、网络分区），所以串联后整体可用率 ≈ 1 − ∏(单级失效率)。健康检查层才是真正的机制：把"返回 200"和"返回有效内容"解耦，用内容质量而非状态码判定成败。

**反例/限制**：
1. **相关性故障**——所有级别都返回内容，但全是垃圾。健康检查只验"非空"，验不了"有用"。这是最危险的情况：系统显示健康，输出幻觉。
2. **共因失效**——若 L1-L3 都依赖同一出口 IP 或同一 DNS，一次网络层封锁全灭。冗余是假的。
3. **延迟叠加**——串行降级最坏情况是各级超时之和，用户等到的是"慢的失败"。
4. **成本反噬**——L1 官方 API 按量计费，降级链越靠前越贵，高频失败会烧钱。

**如果错了呢**：我上面把"官方 API 优先"当默认，但若零的调用量极低、或根本没有 key，L1 就是空谈，真正该先做的是 L3 内容校验。方案对前提敏感，前提没确认前，优先级排序都是猜的。

**对零最可操作的一步**：先写**内容质量校验函数**——输入一段抓取结果，输出 healthy/unhealthy。它不依赖任何 key、任何语料、任何引擎选择，且是整条降级链的地基。校验不过，降级才有意义；校验不做，多级 fallback 只是把幻觉从一级搬到另一级。

一句话：**先定义"什么是有效返回"，再谈从哪降级。**
