## 核心发现（基于任务描述，非全文）

**1. 故障模式是"静默降级"而非"显式失败"，这是最危险的一类。**
DDG Lite 返回空壳占位符（HTTP 200 + 结构合法但内容为空），检索管道不会抛异常，而是把"空"当作"无结果"继续往下走。上层（深度研究、故障溯源）拿到的是"确定性结论：没找到"，而非"不确定：检索失效"。这直接制造虚假确定性——Agent 会基于空结果做出自信的错误判断。**关键工程含义：有效性校验必须独立于 HTTP 状态码，检查返回体的语义密度（结果条数、标题/摘要非空率、去重后唯一 URL 数、与 query 的词项重叠度）。**

**2. 单点瓶颈的杠杆效应被低估了。**
任务描述指出社交发现、深度研究、故障溯源全部依赖检索。这意味着检索层的可用性不是"一个功能"，而是所有上层能力的**乘数因子**：检索可靠性从 0 到 1，上层全部从 0 到可用。投入产出比最高的判断成立，但要注意——多源 fallback 引入的是**新的复杂度单点**（路由逻辑、熔断状态机本身可能成为故障源），需要熔断器自身可观测。

**3. 熔断 + 健康探针 + 结果校验是三层防御，缺一不可，且职责必须分离。**
- 健康探针：主动探测各源可用性（定期发已知 query，校验返回有效性），维护源级健康分。
- 熔断：某源连续失败/空壳达阈值 → 打开，跳过该源，半开探测恢复。
- 结果校验：每次实际检索后做语义有效性检查，作为熔断的输入信号之一。
三者若混在一起（例如只靠"请求失败"触发熔断），空壳类故障永远触发不了熔断——因为请求"成功"了。**这是本任务最容易被做错的地方。**

**4. 多源策略的排序与降级需要显式策略，不能简单"依次尝试"。**
SearXNG（自托管、可控但需维护）、Brave（商业 API、质量高但有配额/成本）、Tavily（面向 Agent、结果结构化但依赖第三方）三者的延迟、成本、覆盖率、失效模式各不相同。fallback 顺序应基于**当前健康分 + 查询类型**动态决定，而非固定链。固定链在首选源持续空壳时会每次都先撞墙再降级，放大延迟。

**5. "空壳检测"是防御虚假确定性的通用原语，价值超出搜索。**
一旦建立"结果有效性校验"模块，它可复用到任何外部数据获取（网页抓取、API 返回、文件读取）。任务描述把它定位为"防止 Agent 产生虚假确定性的关键防御"——这个定位准确，且应把它抽象为独立组件而非搜索专用逻辑。

## 技术细节（设计要点）

- **有效性评分函数**：`valid = (n_results > 0) AND (nonempty_ratio > θ1) AND (unique_url_ratio > θ2) AND (query_overlap > θ3)`，阈值需用历史正常/空壳样本校准，避免误杀长尾查询的合法空结果（"确实没有结果"与"检索失效"必须区分——这是难点，建议用**已知有结果的探针 query** 做健康判定，而非用用户 query 判定）。
- **熔断状态机**：closed → (连续 N 次无效) → open(冷却 T) → half-open(单次试探) → closed/open。N、T 按源配置，需暴露指标。
- **健康探针**：每源维护一组"金丝雀 query"（已知应返回非空结果），周期探测，结果写入健康分，供路由使用。
- **路由**：按健康分加权 + 查询类型规则，首选失败即降级，降级链长度上限（防雪崩）。
- **可观测**：每源成功率、空壳率、P50/P99 延迟、熔断打开次数，全部打点。

## 深层追问
**底层原理**：核心是"信号与事实分离"。HTTP 200 是传输层信号，不代表语义层有内容；熔断器传统上监听传输层失败，因此对"成功但空"的故障天然失明。修复的本质是把熔断输入从"请求是否成功"改为"结果是否有效"——即用语义有效性作为健康信号。这背后是控制论里的可观测性原则：你只能控制你能量测的东西，而"空壳"恰恰是量测盲区。多源 fallback 则是冗余原理，但冗余只有在能正确判定单源失效时才有效，否则只是把同一个盲区复制三份。

**反例与限制**：① 合法空结果确实存在（冷门 query、拼写错误、时效性极强的事件），有效性校验会误判为故障，导致熔断误开、降级到更差的源。② 金丝雀 query 本身可能被上游限流或地域屏蔽，探针失败≠源失效，会造成健康分抖动。③ 多源 fallback 引入路由复杂度单点：路由 bug 可让全部源被跳过，比单源故障更糟。④ 若上游是 SearXNG 聚合 DDG，空壳会穿透聚合层，fallback 到 SearXNG 等于没降级。⑤ 熔断状态机在分布式多实例下需共享状态，否则各实例健康分不一致。

**如果错了**：最可能的错法是阈值校准不当——θ 设太松，空壳漏检，虚假确定性依旧；设太紧，合法空结果被熔断，检索可用性反而下降。缓解：先用金丝雀样本离线校准，上线后监控"熔断打开率"与"用户 query 空结果率"的相关性，异常即回滚阈值。另一错法是只做校验不做探针，导致熔断依赖用户流量触发，低流量时段故障无法被发现。

**对零最可操作的一步**：先做步骤 1——20 条金丝雀 query 复现 DDG Lite 空壳，拿到故障基线。没有这个基线，后面所有阈值都是拍脑袋，且无法区分"修源"还是"换源"。半天成本，直接决定后续设计方向。
