## 深度研究

你给出的结构里，「搜索摘要」三项（GitHub / arXiv / HN）全空，「全文内容（已抓取）」也是空的。没有可分析的文本，任何「深度分析」都只会是我凭训练数据编出来的，而不是基于你所谓已抓取的内容。那正是你最该避免的东西：检索层失效时用生成层假装检索层还在工作。

不过你这条消息里有一个真问题值得直接回应，它比那份空摘要重要：

**你诊断对了瓶颈，但把 fallback 链当成了工程解，这一步可能是错的。**

几个具体判断：

1. **SearXNG / Brave / Tavily / Exa 不是同一层的东西。** SearXNG 是元搜索引擎（自托管、聚合上游），Brave 是独立索引+API，Tavily 和 Exa 是面向 LLM 的检索 API（Exa 偏语义/神经检索，Tavily 偏 agent 场景）。把它们串成一条 fallback 链，等于把「聚合器」和「被聚合的源」混在一层。SearXNG 挂了 fallback 到 Brave 合理；但 SearXNG 本身就在调 Brave/Google 等，链路里会出现同一上游被走两遍，fallback 的独立性是假的。

2. **真正的 fallback 要按「失效模式」分层，不是按「产品名」排队。** 检索失效至少有四种：网络/配额失败（该重试或换 provider）、上游索引缺失（该换索引源）、查询语义不匹配（该换检索范式，关键词→语义）、结果质量差（该重排或换源）。一条线性链只能治第一种。你现在「社交发现/深度研究/故障溯源全瘫痪」，大概率不是单一 provider 宕机，而是查询范式不对——那换多少个 provider 都没用。

3. **可验证性被高估了。** 你说「有明确可验证的工程解」，但 fallback 链的可验证性只到「请求是否返回」这一层。返回了但内容不对，链是绿的，能力还是瘫的。你需要的是每层的质量信号（结果数、去重后新颖度、与查询的语义相关度），否则 fallback 只是把静默失败换成了静默成功。

**可操作的最小下一步：**
- 先别搭四级链。用一次真实失败查询，手动分别打 SearXNG、Brave、Tavily、Exa，记录：返回码、结果数、前 5 条是否相关。这一步就能告诉你失效在哪一层。
- 按失效模式写三个独立分支（重试/换源/换范式），而不是一条 if-else 产品链。
- 给每层加一个质量闸门，不达标才降级。

## 深层追问
**底层原理**：fallback 链的隐含假设是「失效可被 provider 切换吸收」。但检索是两段函数——召回(索引覆盖×查询匹配)与排序。换 provider 只改召回源，不改查询与索引的匹配关系。所以单链只在「同一范式内某源宕机」时有效。

**反例/限制**：
- 反例：查询是「上周某推文」，SearXNG/Brave/Tavily/Exa 全走关键词或网页索引，全召不回——四级链全绿，结果全空。失效在范式，不在 provider。
- 限制：SearXNG 聚合 Brave，链里 Brave 出现两次，独立性是假的；配额失败与索引缺失被混为一类，重试治不了后者。
- 质量闸门本身有假阳性：结果数达标但语义漂移，链判「成功」。

**如果错了**：错在把「可用性」当「有效性」。代价是静默失败——比宕机更危险，因为监控不报警，你以为能力还在。

**对零最可操作的一步**：拿一次真实失败查询，手动打四个源，只记三项：返回码、结果数、前5条是否相关。若四源都返回但都不相关→问题在查询范式，别搭链，去改检索方式（关键词→语义/时间过滤）。若只有某源失败→那才是 fallback 该管的事。先测，再建。
