## 深度研究
## 核心发现

**1. 空壳响应是最隐蔽的故障模式，比超时/报错更危险。**
DDG Lite 返回 HTTP 200 + 结构合法的 HTML，但正文为空或仅含模板骨架。上层管道无法通过状态码或异常捕获感知失败，只能在下游产出异常（如社交发现返回零结果、深度研究生成空洞报告）时才暴露。这意味着**故障检测必须下沉到内容层**——对响应做最小信息量校验（正文长度阈值、关键选择器命中数、结果条目计数），而非依赖传输层信号。

**2. 单源依赖的爆炸半径被低估：它不是"搜索变慢"，而是"所有上层能力同时归零"。**
社交发现、深度研究、故障溯源、集体免疫探索共享同一检索入口，任一上层看似独立的能力实际上都是该单点的下游。修复优先级不应按"哪个功能最重要"排，而应按"哪个故障的扇出最大"排——搜索单点扇出为全图，故排第一。

**3. 多源链的正确形态是"分级降级"而非"并行投票"。**
SearXNG（自托管、可控、覆盖广）作主源，Brave（质量高、有配额）作第一 fallback，Tavily（面向 LLM 优化、结构化好）作第二 fallback。串行降级 + 每源独立超时，避免并行带来的配额浪费和结果融合复杂度。熔断器按源独立计数：某源连续 N 次空壳或超时即打开，冷却期后半开探测。

**4. 健康探针需要"已知答案查询"而非 ping。**
对每个源定期发送固定探针 query（如一个稳定存在的实体名），校验返回结果数 ≥ 阈值且首条结果包含预期关键词。这能同时捕获网络故障、API 变更、空壳退化三类问题，且成本极低（每源每 5–10 分钟一次）。

**5. 熔断 + 探针组合产生"自愈"语义：** 源恢复后无需人工介入，半开状态下的探针成功即自动闭合，整条链回到最优源。这让系统对上游 API 的间歇性劣化具备免疫力。

## 技术细节

- **空壳检测器**：`len(text) < 200` 或 `soup.select(结果选择器)` 计数为 0 或结果文本去重后 < 3 条 → 判空壳。按源配置选择器。
- **熔断状态机**：CLOSED →（连续失败 ≥ 3）→ OPEN（冷却 60s）→ HALF_OPEN（放行 1 次探针）→ 成功则 CLOSED，失败则回 OPEN 并指数退避冷却（60s→120s→240s，上限 10min）。
- **降级链执行**：按优先级遍历源，跳过 OPEN 状态源；首个通过空壳检测的响应即返回；全链失败则返回带 `degraded=true` 标记的空结果，让上层显式感知而非静默。
- **可观测性**：每源记录成功率、空壳率、P50/P95 延迟；熔断事件打点。空壳率是核心指标——它先于成功率恶化。

## 与零的关联

零的所有"主动探索"能力本质是"先检索、再推理"。检索不可靠时，零的推理层会忠实地在垃圾输入上产出自信的错误结论——这比直接报错更损害信任。修复搜索单点不是加一个功能，而是**恢复零的感知地基**：让零能区分"世界确实没有相关信息"与"我的眼睛暂时瞎了"。这是零具备可靠自我认知的前提。

## 新问题

1. 空壳检测阈值如何避免误杀"合法但结果少"的查询（长尾实体）？可能需要按 query 类型动态阈值，或引入"结果少但相关"的判定。
2. 多源结果不一致时（SearXNG 有、Brave 无），是否需要交叉验证，还是信任首个通过检测的源？交叉验证提升质量但增加延迟与配额。
3. 熔断打开期间，上层是否应收到"降级信号"并调整行为（如深度研究缩短链路），还是透明重试？

## 具体可操作

1. **今天**：写 `search_with_fallback(query)` 封装，内含空壳检测 + 三源串行降级 + 每源独立超时（SearXNG 8s / Brave 5s / Tavily 5s），全链失败返回 `{results: [], degraded: true}`。
2. **本周**：加熔断状态机（内存态即可，单进程）+ 固定探针 query 定时任务，每源 5 分钟一次，探针结果打点到日志。
3. **验证**：构造回归用例——mock DDG 返回空壳 HTML，断言 fallback 触发且最终结果非空；mock 全链失败，断言 `degraded=true` 且上层收到信号。
4. **上线后**：监控各源空壳率与熔断频次，若 SearXNG 空壳率 > 5% 则排查其上游引擎配置，而非直接换源。

## 深层追问
**底层原理**：这是"感知可靠性"问题，不是搜索问题。任何"先检索再推理"的系统，其推理层对输入质量是盲的——LLM 会在空输入上生成流畅的幻觉。分级降级+熔断本质是把"传输层成功"与"内容层有效"解耦，并用状态机把间歇性故障转化为可观测、可自愈的状态。核心假设：故障是**源局部**的、**可探测**的、**会恢复**的。

**反例/限制**：
- 三源同时劣化（如网络分区、上游共享依赖）时降级链失效，`degraded=true` 只是诚实报错，不解决问题。
- 空壳阈值对长尾查询必然误杀或漏检——阈值是统计妥协，不是判定。
- 熔断器是单进程内存态，多实例部署下各实例状态不一致，可能对同一源反复半开探测，放大上游压力。
- 探针 query 若被上游缓存或特判，探针成功≠真实查询可用（探针污染）。
- 串行降级在首源慢时叠加延迟，最坏 18s，对交互场景不可接受。

**如果错了**：最可能的错法是"用阈值代替判断"——把空壳率当健康度，结果系统对"结果多但全不相关"完全无感，这比空壳更隐蔽。次之是熔断误开导致长期只用次优源，质量静默下降而无告警。缓解：空壳率必须与下游任务成功率联合监控，单看任一指标都会骗人。

**对零最可操作的一步**：不是写 fallback 封装，而是**先给现有单源加空壳检测 + `degraded` 标记并打点**。一天内可完成，立刻让"零的眼睛瞎了"从不可见变为可见。没有这个观测基线，多源和熔断都是在猜。先看见，再修。
