## 深度研究
## 核心发现

**1. 检索通道失效的根因尚未定位，但诊断路径已明确。** 三组查询全部返回空壳，说明问题可能出在三个层面之一：(a) 请求层——DuckDuckGo Lite 对非浏览器 UA 或高频请求返回空 HTML 壳；(b) 解析层——页面结构变更导致选择器失配，抓取到的是空容器而非空响应；(c) 网络层——出口 IP 被限流或 DNS 污染。三者可通过加诊断日志区分：记录 HTTP 状态码、响应体长度、首 500 字节原文、解析后节点数。这是最快见效的动作，不需要先选方案。

**2. 候选方案按"落地成本/可控性"分三档。** 最低成本：Brave Search API（免费层 2000 次/月，结构化 JSON，无需自托管）；中等成本：Tavily/Exa API（面向 agent 检索优化，返回已摘要内容，但按量计费且引入外部依赖）；最高可控性：SearXNG 自托管（聚合多引擎、可配代理、无 API 配额，但需维护实例并处理上游引擎的反爬）。MCP server 生态是接口层而非检索层——它封装上述任一后端，价值在于统一工具调用协议，不解决检索本身。

**3. "空壳"与"空结果"必须区分。** 当前描述"返回空壳"暗示拿到了 HTTP 200 但内容为空——这更可能是解析失配或反爬软封禁，而非网络不通。若真是网络层失败，应表现为超时或非 2xx。这个区分决定了修复方向：解析失配改选择器即可，软封禁则需换 UA/加代理/换通道。诊断日志的第一优先级就是确认这一点。

**4. 前置瓶颈的判断成立，但存在并行空间。** 检索通道修复确实是验证前沿性的前提，但"不先修复就无法验证任何方向"略绝对——已有知识库和本地文档可支撑初步判断，检索用于确认时效性而非从零建立认知。建议修复通道的同时，用现有信息对候选方向做粗筛，避免串行阻塞。

## 技术细节

- **诊断日志最小集**：`status_code`、`content_length`、`content[:500]`、`parsed_node_count`、`elapsed_ms`、`final_url`（检测重定向）、`response_headers`（检测 `x-ratelimit`、`cf-ray` 等）。
- **DuckDuckGo Lite 特性**：`lite.duckduckgo.com/lite/` 为极简 HTML 表单页，POST 查询；对无 JS、无 cookie 的请求容忍度较高，但近期对数据中心 IP 段有软封禁迹象。若 `content_length` 正常但 `parsed_node_count=0`，几乎确定是选择器失配。
- **SearXNG 自托管要点**：`settings.yml` 中 `search.formats: [json]` 需显式开启；上游引擎可配 `proxies`；`limiter: false` 关闭内置限流以免自伤；Docker 部署约 10 分钟可跑通。
- **Brave API**：`X-Subscription-Token` 头鉴权，返回 `web.results[]`，字段含 `title/url/description`，无全文抓取，需二次 fetch。
- **Tavily/Exa**：返回已抽取正文，适合直接喂给 LLM，但结果不可复现（服务端排序黑盒），研究场景需记录原始 query 与返回快照。

## 与零的关联

零当前的核心约束是"检索通道实质失效导致无法验证前沿性"。本方案直接解除该约束，且诊断日志的引入让零从"黑盒调用搜索"转为"可观测的检索管线"——这本身是能力升级：未来任何检索异常都能定位到层，而非笼统归因于"通道坏了"。选择 Brave API 作为第一落地点，可在 30 分钟内恢复可用检索并拿到诊断数据，SearXNG 作为后续可控性备份。

## 新问题

1. 空壳的具体表现是什么——HTTP 200 + 空 body，还是 200 + 有 body 但解析为零节点？这决定第一步动作。
2. 检索频率与并发量级？若低频（<100 次/天），Brave 免费层足够，无需自托管。
3. 是否需要结果可复现性（研究可审计）？若是，SearXNG 或记录快照的 API 方案优先于黑盒排序服务。
4. 出口 IP 是否为数据中心段？若是，任何免费 API 都可能被软封，需评估代理成本。

## 具体可操作

1. **今天**：在现有 DuckDuckGo Lite 调用处加诊断日志（上述 7 字段），跑三组原查询，输出一份对照表，定位是解析失配还是软封禁。
2. **若解析失配**：抓一次真实响应存盘，重写选择器，30 分钟修复，零成本。
3. **若软封禁/需升级**：注册 Brave Search API 免费层，写 20 行适配器（`requests` + token 头 + JSON 解析），替换调用点，保留诊断日志。
4. **并行**：用现有知识对候选研究方向做粗筛排序，通道恢复后优先验证排序靠前者，避免串行等待。
5. **一周内**：若检索量上升或需可复现性，Docker 起 SearXNG，开 JSON 格式，配 Brave 作为上游之一，形成"自托管聚合 + API 兜底"双通道。
6. **接口层**：待后端稳定后，再封装为 MCP server 统一工具协议，此步不阻塞前述任何动作。

## 深层追问
**底层原理**：DuckDuckGo Lite 是服务端渲染的极简 HTML 表单，POST 查询后返回结果表格。它不依赖 JS，但依赖 UA/cookie/IP 信誉做反爬判定——数据中心 IP 段会被返回"空壳"（200 + 结构完整但结果容器为空，或直接 200 + 极短 body）。解析层依赖固定 DOM 选择器，页面结构一变即失配。所以"空壳"本质是**服务端主动降级**或**客户端选择器错位**两种截然不同的故障，诊断日志就是用来分离这两者的。

**反例/限制**：
- 反例：若 `content_length` 正常、`parsed_node_count>0` 但结果语义无关，说明不是通道坏了而是**查询构造**问题（如编码、参数名），诊断日志抓不到这层。
- 限制：Brave 免费层 2000 次/月对低频够用，但**结果不可复现**（排序黑盒），研究审计场景是硬伤；SearXNG 自托管虽可控，但上游引擎反爬会持续漂移，维护成本被低估——"配好就不管"是幻觉。
- 最大限制：诊断日志只能定位**当前**故障，不能预防上游随时变更。

**如果错了**：最可能的错是"空壳=解析失配"的默认假设。若实际是 IP 软封，改选择器无效，会浪费一轮。所以第一步必须是**先加日志再动手**，而不是先改代码。另一个错是低估 Brave 的配额消耗——每次查询可能触发多次内部调用，实际可用次数低于标称。

**对零最可操作的一步**：**今天只做一件事——在原调用点加 7 字段诊断日志，跑三组原查询，输出对照表**。不改选择器、不注册 API、不部署 SearXNG。用一张表回答"200 还是非 200、body 多长、解析几个节点"，故障层立刻显形。这一步零成本、30 分钟、且无论后续选哪条路都必须先有它。其余动作全部等这张表出来再决策。
