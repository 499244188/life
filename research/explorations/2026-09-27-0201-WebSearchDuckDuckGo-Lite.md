## 核心判断

**把“云端 WebSearch 替代 DuckDuckGo Lite”当作唯一瓶颈，这个前提需要先验证，而不是直接接受。**

理由：

1. **DuckDuckGo Lite 失效 ≠ 搜索层失效。** 它只是众多可替换端点之一。真正要区分的是：
   - 是 DDG 封了你的请求特征（UA、频率、IP）？
   - 还是你的抓取/解析管线坏了？
   - 还是网络出口本身不通？
   这三种原因的修法完全不同，直接跳到“换云端方案”可能是在治错病。

2. **“云端 WebSearch”不是一个方案，是一类方案。** 至少分三层：
   - **托管搜索 API**：Brave Search API、Bing Web Search API、Tavily、Exa、Serper、SearXNG 自建。
   - **自建元搜索**：SearXNG 实例 + 自己的解析层，可控性最高，但要维护。
   - **浏览器级抓取**：Playwright/headless + 搜索引擎结果页解析，最脆弱，最容易再被封。

3. **投入产出比最高的往往不是“换云端”，而是“加一层可切换的搜索抽象”。** 把搜索做成接口，后端可插拔（DDG Lite → SearXNG → Brave API → Tavily），这样单点失效不再瘫痪全部能力。这比赌某一个云端方案更稳。

## 与零的关联

如果“零”是一个依赖搜索做社交发现、深度研究、故障溯源的 agent，那么：

- **搜索是它的感知层**，感知层单点故障 = 上层全瘫。这个判断方向是对的。
- 但正确的工程动作是**冗余 + 抽象**，不是**替换单点**。替换单点只是把“DDG 挂了”变成“Brave 挂了”。
- 另外要问：社交发现和故障溯源真的都依赖通用 WebSearch 吗？故障溯源很多时候靠的是日志、issue tracker、特定 API，不是通用搜索。把不同能力都压在同一个搜索层上，本身就是架构问题。

## 深层追问
**底层原理**：搜索抽象层的本质是把“查询→结果”定义成稳定接口，后端可插拔。失效隔离靠的是接口边界，不是某个后端更稳。缓存+降级是核心：同一 query 命中缓存直接返回，未命中按优先级调后端，失败自动切下一个。

**反例/限制**：
1. 抽象层不解决“所有后端同时被限流”——免费端点共享 IP 池时可能一起挂。
2. 不同后端结果格式、排序、时效性差异大，统一成同一 schema 会丢信息或引入偏差。
3. 缓存有 stale 问题：故障溯源、新闻类查询缓存反而有害。
4. 自建 SearXNG 要维护，实例被滥用会被上游封，等于把单点故障换了个位置。
5. 延迟叠加：降级链越长，最坏情况响应越慢。

**如果错了**：错在“把架构问题当成端点问题”。如果 DDG Lite 失效其实是解析管线坏了，换任何后端都白搭；如果是网络出口问题，云端 API 也走同一出口照样挂。先归因，再动手。

**对零最可操作的一步**：用 curl 直接打 DDG Lite，记录状态码/响应体/耗时，确认是限流、网络还是解析。这一步 5 分钟，能决定后面所有方向。在归因完成前，不要写任何抽象层代码——那可能是在给错误的病做手术。
